# 登录页 · 白话版

> 这一章讲一件很小的事：怎么确认「你是你」，然后把这句话记住，直到你下次来。

## 一、登录页的位置：它为什么被放在 Layout 之外

去银行办事，你会先经过大堂、取号机、等候区，最后才到柜台。但 VIP 室不一样——它不在大堂的动线上，你得先被领进去。

登录页就是这间 VIP 室。前面所有页面都长在同一个「大堂」里：顶上一条导航，底下一条页脚，中间换内容。这个外壳叫 `Layout`。登录页偏偏不在里面，它是和大堂**并排**的另一个房间。

为什么不放进去？因为大堂的墙上挂着一块牌子，写着「你好，张三 · 购物车 3 件」。登录页的工作恰恰是「还不知道你是谁」。你一进门，牌子写着「请先登录」，而表单就在旁边让你输入账号——这画面很荒唐。

还有个更实际的麻烦：大堂一开张就会去问仓库「今天有哪些分类」「购物车里有什么」，这些都是要先知道你是谁才能答的问题。登录页被塞进大堂，就等于每次登录都先挨三个「你是谁」的白眼。

所以最简单的一条规矩：**登录页上不该出现需要登录才能拿的数据**。如果你在登录页看到红色的「未授权」，先别怀疑接口，先怀疑它是不是被错塞进大堂了。

## 二、路由配置与进入登录页的入口

一栋楼有几个门都能进大厅：正门、侧门、地下车库的电梯。登录页也有四个门——导航栏的「请先登录」、结算时被拦下、退出登录、以及朋友发来的一条链接。四个门必须通到同一个房间，地址都是 `/login`。

进门之后怎么走，才是这一节真正的内容。

`push` 和 `replace` 的区别，可以想成「在书里夹书签」和「撕掉刚才那页」。

- `push` 是夹书签：你看完登录页，再夹一张首页的书签。想回头翻，第一个翻到的是登录页。
- `replace` 是撕页：登录成功后把「登录页」这一页直接撕掉，你回翻只会回到更早的那页。

登录成功要用 `replace`。否则用户登录完、进了首页、随手按一下返回——回到登录页，而他明明已经登录了。移动端用户特别爱按返回键，这个坑几乎人人都踩过。

还有一种情况需要「记住你要去哪」。用户想看订单，被拦下来先去登录。等他登录完，你总不能把他丢回首页——他刚才明明是要看订单的。所以拦他的时候要在他口袋里塞张纸条：`/login?redirect=/member`，登录成功后按纸条上的地址送他过去。

但这张纸条是**用户自己能写的**。坏人可以伪造一张写着「去钓鱼网站」的纸条，用户登录完就被送到假页面。所以纸条上的地址只能认站内的，凡是开头不是 `/` 的，一律当没写。

## 三、表单校验：规则、触发时机与自定义校验器

填快递单时，快递员不会等你把整张单子填完再指错。他会一边看一边说「电话少了一位」「地址写到区就行」。这就是「边填边校验」；而你把单子交上去、他扫一眼说「重填」，那是「提交时校验」。

两种都要有，但**时机**很讲究。

账户不能为空——这一条适合在「离开输入框」时提示。你刚点进输入框、一个字还没打，就弹「不能为空」，纯属找骂。

密码 6–14 位——同样适合离开输入框再提示。如果设成「一变化就校验」，你打第一个字符时看到「长度不足」，会觉得这表单在嘲讽你。

「必须勾选协议」——这一条适合「一变化就校验」。勾选框只有勾和不勾两种状态，用户一勾上就能立刻看到提示消失，反馈非常干脆。

这三条规则写在一起，长这样：

```js
const rules = {
  account: [{ required: true, message: '用户名不能为空', trigger: 'blur' }],
  password: [
    { required: true, message: '密码不能为空', trigger: 'blur' },
    { min: 6, max: 14, message: '密码长度要求 6-14 个字符', trigger: 'blur' },
  ],
  agree: [{ validator: (rule, val, cb) => (val ? cb() : cb(new Error('请先同意协议'))), trigger: 'change' }],
}
```

规则要生效，还差三样东西对上号：`model` 告诉表单「数据在哪」，`rules` 告诉它「规矩是什么」，`prop` 告诉每个输入框「你对应哪条规矩」。

这里的 `prop` 是**按名字对**的。就像快递单上写着「收件人：李四」，而你填在「寄件人」那一栏——单子没填错，但它不属于那一栏。`prop="account"` 而规则里叫 `userName`，那条规矩就永远没人认领，校验静默失效。新手排查半天「为什么密码有红字、账户没有」，八成就是这个。

最后一条自定义规则要「回话」。校验器被问「这条过了吗」，你必须明确回答「过了」或「没过」。忘了回话，它既不算过也不算不过——规矩就蒸发了。

## 四、登录业务：从校验通过到跳转首页

去餐厅吃饭，点菜、下单、上菜、买单，顺序乱了就出事。登录也一样，四步：

1. **先验票**：表单校验过了吗？没过就停在这里。
2. **再去核身份**：调登录接口，把账号密码发过去。
3. **告诉用户结果**：成功了就说「登录成功」。
4. **送到目的地**：按纸条上的地址（或者首页）跳过去。

代码大概是这个形状：

```js
const doLogin = async () => {
  const valid = await formRef.value.validate().catch(() => false)
  if (!valid) return
  await userStore.getUserInfo({ account: userInfo.value.account, password: userInfo.value.password })
  ElMessage({ type: 'success', message: '登录成功' })
  router.replace(route.query.redirect || '/')
}
```

有个容易踩的地方：`validate()` 有两种「通知方式」。旧方式像对讲机——你喊一声，它用另一台机器回你；新方式像打电话——你拨过去，它直接在电话里回，没接通就「砰」地挂断（抛错）。用打电话这种方式时必须接住那个「砰」，也就是 `.catch()`。不接，控制台就会冒出一条没人处理的异常。功能没坏，但下次真出问题，你会在噪声里找不到它。

还有一件小事：用户手快，会连点两下登录按钮。两下就是两次请求，两次请求就是两条登录记录。解决办法是给按钮加个「正在忙」的开关——忙的时候按钮变成转圈、不能点。这个开关顺便还解决了另外两件事：用户知道「我点上了」，以及请求失败后按钮能恢复、可以重试。

## 五、Pinia 管理用户数据：state、action 与持久化

一个人搬家，最省事的做法不是每次要用东西就跑回旧房子拿，而是**一次性搬进新家**，之后随用随取。

Pinia 就是那个新家。组件不该知道「登录接口叫什么、参数怎么拼」，它只该说「给我一份用户信息」。真正干活的函数放在 store 里：

```js
export const useUserStore = defineStore('user', () => {
  const userInfo = ref({})
  const getUserInfo = async ({ account, password }) => {
    const res = await loginAPI({ account, password })
    userInfo.value = res.result
  }
  const clearUserInfo = () => { userInfo.value = {} }
  return { userInfo, getUserInfo, clearUserInfo }
}, { persist: true })
```

最后那个 `persist: true` 是关键。没有它，`userInfo` 只活在内存里——用户按一下 F5 刷新，就像断了电，家当全没了，他会被要求重新登录。有了它，Pinia 会把这个 store 的内容写进浏览器本地存储，刷新后自动读回来。

「搬家」也有讲究：**清空时要整箱清，不要逐件挑**。写成 `userInfo.value = {}` 而不是把 `token`、`nickname`、`avatar` 一个个置空——因为逐件清一定会漏，而漏掉的那一件，往往就是权限判断要用的那一件。

还有一条：**别存两份相同的状态**。有人喜欢额外加一个 `isLogin` 布尔值，登录时设 `true`、退出时设 `false`。问题是它和 `token` 是两回事，总会有一次只更新了其中一个。正确的做法是不存它，用的时候现算：有 token 就是登录了。

## 六、请求拦截器：给每个请求加上 token

进公司大楼，第一天办张门禁卡。之后你走哪道门都不用再掏身份证——闸机自动认你的卡。

token 就是这张门禁卡，**请求拦截器**就是那道闸机。它待在「请求即将发出」的这个位置上，每来一个请求就自动往口袋里塞一张卡：

```js
httpInstance.interceptors.request.use(config => {
  const userStore = useUserStore()
  const token = userStore.userInfo.token
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
```

把这个动作放在这里，而不是放在每个接口函数里，理由很朴素：**放在几十个地方一定会漏，放在一个地方不会漏**。而且哪天物业换了读卡方式（比如从 `Bearer` 改成别的头），你只需要改这一处。

`Bearer` 是个固定单词，意思是「持卡人」。写成 `bearer`、`Bearer x` 少个空格、或者漏掉空格，闸机都不认。

闸机还有另一个方向：**出门时也要看一眼**。如果服务器回来说「卡失效了」（状态码 401），响应拦截器就该做三件事——把本地这张废卡扔掉、把用户送回登录页、并且告诉他「刚才要去哪」，省得他登录完还得自己再点一遍。

这里有个特别容易翻车的细节：拦截器是**在文件被加载的那一刻**注册的，而那时候 Pinia 可能还没装好。你在拦截器外面就调用 `useUserStore()`，会得到一个「当前没有 Pinia 实例」的报错。正确姿势是把这行调用放到拦截器函数**里面**——等真的来请求了，Pinia 早就准备好了。

## 七、退出登录与登录态失效的处理

退房要按顺序：先还钥匙，再走人。反过来——人已经出小区了，钥匙还在兜里，下一位住户进不来。

所以退出登录的顺序是：**先清状态，再跳转**。

```js
const confirm = () => {
  userStore.clearUserInfo()
  router.replace('/login')
}
```

反过来写会露馅：页面已经跳走了，store 里还留着旧用户。那些依赖 store 的地方会短暂显示「你好，张三」，而张三已经走了。

真实项目里还会多一步——给服务器打个电话说「这张卡作废了」。但这一步必须包在「无论如何都继续」的保护里：

```js
try {
  await logoutAPI()
} finally {
  userStore.clearUserInfo()
  router.replace('/login')
}
```

因为如果网络不通、接口挂了，用户就退不出去了。把「退出」绑死在网络成功上，等于给用户留了一扇从里面打不开的门。

还有另一种「退出」是用户没主动做、但系统替他做的：**卡过期了**。这时候的处理路径和主动退出完全一样（清本地、回登录页、记住原地址），唯一该不同的是提示语——主动退出不用说什么，被动过期要说一句「登录已过期，请重新登录」，不然用户会以为自己刚才手滑点错了什么。

最后提一下前面那张「纸条」的安全写法。只认站内地址，判断方式是看它是否以单个 `/` 开头：

```js
function safeRedirect(path) {
  if (typeof path !== 'string') return '/'
  if (!path.startsWith('/') || path.startsWith('//')) return '/'
  return path
}
```

`//evil.example.com` 看起来像站内路径，其实浏览器会把它当成「换一台服务器」。所以光判断「有没有 `/`」不够，还得排掉「两个斜杠开头」。这类问题用「只允许什么」的白名单去挡，永远比用「禁止什么」的黑名单可靠。

## 八、工程实践与常见坑

**一、`prop` 拼错。** 规矩没人认领，那一项永远通过，而且不报错。表现是「有的字段有提示、有的没有」。

**二、`await validate()` 不接 `.catch`。** 校验失败时抛出一条没人处理的异常，控制台红一片。

**三、登录成功用 `push`。** 用户按返回键回到登录页，还以为自己没登录成功。

**四、`redirect` 直接拿去跳转。** 用户能被送到站外，这是真正的安全漏洞，不是体验问题。

**五、token 存 `localStorage` 就以为安全了。** 同源的任何一段脚本都能读走它。至少要做到：不往 `innerHTML` 里塞用户输入、依赖定期升级、敏感操作二次确认。

**六、拦截器外面调用 `useUserStore()`。** 报「没有 Pinia 实例」。把这行挪进拦截器函数体内。

**七、退出登录先跳转后清状态。** 页面上会闪一下旧用户名。

**八、退出接口失败就不清本地。** 用户退不出去。用 `finally` 兜住。

**九、登录页放进 `Layout`。** 一进页面就打三个需要登录态的接口，满屏 401。

**十、只清内存不清本地存储。** 刷新一下又「自动登录」了。用 store 的 action 统一清，别手写 `localStorage.setItem`。

## 一句话总结

登录页做的三件事——**验明身份、把身份存到你翻不过去的地方（store + 持久化）、再把你送回刚才想去的地方**——其余全是细节，而细节里最贵的那条是：`redirect` 只认站内地址，退出顺序永远是先清状态再跳转。
