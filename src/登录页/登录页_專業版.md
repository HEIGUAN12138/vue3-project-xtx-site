# 登录页

> 登录页是全站唯一一个「不认识用户」的页面。它的全部工作只有三件：确认你是你、把你的身份存下来、把页面还给你刚才想去的地方。

## 一、登录页的位置：它为什么被放在 Layout 之外

前面几章的所有页面都挂在 `Layout` 这个外壳下：顶部有导航、底部有页脚、中间是 `<RouterView />`。登录页是个例外，它是一条**平级的顶层路由**，不嵌套在 `Layout` 里。

```js
// router/index.js
{
  path: '/login',
  component: () => import('@/views/Login/index.vue'),
}
```

原因不是审美，而是状态：`Layout` 的顶部导航要渲染「购物车件数」「你好，某某」这些依赖登录态的内容。如果登录页也放在 `Layout` 里，用户在表单里输入账号时，顶部导航就在旁边显示「请先登录」，逻辑上自相矛盾；更实际的问题是，`Layout` 在 `onMounted` 里会发起分类、购物车等请求，登录页一进来就白白多打几个接口。

所以登录页自带一套极简外壳：顶部只有 logo 和「进入网站首页」的入口，底部只有一排无关紧要的页脚链接。它和 `Layout` 是**并列关系**，不是父子关系：

```
/                     Layout
├── /                 Home
├── /category/:id     一级分类
├── /detail/:id       商品详情
└── /login            独立页面（不在 Layout 内）
```

这一节的推论是：**任何依赖登录态的请求，都不该在登录页触发**。一旦你发现登录页打出「未授权」的红色报错，先检查是不是它被错误地放进了 `Layout`。

## 二、路由配置与进入登录页的入口

入口一共有四个，它们都必须指向同一个地址 `/login`：

```html
<!-- 1. 顶部导航的「请先登录」 -->
<li><a href="javascript:;" @click="router.push('/login')">请先登录</a></li>

<!-- 2. 结算时未登录，被路由守卫拦下 -->
<!-- 3. 退出登录后主动跳转 -->
<!-- 4. 站外分享链接直接打开 -->
```

第一个入口用 `<a href="javascript:;">` 而不是 `<RouterLink>`，是因为它处在一个需要阻止默认行为的 DOM 结构里；更好的写法仍然是用 `<RouterLink to="/login">`，让浏览器保留「中键新开标签页」的能力。

**跳转方式分两种**，`push` 与 `replace` 的区别在这个页面格外重要：

```js
// 登录成功后：replace，把「登录页」从历史记录里抹掉
router.replace('/')

// 退出登录：push，让用户还能「前进」回会员中心？
router.push('/login')   // 实践上仍推荐 replace + 清空历史
```

用 `replace` 的理由是**返回键陷阱**：如果用 `push`，用户登录成功、进到首页、按一下浏览器返回，会回到登录页——而他明明已经登录了。这个坑在移动端尤其明显，因为很多用户习惯用返回键代替首页按钮。

还有第三种情况需要 `redirect` 参数：用户直接访问 `/member`，被守卫拦下来送到 `/login`，登录成功后应该回到 `/member` 而不是首页。这时路由是 `/login?redirect=/member`：

```js
router.replace(route.query.redirect || '/')
```

`redirect` 是**用户可控的输入**，必须校验：`redirect` 只能是站内路径，否则就是开放重定向漏洞（open redirect）——攻击者构造 `/login?redirect=https://evil.example` 让用户登录后跳到钓鱼站。校验方式在第七节展开。

## 三、表单校验：规则、触发时机与自定义校验器

校验要求只有三条：账户不能为空、密码 6–14 位、必须勾选协议。这三条在 Element Plus 里写成一个规则对象：

```js
import { ref } from 'vue'

const userInfo = ref({ account: '', password: '', agree: false })

const rules = {
  account: [{ required: true, message: '用户名不能为空', trigger: 'blur' }],
  password: [
    { required: true, message: '密码不能为空', trigger: 'blur' },
    { min: 6, max: 14, message: '密码长度要求 6-14 个字符', trigger: 'blur' },
  ],
  agree: [
    {
      validator: (rule, val, callback) => {
        return val ? callback() : callback(new Error('请先同意协议'))
      },
      trigger: 'change',
    },
  ],
}
```

模板侧的关键是三个绑定，缺一个校验就不会生效：

```vue
<el-form ref="formRef" :model="userInfo" :rules="rules" status-icon>
  <el-form-item prop="account" label="账户">
    <el-input v-model="userInfo.account" />
  </el-form-item>
  <el-form-item prop="agree" label-width="22px">
    <el-checkbox v-model="userInfo.agree" />
  </el-form-item>
</el-form>
```

- `:model` 提供数据源，`:rules` 提供规则，`prop` 把表单项和规则里的字段名对上。三者是**字符串匹配**关系，`prop="account"` 对不上 `account` 规则时，那一项永远校验通过，而且不报错——这是新手最常见的一类「校验失灵」。
- `trigger` 决定什么时候校验：`blur` 是失焦，`change` 是值变化。密码用 `blur` 而不是 `change`，否则用户输入第一个字符就会看到「长度不足 6」，体验极差。
- 自定义校验器的回调写法必须**返回**结果：旧版 `async-validator` 要求回调里 `callback()` 表示通过、`callback(new Error(msg))` 表示失败；如果忘了返回值，规则会静默失效。

第三条规则还可以用更简洁的写法，直接抛错或返回 Promise：

```js
const rules = {
  agree: [
    {
      validator: (rule, val) => (val ? Promise.resolve() : Promise.reject(new Error('请先同意协议'))),
      trigger: 'change',
    },
  ],
}
```

`async-validator` 同时支持回调、Promise、`throw` 三种风格，但**一个校验器里只该用一种**。混着写会出现「链式校验里第一个错误吞掉了后面所有错误」的问题。

## 四、登录业务：从校验通过到跳转首页

点击登录时，组件只做四件事，顺序不能乱：

```js
import { ElMessage } from 'element-plus'
import 'element-plus/theme-chalk/el-message.css'
import { useUserStore } from '@/stores/userStore'
import { useRouter, useRoute } from 'vue-router'

const formRef = ref()
const userStore = useUserStore()
const router = useRouter()
const route = useRoute()

const doLogin = async () => {
  const valid = await formRef.value.validate().catch(() => false)
  if (!valid) return

  try {
    await userStore.getUserInfo({
      account: userInfo.value.account,
      password: userInfo.value.password,
    })
    ElMessage({ type: 'success', message: '登录成功' })
    router.replace(route.query.redirect || '/')
  } catch (e) {
    ElMessage({ type: 'error', message: e.response?.data?.msg || '账号或密码错误' })
  }
}
```

几个细节值得单独拿出来说。

**第一，`validate()` 的两套调用方式。** 老写法是 `formRef.value.validate(valid => { ... })`，新写法是 `await formRef.value.validate()`。区别在失败时：回调式**不会抛错**，Promise 式**会 reject**。所以 `await` 必须配 `.catch()`，否则校验不通过时控制台会多一条无人处理的 Promise 异常——功能没错，但会让真正的问题淹没在噪声里。

**第二，为什么先 `ElMessage` 再跳转。** 提示框是挂在 `body` 上的独立层，跳转不会销毁它；但如果组件自己实现了「页内成功条」，跳转就会把它连同组件一起卸载。用消息组件而不是页内提示，是刻意的选择。

**第三，`replace` 不是 `push`。** 见第二节。

**第四，登录请求不能重复发。** 用户手快连点两下，会发两次登录请求。处理方式是加一个 `loading` 状态把按钮禁用：

```js
const loading = ref(false)
const doLogin = async () => {
  if (loading.value) return
  loading.value = true
  try { /* ... */ } finally { loading.value = false }
}
```

按钮写 `<el-button :loading="loading">`，Element Plus 会自动变成转圈并把按钮置为不可点。这一个开关同时解决了三件事：重复提交、用户不知道点没点上、请求失败后无法重试。

## 五、Pinia 管理用户数据：state、action 与持久化

组件不该知道「登录接口叫什么」，它只该知道「我要一份用户信息」。这层职责被搬到 Pinia：

```js
// stores/userStore.js
import { defineStore } from 'pinia'
import { ref } from 'vue'
import { loginAPI } from '@/apis/user'

export const useUserStore = defineStore('user', () => {
  const userInfo = ref({})

  const getUserInfo = async ({ account, password }) => {
    const res = await loginAPI({ account, password })
    userInfo.value = res.result
  }

  const clearUserInfo = () => {
    userInfo.value = {}
  }

  return { userInfo, getUserInfo, clearUserInfo }
}, {
  persist: true,
})
```

`persist: true` 来自 `pinia-plugin-persistedstate`，它把整个 store 序列化进 `localStorage`。没有这一行，用户按 F5 刷新页面就会「掉线」——因为 `userInfo` 只活在内存里。

三个结论随之而来：

- **持久化的是整份 `userInfo`，包括 token。** 所以 `localStorage` 里躺着你的登录凭证，任何能执行脚本的东西都能读走。这是第六节的伏笔，也是案例分析里 Ticketmaster 事件的直接教训。
- **`clearUserInfo` 必须把对象换成空对象**，而不是 `userInfo.value.token = ''` 这样逐字段清。逐字段清总会漏掉一两个字段，而「漏掉的那一个」往往就是权限判断依赖的那个。
- **store 里不要存派生数据**。比如「是否登录」不该是一个独立的 `isLogin` 状态，而应该是 `computed(() => !!userInfo.value.token)`。两份状态必然不同步，这个坑在第 10 章购物车里会再出现一次。

组件里只写业务意图，不写业务流程：

```js
const userStore = useUserStore()
const doLogin = async () => {
  const valid = await formRef.value.validate().catch(() => false)
  if (!valid) return
  await userStore.getUserInfo({ account: userInfo.value.account, password: userInfo.value.password })
}
```

## 六、请求拦截器：给每个请求加上 token

登录之后，除了商品列表这类公开接口，其余请求都要带上凭证。如果每个接口函数里都写一遍 `headers: { Authorization: ... }`，结果是：一定会漏，而且改协议时（比如从 `Bearer` 改成 `X-Token`）要改几十个文件。

正确位置是 axios 实例的请求拦截器（request interceptor），它在请求真正发出前被调用：

```js
// utils/http.js
import axios from 'axios'
import { useUserStore } from '@/stores/userStore'

const httpInstance = axios.create({ baseURL: '/api', timeout: 5000 })

httpInstance.interceptors.request.use(
  config => {
    const userStore = useUserStore()
    const token = userStore.userInfo.token
    if (token) config.headers.Authorization = `Bearer ${token}`
    return config
  },
  e => Promise.reject(e)
)
```

这里的 `Bearer` 是 HTTP 认证方案的关键字（`Authorization: Bearer <token>`），它与 `Basic` 并列，属于 RFC 6750 定义的 OAuth 2.0 令牌用法。后端按这个格式解析，前端写错大小写或漏掉空格都会导致 401。

再配一个响应拦截器，把「登录失效」统一处理掉：

```js
httpInstance.interceptors.response.use(
  res => res.data,
  e => {
    if (e.response && e.response.status === 401) {
      const userStore = useUserStore()
      userStore.clearUserInfo()
      router.replace(`/login?redirect=${encodeURIComponent(router.currentRoute.value.fullPath)}`)
    }
    return Promise.reject(e)
  }
)
```

拦截器里有两个容易被忽略的细节。**第一，拦截器是在模块顶层注册的，此时 Pinia 可能还没 `app.use`**。`useUserStore()` 只有在 `main.js` 里 `app.use(pinia)` 之后才能调用，所以拦截器不能在模块加载阶段就调用 `useUserStore()`，必须放到请求回调里**延迟调用**——上面代码里 `const userStore = useUserStore()` 写在拦截器函数体内，就是这个原因。**第二，`router` 要能在非组件环境里用**，通常从 `@/router/index.js` 直接 import 实例，而不是 `useRouter()`（后者只能在 `setup` 里调）。

## 七、退出登录与登录态失效的处理

退出登录的业务只有两步，顺序同样不能反：

```js
const confirm = () => {
  userStore.clearUserInfo()      // 1. 先清状态
  router.replace('/login')       // 2. 再跳转
}
```

反过来写会出问题：如果先跳转再清状态，页面已经渲染成「未登录」的样子，但 store 里还是旧数据，某些依赖 store 的组件会短暂显示「你好，某某」。更严重的是，如果跳转后立刻触发了带拦截器的请求，此时 token 还在，请求会带着已作废的凭证再打一次。

真实项目里退出还要调一个 `logout` 接口，让服务端把 token 拉黑：

```js
const logout = async () => {
  try {
    await logoutAPI()            // 服务端作废 token
  } finally {
    userStore.clearUserInfo()    // 无论接口成功与否，本地都要清
    router.replace('/login')
  }
}
```

`finally` 是刻意的：接口挂了，用户也必须能退出去。把「退出」设计成依赖网络成功，等于给用户留了一扇打不开的门。

**登录态失效（token 过期）和主动退出是两条路径，但终点相同**，都是「清本地 + 回登录页 + 记住原地址」。区别只在提示文案：主动退出不需要提示，被动过期应该告诉用户「登录已过期，请重新登录」，否则用户会以为自己点错了什么。

关于 `redirect` 的安全校验，正确写法是只接受以 `/` 开头且不以 `//` 开头的路径：

```js
function safeRedirect(path) {
  if (typeof path !== 'string') return '/'
  if (!path.startsWith('/') || path.startsWith('//')) return '/'
  return path
}
```

`//evil.example.com` 会被浏览器当成协议相对 URL，`/\/evil` 这类变体也要靠白名单而非黑名单来防。**能用白名单就不要用黑名单**，这是安全领域少有的、几乎不需要权衡的结论。

## 八、工程实践与常见坑

**第一，`prop` 拼错导致校验静默失效。** `prop="userAccount"` 而规则里叫 `account`，那一项永远通过。表现是「密码有提示、账号没有」，很容易被当成组件 bug 排查半天。

**第二，`await validate()` 没接 `.catch`。** 校验失败时抛出未处理的 Promise 拒绝，控制台红一片，真正的问题反而被淹没。

**第三，登录成功后用 `push`。** 用户按返回键回到登录页。应使用 `replace`。

**第四，`redirect` 直接拼进 `router.replace`。** 开放重定向漏洞。必须校验成站内路径。

**第五，把 token 存在 `localStorage` 却没有任何 XSS 防护意识。** `localStorage` 对同源脚本完全透明，一个 `document.cookie` 偷不到的东西它能读到。能做的有三件：敏感操作二次验证、`innerHTML` 一律不用（或先净化）、依赖库定期升级。

**第六，拦截器在模块顶层调用 `useUserStore()`。** 报 `getActivePinia() was called but there was no active Pinia`。把调用挪进拦截器函数体内。

**第七，退出登录先跳转后清状态。** 页面出现「已登录」的残留闪现。

**第八，退出接口失败就不清本地状态。** 用户退不出去。用 `finally`。

**第九，`persist` 开着却忘了 `clearUserInfo` 里也要覆盖持久化。** 正常情况下插件会同步，但如果手写过 `localStorage.setItem`，就会出现「内存清了、硬盘还在」，刷新一下又登录了。

**第十，登录页放进 `Layout`。** 登录页触发依赖登录态的请求，一进来就一片 401。
