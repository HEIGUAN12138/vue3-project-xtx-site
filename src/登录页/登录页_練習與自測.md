# 登录页 · 练习与自测

> 题量：是非 10 / 选择 10 / 配对 8 / 情境 3 / 代码阅读 3 / 延伸思考 2。答案紧跟各区块。

## 一、是非题（10 题）

1. 登录页应该嵌套在 `Layout` 里，这样才能共用顶部导航和页脚。
2. 登录成功后应使用 `router.replace` 而不是 `router.push`。
3. `redirect` 参数可以直接传给 `router.replace`，不需要校验。
4. `el-form` 的 `prop` 与 `rules` 里的字段名不一致时，那一项会报错提示。
5. 密码校验适合设置 `trigger: 'blur'`，而不是 `trigger: 'change'`。
6. `await formRef.value.validate()` 在校验失败时会 reject。
7. `persist: true` 会把 store 的内容写入浏览器本地存储。
8. token 存在 `localStorage` 里对同源脚本不可见。
9. 退出登录应先清状态再跳转。
10. 401 与 403 的处理方式应该一样，都跳登录页。

### 答案解析

1. **错**。`Layout` 会发起依赖登录态的请求（分类、购物车），登录页放进去会满屏 401；且顶部导航会显示「请先登录」，与表单逻辑冲突。
2. **对**。`push` 会让用户按返回键回到登录页。
3. **错**。`redirect` 是用户可控输入，不校验会导致开放重定向（open redirect）。
4. **错**。会静默失效——既不报错也不校验，这是最隐蔽的一类 bug。
5. **对**。`change` 会在输入第一个字符时提示「长度不足」，体验差。
6. **对**。回调式不抛错，Promise 式抛错，所以必须配 `.catch()`。
7. **对**。由 `pinia-plugin-persistedstate` 提供。
8. **错**。`localStorage` 对同源脚本完全透明，任何一段脚本都能读走。
9. **对**。反序会导致「已登录」状态在页面上短暂闪现。
10. **错**。401 是未认证（跳登录），403 是已认证但无权限（提示即可，不应踢出）。

## 二、选择题（10 题）

1. 登录页不放进 `Layout` 的主要原因是？
   A. 样式不同　B. 避免触发依赖登录态的请求与「请先登录」的矛盾　C. 减少代码量　D. 路由不能嵌套

2. 登录成功后跳转首页，正确的方式是？
   A. `router.push('/')`　B. `router.replace('/')`　C. `location.href = '/'`　D. `window.open('/')`

3. 用户直接访问 `/member` 被拦截，登录后应回到？
   A. 永远回首页　B. `/member`　C. 登录页　D. 空白页

4. `rules` 中 `prop` 不匹配时的表现是？
   A. 控制台报错　B. 表单项永远通过且无提示　C. 整个表单无法提交　D. 规则自动匹配

5. 自定义校验器返回 `undefined` 且不调用 callback，结果是？
   A. 通过　B. 失败　C. 规则静默失效　D. 抛出异常

6. `await formRef.value.validate()` 校验失败时应当？
   A. 忽略　B. 用 `.catch()` 接住或包在 `try/catch` 里　C. 改成回调式　D. 重复调用

7. 把 token 放进请求头的正确做法是？
   A. 每个接口函数里手写　B. 请求拦截器统一加　C. 响应拦截器加　D. 路由守卫加

8. 请求拦截器报「没有 Pinia 实例」，最可能的原因是？
   A. 没装 Pinia　B. 在模块顶层调用了 `useUserStore()`　C. token 为空　D. 没写 baseURL

9. 退出登录时接口失败，正确的是？
   A. 不退出　B. 提示失败后留在原页　C. 用 `finally` 保证清状态并跳转　D. 重试三次

10. 判断 `redirect` 是否为站内路径，最可靠的方式是？
    A. 不含 `http` 字符串　B. 以 `/` 开头且不以 `//` 开头　C. 长度小于 100　D. 包含域名

### 答案解析

1. **B**。这是本章第一节的核心论证。
2. **B**。`push` 会留下历史记录，返回键回到登录页；`location.href` 会整页刷新，丢失 SPA 状态。
3. **B**。用 `redirect` 参数传回来，登录后按它跳转（需校验站内）。
4. **B**。校验按 `prop` 字符串匹配，对不上就没人认领这条规则。
5. **C**。既不通过也不失败，规则蒸发。
6. **B**。Promise 式失败会 reject，不接会抛未处理异常。
7. **B**。集中一处不会漏；分散写一定会漏，且改协议时要改多处。
8. **B**。拦截器在模块加载时注册，此时 `app.use(pinia)` 可能还没执行，必须把调用挪进拦截器函数体内。
9. **C**。退出不能依赖网络成功，否则用户被关在站内。
10. **B**。`//evil.com` 会被浏览器当成协议相对 URL；A、C、D 都是不可靠的启发式判断。

## 四、情境分析（3 题）

### 情境 1：密码有红字，账户没有

用户清空账户点登录，页面只提示「密码不能为空」，账户那一栏毫无反应。

**问**：最可能的原因与排查顺序。

**答**：先看 `el-form-item` 的 `prop` 是否与 `rules` 的键名逐字一致（`prop="userAccount"` vs `rules.account`）。这是最常见原因，且不报错。其次看 `:model` 是否绑定到了包含该字段的对象上，以及 `el-input` 是否用 `v-model` 绑定了同一字段。最后才怀疑 `rules` 本身写错。排查顺序就按「绑定关系 → 数据源 → 规则内容」，因为前两者的错误是静默的。

### 情境 2：登录成功，按返回键又回到登录页

用户登录后进入首页，点浏览器返回，又看到登录表单；再点登录，提示「登录成功」，循环。

**问**：原因与修法。

**答**：登录成功后用了 `router.push('/')`，历史记录栈里 `登录页 → 首页` 都在。修法是把成功跳转改为 `router.replace(route.query.redirect || '/')`，把登录页从栈里替换掉。同时检查「请先登录」的跳转是否用了 `push`——那是对的，因为用户可能确实想返回；只有**成功之后**的跳转该用 `replace`。

### 情境 3：刷新页面就掉线

用户登录成功，进会员中心正常；按 F5 刷新，跳回了登录页。

**问**：两个可能原因与各自的验证方法。

**答**：一是 store 没有开启 `persist`，`userInfo` 只存在内存里，刷新即丢——验证方法是看 `localStorage` 里有没有对应的键。二是开了 `persist` 但退出/清空时手写了 `localStorage.removeItem` 之外的操作，导致内存与本地不一致——验证方法是刷新前后各打一次 `userStore.userInfo`。还有一种少见情况：`persist` 的 `key` 与页面其他代码冲突，被覆盖成了空对象。

## 五、代码阅读（3 题）

### 题 1

```js
const doLogin = () => {
  formRef.value.validate(async (valid) => {
    if (valid) {
      await loginAPI({ account, password })
    }
  })
}
```

**问**：这段代码有三处问题，分别是什么？

**答**：一，校验失败时没有任何反馈，用户点了没反应；二，登录成功后既没提示也没跳转，用户不知道发生了什么；三，`validate` 的回调被写成 `async`，回调里的 `await` 抛错不会被外层捕获，异常会变成未处理的 Promise 拒绝。正确写法是用 `await formRef.value.validate().catch(() => false)` 拿到布尔值，再顺序执行提示与 `router.replace`。

### 题 2

```js
httpInstance.interceptors.request.use(config => {
  const userStore = useUserStore()
  config.headers.Authorization = userStore.userInfo.token
  return config
})
```

**问**：这段代码的两个隐患。

**答**：一，没判断 token 是否存在——未登录时会把 `undefined` 写进请求头，后端可能返回 400 而不是预期的「未登录」；二，`Authorization` 的值缺少 `Bearer ` 前缀，后端按 OAuth 2.0 规范解析会失败。正确的写法是 `if (token) config.headers.Authorization = \`Bearer ${token}\``。另外若 `useUserStore()` 写在拦截器函数体外，还会有 Pinia 未初始化的问题。

### 题 3

```js
const logout = async () => {
  await logoutAPI()
  userStore.clearUserInfo()
  router.replace('/login')
}
```

**问**：网络异常时会发生什么？如何修？

**答**：`logoutAPI()` reject 后，后面两行都不执行，用户点退出没有任何反应，token 仍留在本地。修法是把清理与跳转放进 `finally`：

```js
try { await logoutAPI() } finally {
  userStore.clearUserInfo()
  router.replace('/login')
}
```

原则是「本地退出」必须无条件成功，服务端作废是尽力而为。

## 六、延伸思考（2 题）

1. token 放在 `localStorage` 与放在 `HttpOnly` cookie，各自的风险与代价是什么？如果你在做的是一个电商前台，会怎么选？

   **思路**：`localStorage` 的风险是 XSS 一旦发生，token 直接可读；好处是跨域配置简单、`Bearer` 头不受 CSRF 影响。`HttpOnly` cookie 的风险是 CSRF（需要 SameSite + token 双保险），好处是脚本读不到；代价是跨域场景要处理 `withCredentials`、`SameSite=None; Secure` 等配置。电商前台的现实选择多为「短效 token + 刷新机制 + 严格 CSP」，因为要接入的第三方（统计、客服、营销）太多，cookie 域的配置成本反而更高。判断依据不是「哪个更安全」，而是「你更愿意把风险放在哪一侧、以及你有没有能力控制第三方脚本」。

2. 登录态除了「有没有 token」，还常需要「这个 token 代表谁、有什么权限」。把权限信息也塞进 token，与每次请求都问服务端，各有什么问题？

   **思路**：塞进 token 的好处是服务端无状态、校验快，坏处是**吊销困难**——用户被降权或封禁后，旧 token 在过期前依然有效；而且 token 体积会随权限增长。每次问服务端的好处是实时，坏处是每个请求多一次查询（通常靠缓存缓解）。折中做法是 token 只放身份与极少量声明（`sub`、`exp`），权限在服务端按需查询或短期缓存，并对敏感操作做二次校验。
