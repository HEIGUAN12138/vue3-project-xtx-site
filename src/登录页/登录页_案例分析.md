# 登录页 · 案例分析

> 四个案例，分别对应本章四件最容易被当成「随便写写」的事：校验规则、凭证存放、登录后跳转、以及过期处理。

## Case 1：表单校验的三代写法——从 jQuery Validate 到 async-validator

### 背景

2006 年，浏览器对表单的支持还停留在「能输入、能提交」。`<input type="text">` 没有任何内置校验能力，唯一的办法是提交后由服务端返回错误页。那一年，jQuery 团队成员 Jörn Zaefferer 发布了 jQuery Validate 插件，第一次让「在浏览器里声明校验规则」变成了一件正经事。

### 事件经过

jQuery Validate 的核心思路一直延续到今天：给表单元素挂规则，插件负责在合适的时机触发校验、渲染错误文案。

```js
$('#loginForm').validate({
  rules: {
    account: { required: true, message: '用户名不能为空' },
    password: { required: true, minlength: 6, maxlength: 14 },
  },
  messages: { password: { minlength: '密码长度要求 6-14 个字符' } },
})
```

2010 年前后，HTML5 把这件事收进了标准：`required`、`minlength`、`pattern`、`type="email"` 这些属性由浏览器原生支持，配合 `checkValidity()` 与 `setCustomValidity()` 就能完成大部分校验。W3C 的约束校验（constraint validation）规范在 2012 年成为候选推荐标准，Chrome、Firefox、Safari 陆续实现。

第三代的转折发生在 2014 年。蚂蚁金服的 yiminghe 发布了 async-validator——一个**与框架无关**的校验库，把规则写成普通对象，支持异步校验器（比如「这个用户名是否已被注册」必须问服务端）。Element UI 与后来的 Element Plus 都选了它作为 `el-form` 的校验内核，这就是本章第三节那套 `rules` 的来源。

三代写法的对比很清楚：

| 代际 | 代表 | 规则放在哪 | 异步校验 |
|------|------|-----------|---------|
| 2006 | jQuery Validate | JS 配置对象 + DOM | 需要手写 `remote` |
| 2010s | HTML5 原生 | HTML 属性 | 不支持 |
| 2014+ | async-validator | 纯 JS 对象 | 内置支持 |

### 与本章的关系

本章第三节那三条规则（必填、长度、自定义勾选），写法完全遵循 async-validator 的约定：**规则是数据，不是代码分支**。理解了「规则是一份可被读取、可被合并、可被动态生成的配置」，你就能解释两件事：为什么校验能按字段触发（每条规则挂在字段名下），以及为什么自定义校验器必须回调或返回 Promise（它要给异步校验留位置）。

顺带解释了第三个细节：`trigger: 'blur'` 不是 Element 的发明，而是「校验时机」这件事被显式建模的结果。

### 参考资料

- [jQuery Validation Plugin 官方站](https://jqueryvalidation.org/) —— 规则的完整写法与 `remote` 远程校验。
- [MDN：Constraint validation](https://developer.mozilla.org/en-US/docs/Web/HTML/Constraint_validation) —— HTML5 原生校验的属性和 API 清单。
- [async-validator](https://github.com/yiminghe/async-validator) —— Element Plus `el-form` 的校验内核，源码只有几千行，值得读一遍。

## Case 2：token 该放在哪——JWT 普及与两次 Magecart 事件

### 背景

传统 Web 应用的登录态放在服务端 session 里，浏览器只持有一个 `HttpOnly` 的会话 ID cookie。这种模式天然免疫脚本窃取：`HttpOnly` 意味着 `document.cookie` 读不到它。

2015 年 5 月，JWT（JSON Web Token）发布为 RFC 7519。它把用户身份直接编码进一个可被前端读取的字符串里，配合 `Authorization: Bearer` 头使用，前后端分离项目因此不再需要 cookie 与跨域配置。前端把 token 存进 `localStorage`，成了那几年最流行的做法。

### 事件经过

代价在三年后集中显现。

2018 年 6 月到 9 月，Ticketmaster 的支付页面被植入了一段第三方脚本。攻击团伙 Magecart 通过被入侵的第三方客服聊天组件把恶意代码注入页面，脚本在用户填写支付信息时实时读取并回传。受影响客户约 4 万名的支付数据被窃，英国信息专员办公室（ICO）在 2020 年 11 月对 Ticketmaster UK 开出 125 万英镑罚单。

同一时期，英国航空（British Airways）在 2018 年 8 月至 9 月遭遇同类攻击：注入的脚本把用户从支付页重定向到一个外观一致的假页面，约 50 万名客户的姓名、地址、银行卡信息被窃。ICO 于 2020 年 10 月开出 2000 万英镑罚单（最初拟罚 1.83 亿英镑，因疫情与企业申辩而下调）。

这两起事件的技术共同点是：**只要恶意脚本能在你的页面里执行，它就能读到页面上的一切**——包括表单里已经填好的内容，也包括 `localStorage` 里的 token。

### 与本章的关系

本章第五节把 `userInfo`（含 token）用 `persist: true` 写进 `localStorage`，第六节让拦截器每次都把它放进请求头。这套做法本身没错，但它有一个明确的前提：**页面里不能有不受控的脚本**。

由此得到三条工程约束，写在本章第八节的坑里：用户输入不进 `innerHTML`；第三方脚本（统计、客服、A/B 测试）必须评估来源与权限；token 的有效期要短，并配合服务端可作废机制——因为一旦泄露，前端没有任何办法收回它。

反过来看，如果安全要求高，把 token 放回 `HttpOnly` cookie 是更稳的选择，代价是要处理 CSRF（跨站请求伪造）与跨域配置。这是一个真实的权衡，不存在「哪个绝对更好」。

### 参考资料

- [RFC 7519：JSON Web Token](https://datatracker.ietf.org/doc/html/rfc7519) —— JWT 的结构与声明（claim）定义。
- [ICO：Ticketmaster UK 被罚 125 万英镑](https://ico.org.uk/about-the-ico/media-centre/news-and-blogs/2020/11/ticketmaster-uk-ltd-fined-1-25million-for-failing-to-protect-customers-payment-details/) —— 官方通报，含攻击时间线与受影响规模。
- [ICO：British Airways 被罚 2000 万英镑](https://ico.org.uk/about-the-ico/media-centre/news-and-blogs/2020/10/ico-fines-british-airways-20m-for-data-breach/) —— 同类攻击的另一份官方记录。

## Case 3：登录后跳回原页面——redirect 参数与开放重定向

### 背景

「登录完回到你刚才想去的地方」这个需求，比 SPA 老得多。1990 年代的 Web 应用就用一个 `return_url` 查询参数来实现它，早期论坛、银行、邮箱都是这么做的。

问题也老：这个参数是**用户可控的**。攻击者只要构造一条 `https://bank.example/login?return_url=https://bank.example.evil.com` 的链接发给受害者，用户在真站点上输入密码、登录成功，然后被送到假站点——而假站点上写着「会话已过期，请重新登录」。这就是开放重定向（open redirect）。

### 事件经过

2012 年 10 月，OAuth 2.0 发布为 RFC 6749，把这个问题的标准解法写进了协议：客户端注册时必须登记 `redirect_uri` 白名单，授权服务器只往白名单里的地址跳转，且匹配必须是**精确匹配**（早期允许前缀匹配的实现出过不少漏洞）。同一份规范还引入了 `state` 参数，用来防止跨站请求伪造把授权码塞给攻击者。

OWASP 则把「未校验的重定向与转发」单独列为一类风险，并给出明确的防御建议：**不要用黑名单**。因为黑名单永远列不全——`//evil.com`、`/\evil.com`、`https:evil.com`、`%2f%2fevil.com`、以及各种编码变体，每一种都能绕过「只禁止 http:// 开头」这种朴素判断。

### 与本章的关系

本章第二节引入 `/login?redirect=/member`，第七节给出校验函数：

```js
function safeRedirect(path) {
  if (typeof path !== 'string') return '/'
  if (!path.startsWith('/') || path.startsWith('//')) return '/'
  return path
}
```

这行判断对应 OWASP 建议的白名单思路：**只接受以单个 `/` 开头的站内路径**。`//evil.com` 被浏览器解释为协议相对 URL（跳到 `https://evil.com`），所以必须单独排除；`javascript:` 协议、`data:` 协议则天然不满足「以 `/` 开头」，被一并挡掉。

一个更严格的做法是把 `redirect` 换成路由名 + 参数，即 `router.replace({ name: 'member' })`，让「跳到哪」变成一个受控的枚举值，而不是一段自由字符串。代价是多写几行映射代码。

### 参考资料

- [RFC 6749：The OAuth 2.0 Authorization Framework](https://datatracker.ietf.org/doc/html/rfc6749) —— `redirect_uri` 白名单与 `state` 参数的原始定义（第 3.1.2 节、第 10.12 节）。
- [OWASP：Unvalidated Redirects and Forwards](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html) —— 绕过手法清单与防御建议。
- [MDN：URL 与相对路径解析](https://developer.mozilla.org/zh-CN/docs/Web/API/URL/URL) —— 理解 `//host` 为什么会被当成另一台服务器。

## Case 4：401 统一处理——token 有效期与拦截器

### 背景

token 有两种设计：**长效**与**短效 + 刷新**。长效的写起来简单，但泄露后危害窗口极长；短效的更安全，代价是前端必须处理「过期」。

微信公众平台的接口 token 就是短效派的典型：`access_token` 有效期 7200 秒（2 小时），过期后必须用 `refresh_token` 或重新获取，重新获取会让旧 token 失效。这个设计在 2013 年随公众号平台开放就定了下来，至今没改。

前端要面对的正是第 7201 秒的那次请求：它带着一个已经作废的 token 发出，服务端回 401。

### 事件经过

axios 2014 年由 Matt Zabriskie 发布，2016 年前后稳定了拦截器 API（`interceptors.request` / `interceptors.response`）。这一套 API 让「统一加头」和「统一处理 401」第一次变得廉价：

```js
httpInstance.interceptors.request.use(config => {
  const token = useUserStore().userInfo.token
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

httpInstance.interceptors.response.use(
  res => res.data,
  e => {
    if (e.response?.status === 401) {
      useUserStore().clearUserInfo()
      router.replace('/login?redirect=' + encodeURIComponent(router.currentRoute.value.fullPath))
    }
    return Promise.reject(e)
  }
)
```

第 2 章（Pinia）里已经提过小兔鲜的「统一 401 处理」，本章把它和登录页接了起来——401 的终点必须是登录页，而且必须带上回来的地址。

实践中还有两个分支需要单独处理：**401 与 403 语义不同**（401 是「你没证明身份」，403 是「你身份够了但没权限」），前者跳登录、后者应提示「无权限」而不是把人踢出去；以及**刷新 token 接口自身的 401 不能触发再刷新**，否则会陷入无限循环——这是几乎所有实现「自动续期」的项目都会踩一次的坑。

### 与本章的关系

本章第六节的拦截器代码，就是这个模式的最小实现。三个关键点在案例里被放大：拦截器延迟调用 `useUserStore()`（避开 Pinia 未初始化）、`router` 从模块直接 import（非组件环境取不到 `useRouter()`）、以及 401 跳转时把当前完整路径写进 `redirect`——最后这一条又回到 Case 3 的安全校验上，闭环。
