## 一、概念快速检测（是非题 10 题）

1. 在 `<script setup>` 中，`this` 指向当前组件实例，可以用 `this.$router` 跳转。
2. `ref` 传入一个对象时，内部会用 `reactive` 处理，因此 `.value.xxx` 的修改是响应式的。
3. `reactive` 可以直接代理数字和字符串，所以 `reactive(0)` 是合法写法。
4. `computed` 在依赖没有变化时直接返回缓存值，不会重新执行计算函数。
5. `watch` 默认会深度监听对象，对象内部字段变化也会触发回调。
6. 在 Vue 3 中，同一个元素上同时写 `v-if` 和 `v-for`，`v-for` 先执行。
7. 子组件可以直接修改 `props` 里的值，Vue 会在下一次渲染时同步回父组件。
8. 在 `onMounted` 回调中，可以通过模板 ref 拿到真实的 DOM 元素。
9. `await nextTick()` 之后，之前对响应式数据的修改已经反映到 DOM 上。
10. 组件卸载时 Vue 会自动清理组件内创建的 `setInterval`，不需要手动 `clearInterval`。

### 答案与解析

1. **否**。`<script setup>` 内没有组件实例上下文，`this` 是 `undefined`。需要路由实例时用 `useRouter()`，需要组件实例时用 `getCurrentInstance()`（但不推荐日常使用）。
2. **是**。`ref` 对对象类型会转交给 `reactive` 处理，所以嵌套字段的修改同样会被 `Proxy` 拦截。
3. **否**。`reactive` 只能接收对象或数组，传入原始值会返回原值并给出警告，因为它无法对原始值建立代理。
4. **是**。`computed` 内部维护 dirty 标记，依赖未变时直接返回上一次的结果，这正是它与「模板里调用方法」的关键差别。
5. **否**。`watch` 默认是浅监听，只关心被监听值的引用是否变化。要监听对象内部字段必须显式加 `deep: true`。
6. **否**。Vue 3 中 `v-if` 的优先级高于 `v-for`，条件表达式执行时循环变量还不存在，因此会报「属性未定义」。
7. **否**。`props` 是只读的，直接修改会在开发环境报警告。子组件应通过 `emit` 通知父组件，由父组件修改数据。
8. **是**。`setup` 阶段 DOM 尚未挂载，`onMounted` 是第一个能安全访问真实 DOM 的时机。
9. **是**。Vue 的更新是异步批处理的，`nextTick` 的回调在 DOM 更新完成后执行，此时读取到的是最新布局。
10. **否**。框架只负责自己创建的副作用（如渲染、侦听器），`setInterval`、`addEventListener`、第三方实例都必须自己在 `onUnmounted` 里清理。

## 二、选择题（10 题，每题 4 选项）

1. **下面的代码执行后，页面上的 `count` 会怎样变化？**
   ```js
   const count = ref(0)
   count++
   ```
   - A. 变成 1，页面更新
   - B. 变成 1，页面不更新
   - C. 仍然是 0，页面不更新
   - D. 报错，`ref` 不支持 `++`

   **答案：C**。`count` 是包装对象，`count++` 实际是对对象本身做自增，会得到 `NaN` 或被忽略，`.value` 始终是 0。正确写法是 `count.value++`。B 错在「变成 1」；D 错在 `ref` 对象本身可以被赋值，只是语义不对。

2. **`const state = reactive({ list: [] })` 之后，`const { list } = state`，再执行 `list.push(1)`，视图为什么没有更新？**
   - A. `reactive` 不支持数组
   - B. 解构拿到的是当时的值，丢失了对代理的引用
   - C. `push` 不会触发响应式
   - D. 必须用 `ref` 才能操作数组

   **答案：B**。解构得到的是普通数组引用，虽然 `push` 改的是同一个数组，但视图的依赖登记在 `state.list` 这个代理属性上，绕过了 `get` 拦截就不会被追踪。A 错，`reactive` 支持数组；C 错，`push` 在代理对象上会触发；D 错，`reactive` 可以管理数组。

3. **一个「筛选后的列表」应该用 `computed` 还是方法？**
   - A. 方法，因为逻辑更灵活
   - B. `computed`，因为依赖不变时可以复用缓存
   - C. 方法，因为 `computed` 不能返回数组
   - D. 两者等价，看个人习惯

   **答案：B**。模板中每次渲染都会调用方法，而 `computed` 只在依赖变化时重算。A、D 忽略了性能差异；C 错，`computed` 可以返回任意类型。

4. **一个侧边栏需要频繁展开/收起，内部有一个较重的图表组件，应该用哪个指令？**
   - A. `v-if`，不用时销毁更省内存
   - B. `v-show`，避免反复创建销毁
   - C. 两个都用
   - D. 用 `v-for` 控制

   **答案：B**。频繁切换的场景下，`v-if` 的创建销毁成本高于 `display` 切换。A 适用于「很少打开、内容很重」的场景；C、D 语法上不成立或无意义。

5. **列表用数组索引作为 `key`，删除中间一项后最可能出现什么现象？**
   - A. 页面白屏
   - B. 被删除行之后的 DOM 状态（如输入框内容）错位
   - C. 数据源被修改
   - D. 不会出现任何问题

   **答案：B**。索引在删除后整体前移，diff 认为「同一位置还是同一个节点」，于是复用了错误的 DOM 状态。A 不会发生；C 是数据操作问题，与 key 无关；D 错。

6. **`defineProps` 和 `defineEmits` 是否需要从 vue 导入？**
   - A. 需要，`import { defineProps } from 'vue'`
   - B. 不需要，它们是编译宏
   - C. 只有 TypeScript 项目需要
   - D. 需要从 `vue/macros` 导入

   **答案：B**。它们是编译期宏，由 `<script setup>` 的编译器处理，不需要导入；手动导入反而会报错。A、D 是错误路径；C 与语言无关。

7. **子组件需要修改父组件传入的 `count`，正确做法是？**
   - A. 直接 `props.count++`
   - B. 声明 `emit('update:count', value)`，由父组件修改
   - C. 把 `props` 复制到本地 `reactive` 后随意改
   - D. 用 `provide/inject` 传一个可写引用

   **答案：B**。这是单向数据流的标准做法，也支持 `v-model` 语法。A 会触发只读警告；C 会让本地状态与父组件脱节，后续不同步；D 会让数据来源不可追踪。

8. **要让 `watch` 监听对象的内部字段变化，需要加什么选项？**
   - A. `immediate: true`
   - B. `deep: true`
   - C. `flush: 'post'`
   - D. 不需要选项，默认就是深监听

   **答案：B**。默认浅监听只比较引用。A 让回调立即执行一次，与深度无关；C 改变回调执行时机；D 与默认行为相反。

9. **在 `onUpdated` 里修改响应式数据，最可能发生什么？**
   - A. 没有任何影响
   - B. 触发下一轮更新，可能形成无限循环
   - C. 只执行一次
   - D. 报错并阻止更新

   **答案：B**。`onUpdated` 在任何更新后触发，在里面改数据会再次触发更新。A、C 与机制不符；D 框架不会阻止，只会让页面卡死。

10. **路由从 `/detail/1` 跳到 `/detail/2`，组件内数据没有刷新，正确修复方式是？**
    - A. 在 `setup` 里重新调用一次请求
    - B. `watch(() => route.params.id, load, { immediate: true })`
    - C. 用 `onUpdated` 里重新请求
    - D. 给组件加 `key` 之外无法修复

    **答案：B**。同组件复用，`setup` 只执行一次，必须监听参数变化。A 不会因参数变化再次执行；C 容易造成重复请求甚至循环；D 说法错误，用 `key` 强制重建组件是另一种可行方案，但并非「无法修复」。

## 三、名词配对（8 组）

| 左列 | 右列 |
|------|------|
| 1. `ref` | A. 由其他状态派生、带缓存的值 |
| 2. `reactive` | B. 状态变化后执行副作用的监听器 |
| 3. `computed` | C. 能包装任意类型的响应式容器，用 `.value` 读写 |
| 4. `watch` | D. 等 DOM 更新完成后执行的回调调度方式 |
| 5. `onMounted` | E. 子组件向父组件通知事件的机制 |
| 6. `nextTick` | F. 返回对象代理、解构会丢失响应性的 API |
| 7. `emit` | G. 父组件向子组件指定位置插入内容的机制 |
| 8. `slot` | H. 组件挂载完成后执行的生命周期钩子 |

### 答案

1-C　2-F　3-A　4-B　5-H　6-D　7-E　8-G

## 四、情境分析（3 题）

### 题目 1：筛选条件变了，列表没变

商品列表页有「品牌」「价格区间」「排序」三个筛选条件，都由 URL 查询参数驱动。用户点了「价格从低到高」之后，地址栏的 `sort=price_asc` 变了，但列表顺序没变。

请回答：
1. 最可能的原因是什么？（提示：组件是否被复用、请求是否被触发）
2. 你会用哪两步验证？
3. 修复方式是什么？

**参考答案**

1. 原因：路由参数变化时组件被复用，`setup` 只执行一次，`load()` 没有被重新调用。也可能是请求函数里读的是初始化时缓存的参数快照。
2. 验证：第一步在 `load()` 里打日志，观察点排序后是否再次执行；第二步在浏览器 Network 面板看是否发出了新请求。若函数没执行 → 监听问题；若请求发出但参数没变 → 参数读取问题。
3. 修复：`watch(() => route.query, load, { immediate: true, deep: true })`；请求函数内部从 `route.query` 实时读取，而不是用解构出来的旧值。

### 题目 2：选了颜色，价格不变

商品详情页的 SKU 组件接收父组件传入的 `goods` 对象，内部写了 `const { skus } = props.goods`，然后根据用户选择计算价格。现在点击颜色，选中样式变了，但价格区域一直显示初始值。

请回答：
1. 问题出在哪一行？
2. 为什么选中样式会变、价格却不变？
3. 最小改法是什么？

**参考答案**

1. 出在 `const { skus } = props.goods` 这行解构。
2. 选中样式依赖的是组件内部的选中状态（普通 `ref`），所以会变；价格依赖 `skus`，而 `skus` 是解构出来的快照，父组件后续更新 `goods` 时它不会同步，因此价格一直停在初始值。
3. 不要解构，改为 `const skus = computed(() => props.goods.skus)`，或用 `toRef(props.goods, 'skus')`；价格用 `computed` 基于当前选中项重新计算。

### 题目 3：页面切走后请求还在发

支付结果页每 2 秒轮询一次订单状态。用户支付成功后返回首页，但控制台显示请求仍在每 2 秒发出，页面越用越卡。

请回答：
1. 这段代码缺了什么？
2. 如果不修，除了性能还有什么风险？
3. 完整修复需要哪几处改动？

**参考答案**

1. 缺 `onUnmounted` 清理，`setInterval` 没有 `clearInterval`。
2. 风险：组件已卸载仍在更新状态，可能报「操作已销毁组件」的警告；轮询持续消耗服务端配额；若轮询回调里还弹提示，会在别的页面误弹。
3. 三处：把 `timer` 声明在 `setup` 顶层作用域（不要放在 `onMounted` 内部）；在 `onUnmounted` 里 `clearInterval(timer)`；轮询回调里加「已成功/已失败」的终止条件，避免无限轮询。

## 五、代码阅读（3 题）

### 题目 1

```js
import { reactive } from 'vue'
const state = reactive({ count: 0 })
const add = () => { state.count++ }
const reset = () => { state = reactive({ count: 0 }) }
```

问：`reset()` 执行后，`state.count` 是多少？页面会更新吗？为什么？

**参考答案**

`state` 是 `const`，重新赋值会直接抛 `TypeError: Assignment to constant variable`。即使改成 `let`，重新赋值也会把变量指向一个新代理，模板里绑定的仍是旧代理的引用，视图不会更新。正确做法是 `state.count = 0`，或整体状态用 `ref` 再 `state.value = { count: 0 }`。

### 题目 2

```js
const list = ref([1, 2, 3])
const total = computed(() => list.length)
list.value.push(4)
console.log(total.value)
```

问：输出是什么？如果把 `list` 换成 `reactive([1,2,3])` 并 `list.push(4)`，结果是否一致？

**参考答案**

两处都输出 `4`。`ref` 的数组通过代理的 `get`/`set` 与数组方法拦截，`push` 会触发依赖；`reactive` 数组同样可被拦截。差异不在这里，而在于 `ref` 需要 `.value`，且整体替换更方便（`list.value = newList`）。

### 题目 3

```js
const count = ref(0)
watch(count, () => { count.value++ })
count.value++
```

问：控制台会打印多少次？实际会发生什么？

**参考答案**

回调里没有 `console.log` 时什么也不打印；但 `watch` 回调修改了被监听的值，会再次触发自身，形成无限递归，Vue 会抛出「Maximum recursive updates exceeded」或页面卡死。这是「在 `watch` 里修改自己的依赖」的典型错误，正确做法是判断条件后再改，或改用 `computed`。

## 六、延伸思考（2 题）

### 思考题 1：什么时候不该用 `computed`

有人认为「凡是算出来的值都应该用 `computed`」。请举出两个反例，并说明判断标准。

**参考思路**

反例一：结果依赖时间（`Date.now()`）或随机数，`computed` 不会因为时间流逝而重算，会导致显示停滞；反例二：计算本身有副作用（发请求、写缓存），`computed` 可能在你不期望的时机被求值，且不应有副作用。判断标准：纯函数、依赖明确、结果可缓存 → 用 `computed`；依赖外部世界或需要主动触发 → 用 `watch` 或方法。

### 思考题 2：组合式 API 是否让代码更难读

选项式的批评者认为：组合式把逻辑塞进一个大 `setup`，新人打开文件不知道从哪读起。请分别站在两边立场各写一段论证，再给出你的结论。

**参考思路**

支持「更难读」：缺少约定的分区，`setup` 容易变成 300 行的流水账；逻辑顺序即执行顺序，阅读者需要自己建立心智模型。支持「更好读」：按功能聚合后，一个功能的全部代码连续可读，改需求只动一处；复用不需要 mixin。结论通常落在「取决于是否遵守约定」：把每个功能抽成 `useXxx` 组合式函数、`setup` 只做编排，可读性反而优于选项式。评分看是否给出可执行的约定，而不是单纯选边。
