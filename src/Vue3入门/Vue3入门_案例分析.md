# Vue3入门：实战案例分析

> 这一章的四个案例都在回答同一个问题：当「写法」发生变化时，真实的项目会付出什么代价、又换回了什么。

---

### Case 1：Vue 3 的「One Piece」发布——一次不向后兼容的重写

**背景**

Vue 2 在 2016 年发布后成为增长最快的前端框架之一，但它的响应式基于 `Object.defineProperty`：只能拦截已知属性的读写，无法监听新增/删除属性，也无法拦截数组索引赋值。要修复这些限制，只能在框架内核上重写。Vue 团队在 2018 年启动了 Vue 3 的开发，目标是换掉响应式内核、改善 TypeScript 支持、并把代码组织方式升级为组合式 API。

**事件经过**

2020 年 9 月 18 日，Vue 3.0 以代号「One Piece」正式发布。官方公布的关键指标是：运行时体积比 Vue 2 小约 20%，配合 Tree-shaking 后按需引入可以更小；渲染性能在新基准测试中有明显提升；同时提供了一条「渐进迁移」路径——通过 `@vue/compat` 兼容构建，让 Vue 2 语法在 Vue 3 运行时上先跑起来，逐个组件迁移。

代价也很明确：Vue 3 不是向后兼容的升级。过滤器（filters）被移除、`$on/$off/$once` 事件总线被移除、`v-model` 在组件上的语义改变、`functional` 组件写法重写。大量生态库需要重写或升级，许多团队因此推迟了两年以上。Vue 2 的官方支持最终在 2023 年 12 月 31 日结束。

**与本章的关系**

这个案例是第一节「为什么换写法」的产业级证据：组合式 API 不是审美选择，而是响应式内核换成 `Proxy` 之后的必然产物——`Proxy` 能拦截任意属性，才让「把逻辑写进普通函数、按需组合」变得可行。同时它也是第三节的注脚：`reactive` 的限制（不能代理原始值、解构丢响应性）正是 `Proxy` 方案的边界。

**参考资料**

- [Vue 3.0 "One Piece" 发布公告](https://blog.vuejs.org/posts/vue-3-one-piece)
- [Vue 3 迁移指南](https://v3-migration.vuejs.org/)
- [Vue 2 终止支持公告](https://v2.vuejs.org/eol/)

### Case 2：GitLab 用 Vue 重写 Issue Board——渐进式替换 jQuery 的样本

**背景**

2016 年的 GitLab 前端以 jQuery 和 Rails 服务端渲染为主。Issue Board（看板）需要拖拽卡片、即时更新列表状态，用 jQuery 手写 DOM 操作意味着每一处状态变化都要手动找到对应节点、手动增删 class、手动同步计数。功能越多，这类「手工同步」的代码越难维护。

**事件经过**

GitLab 在 2016 年公开说明了选择 Vue 的理由：模板语法接近 HTML，后端开发者容易上手；可以渐进式接入，不必一次性重写整个页面；相比 React，当时的 Vue 对「在服务端渲染页面里嵌入小组件」更友好。他们先在 Issue Board 这一个页面上用 Vue 重写，把拖拽、列计数、卡片状态更新交给响应式系统，验证可行后再逐步扩展到其他页面。

这个决策的关键不在于「Vue 比 jQuery 好」，而在于迁移方式：他们保留了 Rails 渲染的外壳，只把需要高频交互的区域换成 Vue 组件。这让迁移风险被限制在单个页面内，也让团队可以按页面节奏推进。

**与本章的关系**

对应第二节与第七节：GitLab 的做法正是「`setup` 只负责准备数据，DOM 相关操作交给框架」的规模化版本。当状态变化不再需要手写 `document.querySelector`，第七节讲的「在 `onMounted` 里做 DOM 操作」就变成了少数场景（图表、地图），而不是日常。

**参考资料**

- [GitLab：Why we chose Vue.js](https://about.gitlab.com/blog/2016/11/30/vuejs/)
- [GitLab 前端开发文档](https://docs.gitlab.com/ee/development/fe_guide/)

### Case 3：create-vue 取代 vue-cli——脚手架换代背后的构建链更替

**背景**

vue-cli 基于 webpack，是 Vue 2 时代的标准脚手架。它的配置能力强，但代价是启动慢、配置项多，一个中等项目冷启动常常要十几秒。Vite 利用浏览器原生 ESM，开发时不需要打包，启动时间从「秒级」降到「毫秒级」。2022 年起，Vue 官方把 `create-vue` 定为推荐脚手架，`npm init vue@latest` 取代 `vue init`。

**事件经过**

create-vue 的默认选项也随之变化：TypeScript 从「可选插件」变成一等公民，状态管理默认推荐 Pinia（不再推荐 Vuex），构建工具固定为 Vite。对学习者的直接影响是：网上大量 vue-cli 时代的教程（`vue.config.js`、`vue init webpack`）在新项目里直接失效，配置文件从 `vue.config.js` 变成 `vite.config.js`，环境变量前缀从 `VUE_APP_` 变成 `VITE_`。

这不是「新版更好用」的问题，而是工具链换代后文档断层的典型场景：一个 2021 年的教程，在 2023 年的脚手架上会有三处以上对不上。

**与本章的关系**

对应第七节末尾提到的工程化背景：`<script setup>` 之所以能成为默认写法，前提是构建工具支持编译期宏（`defineProps`、`defineEmits` 不需要 import）。如果项目还在用老脚手架，本章的写法可能无法直接编译，这也是下一章「项目起步」要先解决环境问题的原因。

**参考资料**

- [create-vue 官方仓库](https://github.com/vuejs/create-vue)
- [Vue 官方快速上手（create-vue 为默认方式）](https://cn.vuejs.org/guide/quick-start.html)
- [Vite 官方文档](https://cn.vitejs.dev/guide/)

### Case 4：小兔鲜的组件拆分——把「一个详情页」拆成可维护的单元

**背景**

本笔记对应的电商项目里，商品详情页同时承担：图片轮播与预览、SKU 规格选择、库存与价格联动、数量增减、加购与立即购买。如果全部写在一个 `.vue` 文件里，这个文件会超过 800 行，且「选规格」和「加购」的代码交错在一起，改一个功能要滚动很久。

**事件经过**

项目采用的做法是按「职责边界」拆成三层：页面组件负责请求与整体布局；`XtxSku` 这类交互组件只负责规格选择与可用性计算，通过 `props` 接收规格树、通过 `emit` 抛出选中的 SKU；纯展示组件（图片、价格、按钮）不持有业务状态。这样拆的好处是：SKU 的「哪个组合可售」逻辑被隔离在一个组件里，可以用固定的规格树单独测试，不必启动整个页面。

代价是组件间要传的数据变多，容易出现「props 层层透传」。项目在跨页面共享购物车数据时，把状态收敛到 Pinia store，而不是继续用 props 往下传。

**与本章的关系**

这是第六节「props 只读、emit 通知」的直接应用：SKU 组件不修改父组件传入的规格数据，只把「用户选了哪个组合」作为事件抛出去。也是第八节第一个坑的反面教材——如果把规格数据解构后放进本地变量，选中状态就会和父组件脱节，表现为「点了颜色，价格不变」。

**参考资料**

- [Vue 官方文档：组件 Props](https://cn.vuejs.org/guide/components/props.html)
- [Vue 官方文档：组件事件](https://cn.vuejs.org/guide/components/events.html)
