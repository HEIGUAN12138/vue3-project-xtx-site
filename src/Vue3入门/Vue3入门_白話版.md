# Vue3入门（白话版）

## 一、从选项式到组合式：为什么要换写法

想象你在整理一个出租屋。选项式的收纳方式是：所有衣服放一个柜子、所有书放一个书架、所有充电线放一个抽屉。找东西时，你先想「这是衣服还是书」，再去对应柜子翻。Vue 2 就是这样：数据放 `data`，方法放 `methods`，算出来的值放 `computed`。小房间还好，东西一多，改一个功能要在三个柜子之间来回跑。

组合式的收纳方式是：按「用途」分箱子。出差箱里放西装、充电器、洗漱包，一拎就走。Vue 3 里，一个功能的变量、计算、监听、生命周期写在一起，将来这个功能要在别的页面复用，整箱搬走就行。

所以组合式 API 不是「新语法更潮」，而是「搬家更方便」。代价是：以前柜子上贴了标签告诉你什么时候该用哪个，现在箱子是你自己打的，顺序也需要你自己负责。写得乱，会比选项式更难读。

## 二、setup 与执行时机：组件第一次运行的地方

你去餐厅吃饭，落座那一刻，桌上还没有菜，服务员先问你「几位、忌口」。这个环节就是 `setup`：组件刚被创建，页面还是空的，但你已经可以准备数据了。

它有两个特点。第一，这个时候你不能碰「桌上已有的东西」，比如页面上的元素、路由实例，这些都还不存在。第二，你返回的东西，才会被端上桌给客人看，也就是模板能用到。Vue 3 的 `<script setup>` 就是一个自动帮你上菜的服务员：你只要写好变量和函数，它会自动全部摆上桌，不用一个个报菜名。

最有用的提醒是：需要量桌子尺寸、装灯泡这样的事，一定要等客人坐好（`onMounted`）再做。刚进店就量桌子，量到的是一张还不存在的桌子，结果只能是空。

## 三、ref 与 reactive：两种响应式容器的分工

先看家里的电表。你用电，表就转；你不用，表不动。中间没有任何人去通知表。响应式就是这个意思：数据被人用了，Vue 就记下来；数据一变，Vue 就去通知那些用过它的地方重新显示。它不是轮询检查，而是「登记 + 通知」。

`reactive` 像一个开放式的储物柜：你把一组东西放进去（列表、加载状态、页码），改动其中任何一格，用过的界面都会更新。但它有两个硬伤：第一，只能装「柜子」，不能单独装一个数字；第二，如果你把里面某一格「拿出一份复印件」放到别处（解构），复印件永远不会变。

`ref` 就是一个带封条的盒子：不管装数字、文字还是一整个柜子，都能装，取东西必须撕开封条（`.value`）。在页面模板里，Vue 会帮你撕；在脚本里，必须自己撕。所以新手最常见的错误就是脚本里忘了 `.value`，改了半天页面不动。

怎么选？会整体换掉的（比如列表整个换成新数据）用 `ref`。只是一堆字段各自修改的用 `reactive`。拿不准就先用 `ref`，它不容易出错。

## 四、模板语法与指令：从数据到 DOM 的映射

家里的智能灯有两种控制方式。一种是开关：按一下开，再按一下关。另一种是调光旋钮：一直在那儿，只是亮度变了。`v-if` 和 `v-show` 就是这两种：`v-if` 是拆灯泡装上灯泡，条件不成立时那个东西根本不存在；`v-show` 是灯泡一直装着，只是把电断了。

所以：经常开关的用 `v-show`（换灯太麻烦），不常变的、或者内容很重的用 `v-if`（不用时干脆不装，省地方）。

列表渲染的 `key`，像超市寄存柜的号码牌。你给每件东西一个固定号码，取出再放回，柜子知道还是同一件。如果你图省事按「第几个格子」编号，中间有人取走一格，后面所有号码就错位了，东西会跑到别人的格子里——这就是「删掉一行，输入框里的字跟着跑」的原因。

`v-model` 是「遥控器 + 接收器」打包。你按遥控器（输入），电视（数据）变化；反过来数据变了，遥控器显示也跟着变。它本质上是「一个值 + 一个更新事件」的组合，不是什么魔法。

## 五、computed 与 watch：派生状态和副作用的分界

你家的体重秤和记事本，正好对应这两个东西。

`computed` 是体重秤：你站上去，它算出数字。你没变，它不会重新算一遍给你看。它只负责「根据已知的东西算出结果」，算完就存着，直到你体重变了才重算。购物车里「选中商品的总价」就应该是秤：勾选变了就算，没变就不动。

`watch` 是记事本旁边的提醒贴：一旦某件事发生，就去做另一件事。比如「体重超过 80 公斤，就提醒自己少吃夜宵」。它不产出值，它执行动作：发请求、存本地、弹提示。

一个常见的错误是「用记事本去记体重」：明明一个 `computed` 就能算出的总价，却用 `watch` 监听每一项再手动累加。这样不但代码长，还容易漏掉某一种变化。

`watchEffect` 是「自动感应」版本：你在它里面用了什么，它就盯着什么，不用你一个个列名单。方便，但出了问题时你不知道到底是谁触发的，所以复杂逻辑还是老老实实列依赖。

## 六、组件通信：props、emit 与插槽

想象一家餐厅。厨房（子组件）做菜，服务员（父组件）负责点单和上菜。

`props` 是服务员递给厨房的点菜单：只能看，不能改。厨房如果偷偷把「不要辣」改成「微辣」，服务员手里的单子和实际做出来的菜就对不上了，出了问题谁也说不清。所以子组件想改数据，不能直接动手，要喊一声。

`emit` 就是厨房喊的那一嗓子：「三号桌的菜好了」。它不直接改父组件的数据，只是通知，改不改、怎么改由父组件决定。这就是「单向数据流」：数据往下走，事件往上走，中间不抄近路。

插槽像餐盘的凹槽。盘子（子组件）决定凹槽在哪、多大，但里面放什么菜（内容）由点菜的人（父组件）决定。作用域插槽更进一步：厨房把「这块肉几分熟」的信息递出来，你可以在凹槽里按这个信息决定摆盘方式。

至于爷爷和孙子要传话，或者两个兄弟页面要共享数据，别用「隔代喊话」的偏方，直接把东西放进公共储物间——那就是下一章的 Pinia。

## 七、生命周期与渲染时机：什么时候该做副作用

装修一套房子有固定顺序：先量房，再水电，再刷墙，最后进家具。你不能在墙还没刷的时候把沙发搬进去。

`onMounted` 就是「墙刷完了、可以进家具」的时刻。所有需要真实场地的事——装吊灯（图表）、量窗帘（元素尺寸）、拉网线（事件监听）——都必须等到这一刻。在这之前动手，等于对着一间还不存在的房子量尺寸。

`onUnmounted` 是「退租」时刻。你要把装的东西拆走：定时器停掉、事件解绑、第三方实例销毁。不拆的后果是，房子已经换租客了，你的电费还在跑——页面切走了，请求还在发，久了就是卡顿和内存上涨。

`nextTick` 是「等搬家师傅把家具摆好再看」。你刚下单买了个柜子（改了数据），立刻去看客厅是看不到的，因为 Vue 是攒一批一起摆。等一个 `nextTick`，柜子就位了，这时候再调位置才有效。

`onUpdated` 要小心用。它相当于「屋里任何东西动一下，你都要起来看一眼」，很容易变成「看一眼就挪一下，挪一下又触发看一眼」的死循环。真想盯某一件东西，用 `watch`。

## 八、工程实践与常见坑

第一个坑：**数据改了，页面不动。** 这就像你把文件从柜子里拿出来复印了一份，然后一直在复印件上改字，原件当然不变。原因通常是解构了 `reactive`，或者在脚本里忘了写 `.value`。解法是别解构，或者用 `toRefs`；整体替换就用 `ref`。

第二个坑：**删掉列表中间一项，下面的输入框内容错位。** 这是号码牌按「第几格」编的后果。把 `key` 换成后端给的唯一 id 就好。

第三个坑：**`v-if` 和 `v-for` 写在一起报错。** Vue 3 会先判断条件、再循环，判断的时候循环变量还不存在，相当于先点名再叫人进场。把条件挪到外层模板，或者先用 `computed` 把列表过滤好。

第四个坑：**在 `setup` 里操作页面元素，报 null。** 还是「房子没盖好就量尺寸」。把代码挪到 `onMounted`；如果元素本身在 `v-if` 里，还要等条件成立后再等一个 `nextTick`。

第五个坑：**路由参数变了，页面不刷新。** 同一个组件被复用了，`setup` 只跑一次，相当于换了房客但没重新装修。用 `watch` 盯住路由参数，并且加 `immediate: true` 让第一次也执行。

第六个坑：**页面切走后定时器还在跑。** 只记得装、不记得拆。所有 `setInterval`、`addEventListener` 都要在 `onUnmounted` 里清理。

---

## 一句话总结

**Vue3 的核心只有一句话：数据被谁用了，Vue 就替谁盯着，一变就重画；你负责决定「什么算状态、什么该缓存、什么时候清理」，剩下的交给它。**
