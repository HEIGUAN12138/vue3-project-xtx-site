# 一级分类页 · 案例分析

> 四个真实背景：为什么参数变化不重建组件、面包屑为什么要写成 `nav`、广告位为什么要带位置参数，以及乱序响应这个老问题。

## Case 1：参数变化为什么不重建组件

### 背景

单页应用的核心是「不刷新页面就换内容」。如果每次参数变化都销毁并重建整棵组件树，那么输入框里的内容、滚动位置、已经加载的图片全部丢失，体验和传统多页跳转没区别。

Vue Router 从 2.x（2016 年）起就确定了一个策略：**路由记录相同、只有参数不同时，复用组件实例**。判定依据是「匹配到的路由记录」，不是「最终 URL」。

### 事件经过

这个策略带来了一个长期存在的困惑。官方文档不得不专门写一节《响应路由参数的变化》，告诉开发者「要用 `watch` 监听 `$route.params`」。这句话从 Vue Router 2 一直保留到 4，说明踩坑的人足够多。

Vue Router 4（2020 年发布，配合 Vue 3）在组合式 API 的语境下补了一个钩子 `onBeforeRouteUpdate`，语义更精确：它只在「同一路由记录内参数变化」时触发。但官方并没有因此取消 `watch` 的写法，因为 `watch` 在组合式函数里更好组合——本章第七节把它包进 `useCategory`，就是利用这一点。

同期 React 生态也在处理同一件事：`useEffect` 的依赖数组漏写参数，就会得到完全一样的表现——地址变了、数据没变。这说明「复用 + 依赖声明」是这一类框架的共同代价，不是 Vue 独有的缺陷。

### 与本章的关系

本章第六节把三种修法排了序，判断依据就来自这段历史：`watch` 是官方长期推荐的写法，`onBeforeRouteUpdate` 语义更准但不管首次进入，`key` 重建范围太大。理解「复用的判定依据是路由记录」这一点，才能解释为什么 `?page=2` 的变化同样会复用组件。

## Case 2：面包屑为什么必须写成 `nav`

### 背景

面包屑在视觉上只是「首页 / 手机数码」一行小字。但对使用屏幕阅读器的人来说，这一行需要被识别成「导航区域」，并且要能听懂「你现在在第几层」。如果只写成 `<div><a>首页</a> / 手机数码</div>`，读屏软件会把它当成普通文本念过去，用户不知道这是一个可跳转的层级结构。

### 事件经过

2014 年 HTML5 成为 W3C 推荐标准，`<nav>` 元素被定义为「页面内的导航链接区域」。2019 年前后，W3C 的 ARIA Authoring Practices Guide（APG）收录了 Breadcrumb 模式，给出了标准写法：外层用 `<nav aria-label="Breadcrumb">`，内部用有序列表 `<ol>`，当前页用 `aria-current="page"` 标记且**不做成链接**。

这个规范与视觉设计恰好一致：最后一层本来就不该能点。所以「最后一层用 `span`」不只是交互上的讲究，也是无障碍上的要求——一个指向当前页的链接，对读屏用户是纯粹的噪音。

### 与本章的关系

本章第三节的 `XtxBread` 用 `nav` 作为根元素，`XtxBreadItem` 在没有 `to` 时渲染 `span`，正好对应 APG 的两条要求。第三节说的「判断放在组件里而不是调用处」，也是为了让每个使用面包屑的页面都自动满足规范，而不是靠每个人记得。

### 参考资料

- [W3C ARIA APG：Breadcrumb Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/)
- [MDN：nav 元素](https://developer.mozilla.org/zh-CN/docs/Web/HTML/Element/nav)
- [MDN：aria-current](https://developer.mozilla.org/zh-CN/docs/Web/Accessibility/ARIA/Attributes/aria-current)

## Case 3：同一个素材，为什么要带「位置」参数

### 背景

运营在后台配一张活动图时，通常不会只上传图片，还要指定「投在哪里」：首页首屏、分类页顶部、详情页侧栏。同一个活动可能同时投多个位置，但素材尺寸和文案都不同。

早期做法是给每个位置各建一个接口，比如 `/home/banner`、`/category/banner`。位置一多，接口数量线性增长，前端每加一个位置就要改一次请求层。

### 事件经过

广告行业很早就用「广告单元（ad unit）」或「展示位置（placement）」来解决这件事：一个接口、一个位置参数，后端按位置返回对应素材与尺寸。Google Ad Manager 的广告单元就是这么设计的，一个页面可以定义多个 unit，各自独立统计曝光与点击。

小兔鲜的 `distributionSite` 是同一思路的简化版：首页传 `1`、分类页传 `2`。好处有三个：前端只维护一个请求函数；后端可以在不改前端的情况下调整某位置的素材；曝光统计天然按位置分组。

### 与本章的关系

本章第四节把首页的 Banner 改成接受 `site` 参数的组件，正是把「位置」当成一等公民。同时那一节也提醒了边界：如果两个位置的**交互行为**也开始分化（一个自动播、一个不播），就不要再往同一个组件里加参数，而应该拆开——参数适合表达「数据差异」，不适合表达「行为差异」。

## Case 4：乱序响应——一个三十年的老问题

### 背景

只要「用户可以连续触发请求」，就存在乱序返回的可能：先发的请求因为网络或后端耗时更长，后回来，把新结果覆盖掉。表现是「搜索结果和输入框对不上」「切了分类显示的还是上一个分类的商品」。

### 事件经过

2000 年代初 Ajax 普及后，这个问题就成了前端面试的常客。当时的解法是给每次请求编号，或者用 `XMLHttpRequest.abort()` 取消上一个请求。

2017 年前后，`AbortController` 进入 Fetch 标准（Chrome 66 起支持），取消请求有了统一的方式：把 `signal` 传进 `fetch`，需要时 `abort()`。随后 Axios 0.22 支持 `signal`，Vue 生态里的请求封装普遍跟进。React 的 `useEffect` 则把「清理函数」写进了 API：effect 返回的函数会在依赖变化时执行，天然适合「取消上一次」。

到这里，社区形成了两种主流做法：**序号比对**（只认最后一次的结果，前面的丢弃）与**主动取消**（把前面的请求 abort 掉）。前者不依赖请求库，后者能省带宽。

### 与本章的关系

本章第六节选了序号比对，理由是它不依赖请求库的能力，也不需要在 `finally` 里区分「是被取消还是真失败」——被取消的请求会 reject，一不小心就会被全局错误提示捕获，弹出「请求失败」。如果项目已经在请求层统一注入了 `signal`，主动取消更好；否则序号方案更稳。
