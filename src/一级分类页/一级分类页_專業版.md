# 一级分类页

> 从这一章开始，页面不再是「写死的」，而是「一个 ID 撑起一整页」。面包屑、Banner、商品列表都依赖同一个参数，而参数会变。

## 一、一级分类页的职责：一个 ID 撑起整页

一级分类页对应路由 `/category/:id`。用户点首页的分类图标、点导航里的一级分类、或者直接粘贴一个链接，最终都落到这个页面，区别只是 `id` 不同。

这一页要做四件事：

1. 告诉用户「我在哪」——面包屑：首页 / 手机数码
2. 展示这个分类的活动图——分类 Banner
3. 让用户能横向切换到别的一级分类——左侧或顶部的分类导航，当前项高亮
4. 展示该分类下的商品——列表 + 分页

这四件事共用同一个数据源：`id`。也就是说，`id` 一变，四块内容都要跟着换。这决定了本章最重要的一条技术约束：**页面必须对参数变化有反应**。

很多人第一次写会写成这样：

```js
const route = useRoute()
const list = ref([])
onMounted(async () => {
  list.value = (await getTopCategoryAPI(route.params.id)).result
})
```

从首页点进来没问题。但当用户在这个页面上点了另一个分类，地址栏从 `/category/1005000` 变成 `/category/1005001`，图像、面包屑、商品列表全都不动——因为组件被复用了，`onMounted` 不会再执行。第六节专门解决这件事。

还有一个更基础的判断：**这一页该不该缓存**。切走再切回来，是希望保留滚动位置和已加载的数据，还是希望重新拉一次？电商列表页通常不缓存，因为价格和库存会变；但切换分类时要避免整页闪白。这两件事的处理方式不同，后面会分开讲。

## 二、静态结构与路由配置：先把占位组件跑通

写页面的第一步永远是「能看到东西」。先建一个只有标题的组件，配好路由，确认能从首页点进来，再往里填内容。

```js
// router/index.js
{
  path: '/category/:id',
  component: () => import('@/views/Category/index.vue'),
}
```

这条路由通常放在 Layout 的 `children` 里，因为它需要顶部导航和页脚：

```js
{
  path: '/',
  component: Layout,
  children: [
    { path: '', component: Home },
    { path: 'category/:id', component: () => import('@/views/Category/index.vue') },
  ],
}
```

导航项与首页分类图标的链接都指向这里，注意必须拼出具体的 `id`：

```html
<!-- LayoutNav -->
<RouterLink v-for="c in navList" :key="c.id" :to="`/category/${c.id}`" class="nav-item">
  {{ c.name }}
</RouterLink>

<!-- Home 分类区 -->
<RouterLink :to="`/category/${c.id}`" class="cat-item">
  <img :src="c.picture" :alt="c.name" />
  <span>{{ c.name }}</span>
</RouterLink>
```

这里有一个容易忽略的细节：`/category` 单独访问（没有 id）会匹配失败。要么给它一个默认分类，要么让它重定向到首页。小兔鲜让「全部分类」这个导航项不指向 `/category`，而是展开一个下拉面板，避免出现「合法路由但没有内容」的状态。

组件骨架：

```html
<template>
  <div class="top-category">
    <div class="container">
      <XtxBread>...</XtxBread>
      <Banner :site="2" />
      <ul class="goods-list">
        <li v-for="g in list" :key="g.id"><GoodsItem :item="g" /></li>
      </ul>
    </div>
  </div>
</template>
```

骨架阶段用假数据就能看清布局是否稳：列表放 4 个、8 个、20 个各试一遍，确认空态、单行不满、图片比例不一致时都不塌。等结构稳了再接接口，否则一旦样式出问题，你分不清是数据形状不对还是 CSS 写错了。

## 三、面包屑导航：组件、接口与「能不能点」

面包屑看着简单，实际上要处理三件事：层级怎么表达、哪一层可点、数据从哪来。

先看结构。一个面包屑是一个 `nav`，里面的层级用分隔符连接：

```html
<!-- XtxBread -->
<nav class="xtx-bread">
  <span class="xtx-bread-item"><slot /></span>
</nav>
```

单个层级做成组件，接受 `to` 决定是否可点：

```html
<!-- XtxBreadItem -->
<template>
  <RouterLink v-if="to" :to="to" class="item"><slot /></RouterLink>
  <span v-else class="item"><slot /></span>
</template>
<script setup>
defineProps({ to: String })
</script>
```

用法：

```html
<XtxBread>
  <XtxBreadItem to="/">首页</XtxBreadItem>
  <XtxBreadItem>{{ category.name }}</XtxBreadItem>
</XtxBread>
```

最后一层不能点——点了就是「跳到当前页」，没有意义。这个判断放在组件里比放在调用处更省事：调用方只关心「这一层有没有目标地址」。

数据来源是一个细节。面包屑需要的只有分类名和父级，但页面还需要商品列表、筛选条件。所以不要为面包屑单独发一个「只要名字」的接口，直接用页面已经在取的分类详情：

```js
const { result } = await getTopCategoryAPI(id)
// result: { id, name, children, picture, saleProperties, ... }
```

只有一种情况值得单独拆接口：这一页的数据量很大，而面包屑在首屏就要显示。这时可以让面包屑用轻量接口先渲染，主内容再慢慢加载。

还有一个边界：**直接分享一个不存在的 id**。接口返回空对象或 404，页面上就会出现「首页 / 」这种残缺面包屑。处理方式是分类名为空时补一个兜底文案，并给一个「返回首页」的出口，而不是让用户困在空白页。

## 四、分类 Banner：把首页的轮播抽成可复用组件

第 5 章的 Banner 是写在首页里的，只服务首页。到了分类页，又要一个 Banner，但图片内容不同。这时候正确的做法不是复制一份，而是**把 Banner 变成带参数的组件**。

小兔鲜的 Banner 接口有一个 `distributionSite` 参数：首页传 `1`，分类页传 `2`。后端按这个值返回不同位置的运营图。

```js
// apis/home.js
export const getBannerAPI = (params = {}) =>
  request.get('/home/banner', { params })
```

组件里把参数声明出来：

```html
<!-- Banner.vue -->
<script setup>
import { ref, onMounted } from 'vue'
import { getBannerAPI } from '@/apis/home'

const props = defineProps({ site: { type: Number, default: 1 } })
const list = ref([])

onMounted(async () => {
  list.value = (await getBannerAPI({ distributionSite: props.site })).result
})
</script>
```

这么改之后，首页 `<Banner />` 不用动（默认 1），分类页写 `<Banner :site="2" />`。

要注意的是，重构成通用组件时**不要把两处的差异都塞进一个 props**。如果分类 Banner 以后要做成「三张图、无自动播放」，首页是「五张图、自动播放」，那就不该继续加 `autoplay`、`count` 之类的参数，而是回到第 5 章的判断：差异小于 20% 就合并，差异会持续增长就分开。

另一个细节：两个位置的图片比例可能不同。首页 Banner 是宽幅大图，分类页的图更扁。所以高度不能写死在一个地方，应该由调用方决定：

```html
<Banner :site="2" height="300px" />
```

组件内部 `el-carousel` 的 `height` 直接绑定这个值。这比在组件里写 `if (site === 2) ...` 干净得多——差异用参数表达，而不是用分支表达。

## 五、导航激活状态与分类列表渲染

分类页里有两个「列表」，性质完全不同，容易混：

- **导航列表**：一级分类的集合，来自 Layout 已经取过的 store，作用是「让用户切到别的分类」
- **商品列表**：当前分类下的商品，来自本页的请求，作用是「展示」

第一个列表不需要再请求。第 4 章已经把分类数据放在 store 里，这里直接读：

```js
import { useCategoryStore } from '@/stores/category'
const categoryStore = useCategoryStore()
// categoryStore.list 就是一级分类集合
```

激活状态怎么判断？两种写法，各有适用场景。

第一种，交给 `RouterLink`：

```html
<RouterLink
  v-for="c in categoryStore.list"
  :key="c.id"
  :to="`/category/${c.id}`"
  active-class="active"
  exact-active-class="active-exact"
>
```

第二种，自己比：

```html
<RouterLink :to="`/category/${c.id}`" :class="{ active: route.params.id === String(c.id) }">
```

差异在于：`active-class` 是**包含匹配**，`/category/1005000` 会让 `/category` 也激活（第 4 章的坑）；自己比则是严格相等。如果导航里混着「全部分类」这种父级链接，就用 `exact-active-class`；如果导航项只有具体分类，两种都行，自己比更直观。

一个常见现象：从二级分类页（`/category/sub/:id`）返回一级分类页时，一级导航不亮。原因是路径不同、`id` 是二级分类的 id，两种判断都对不上。这时候需要「找到当前二级分类的父级 id 再激活」，属于信息架构层面的问题，不是 CSS 能解决的。

商品列表部分：

```js
const list = ref([])
const total = ref(0)
const reqParams = reactive({ categoryId: null, page: 1, pageSize: 20 })

async function loadGoods() {
  const { result } = await getCategoryGoodsAPI(reqParams)
  list.value = result.items
  total.value = result.counts
}
```

渲染时给每一项一个稳定的 `key`。用 `index` 做 key 在切换分类时会复用旧节点，图片和文字出现「错位一帧」的现象——因为 Vue 认为「第 0 项还是第 0 项」，只更新了内容，而图片的加载是异步的。

```html
<li v-for="g in list" :key="g.id"><GoodsItem :item="g" /></li>
```

空态也要写。一个新分类没有商品是正常的，页面应该显示「该分类暂无商品」并给一个返回入口，而不是留一片白。

## 六、路由缓存问题：同一个组件、不同的 ID

这是本章最核心的一个坑，值得单独一节。

Vue Router 在**路由记录相同、只有参数变化**时，会复用组件实例，不会销毁重建。所以 `/category/1005000` → `/category/1005001` 时：

- `setup` 不重新执行
- `onMounted` 不重新执行
- `onUnmounted` 不执行
- 只有 `route.params` 变了

结果就是：地址栏变了，页面不动。第一次遇到的人通常会怀疑「是不是接口没请求」，其实请求根本没发。

三种修法，按推荐顺序。

**第一种，监听参数**（推荐）：

```js
const route = useRoute()
const id = computed(() => route.params.id)

watch(id, async (val) => {
  if (!val) return
  await loadCategory(val)
}, { immediate: true })
```

`immediate: true` 让首次进入也会执行，所以不要再写 `onMounted`，否则会请求两次。这是最常见的「多请求一次」的来源。

**第二种，给 RouterView 加 key**：

```html
<RouterView :key="route.fullPath" />
```

这样任何路径变化都会重建整个子树。代价是：Layout 里的所有状态被重置（展开的菜单、滚动位置），过渡动画重放，而且这个 key 加在 Layout 上会影响所有子页面，不只是分类页。范围太大，通常不划算。

**第三种，`onBeforeRouteUpdate`**：

```js
onBeforeRouteUpdate((to) => {
  loadCategory(to.params.id)
})
```

它只在「同一路由记录内参数变化」时触发，语义最精确。缺点是它不在组合式 API 的主线里，读代码的人要额外知道这个钩子；而且它不会处理首次进入，仍然要配合 `onMounted` 或 `watch`。

选第一种的理由是可读性：一个 `watch` 就把「参数变了要干什么」写在了一起，和第六节要讲的函数拆分也好配合。

还有一个衍生问题：**快速连续切换分类时的竞态**。用户点了 A、又点了 B，A 的响应如果比 B 晚回来，就会把 B 的数据覆盖掉。处理方式是记录一个序号，只接受最新一次的结果：

```js
let seq = 0
async function loadCategory(id) {
  const cur = ++seq
  const { result } = await getTopCategoryAPI(id)
  if (cur !== seq) return          // 已经有更新的请求了
  category.value = result
}
```

## 七、基于业务逻辑的函数拆分

到这一节，页面组件里已经堆了三件事：取分类详情、取商品列表、处理参数变化。继续往里写会变成一个两百行的 `script`。这时候该拆。

拆的原则不是「按代码长度切」，而是「按变化的理由切」。分类详情和商品列表的变化理由不同（前者跟分类走，后者跟分页和筛选走），所以应该拆成两块。

```js
// composables/useCategory.js
import { ref, watch } from 'vue'
import { useRoute } from 'vue-router'
import { getTopCategoryAPI } from '@/apis/category'

export function useCategory() {
  const route = useRoute()
  const category = ref({})
  const loading = ref(false)
  let seq = 0

  async function load(id) {
    const cur = ++seq
    loading.value = true
    try {
      const { result } = await getTopCategoryAPI(id)
      if (cur === seq) category.value = result || {}
    } finally {
      if (cur === seq) loading.value = false
    }
  }

  watch(() => route.params.id, (id) => { if (id) load(id) }, { immediate: true })

  return { category, loading }
}
```

商品列表单独一个：

```js
// composables/useCategoryGoods.js
export function useCategoryGoods() {
  const route = useRoute()
  const list = ref([])
  const total = ref(0)
  const page = ref(1)

  async function load() {
    const { result } = await getCategoryGoodsAPI({
      categoryId: route.params.id,
      page: page.value,
      pageSize: 20,
    })
    list.value = result.items
    total.value = result.counts
  }

  watch(() => [route.params.id, page.value], load, { immediate: true })

  return { list, total, page }
}
```

拆出来之后，页面组件只剩组装：

```js
const { category, loading } = useCategory()
const { list, total, page } = useCategoryGoods()
```

有两个地方容易拆坏。

第一，**`useRoute()` 必须在 `setup` 期间调用**，不能把 composable 放到事件回调里执行，否则拿不到当前路由上下文。

第二，**`watch` 写在 composable 里，依赖的是调用时的组件实例**。这没问题，但意味着这个 composable 不能在组件外调用（比如在 router 守卫里），否则监听不会自动清理。第 4 章讲的 `effectScope` 就是这条规则的底层原因。

最后一点判断：**不要为了「看起来架构好」而拆**。如果一个函数只被一个组件用、只做一件事、不超过三十行，留在组件里更快读懂。拆分的收益是「复用」和「隔离变化」，两者都不成立时就只是把代码挪远了。

## 八、工程实践与常见坑

**第一，点另一个分类页面不动。** 现象是 URL 变了、内容没变。原因是路由记录相同、组件被复用，`onMounted` 不再执行。处理方式：`watch(() => route.params.id, ..., { immediate: true })`。

**第二，接口请求两次。** 同时写了 `onMounted` 和带 `immediate` 的 `watch`。处理方式：二选一，通常只留 `watch`。

**第三，面包屑最后一层也能点。** 因为调用时给每一层都传了 `to`。处理方式：最后一层不传 `to`，由组件内部判断渲染成 `span`。

**第四，快速切换分类后数据串了。** 旧请求晚回来覆盖了新数据。处理方式：序号比对，或 `AbortController` 取消上一个请求。

**第五，Banner 在分类页比例不对。** 因为复用了首页写死的高度。处理方式：高度与站点参数都由调用方传入，组件不猜。

**第六，列表用 `index` 当 key。** 切分类时图片错位闪一下。处理方式：用数据的 `id`。

**第七，空分类留白。** 新分类没有商品时页面一片空白。处理方式：写空态文案 + 返回入口。
