# 一级分类页 · 练习与自测

> 题量：是非 10 / 选择 10 / 配对 8 / 情境 3 / 代码阅读 3 / 延伸思考 2。答案紧跟各区块。

## 一、是非题（10 题）

1. 路由从 `/category/1` 切到 `/category/2` 时，组件会先销毁再重建。
2. `watch(() => route.params.id, fn, { immediate: true })` 在首次进入时也会执行一次。
3. 同时写 `onMounted` 和带 `immediate` 的 `watch`，首次进入只会请求一次。
4. `<RouterView :key="route.fullPath" />` 只影响当前这一个子页面。
5. 面包屑的最后一层不应该做成链接。
6. 面包屑必须单独发一个「只取分类名」的接口。
7. `active-class` 是包含匹配，`/category/1005000` 会让 `/category` 也激活。
8. Banner 组件的高度应该由使用它的页面传入，而不是组件内部按位置写死。
9. 切换分类时列表用 `index` 当 key，会出现图片错位一帧的现象。
10. 连点两个分类时，先发的请求如果后返回，会覆盖后发请求的结果。

### 答案解析

1. **错**。路由记录相同、只有参数变化时，组件实例会被复用，`setup`/`onMounted` 都不会再执行。
2. **对**。`immediate` 让监听立即执行一次，效果等同于首次加载。
3. **错**。两处都执行，会请求两次。
4. **错**。`key` 加在哪里就重建哪棵子树；加在 Layout 上会让整个外壳一起重建。
5. **对**。点击它等于「跳到当前页」，对交互与读屏用户都是噪音。
6. **错**。通常直接复用页面已取的分类详情；只有「面包屑必须首屏可见且主数据很慢」时才值得拆。
7. **对**。这是第 4 章讲过的坑，本章仍会复现。
8. **对**。不同位置的图片比例不同，高度属于使用方的决策。
9. **对**。Vue 会认为「第 0 项还是第 0 项」，只换内容不换节点，异步加载的图片会闪。
10. **对**。这是典型的乱序响应，需要序号比对或取消请求。

## 四、情境分析（3 题）

### 情境 1：切换分类后页面纹丝不动

用户在分类页点了左侧另一个分类，地址栏从 `/category/1005000` 变成 `/category/1005001`，但面包屑、Banner、商品列表都没变。Network 面板没有新请求。

**问**：原因与修法。

**答**：路由记录相同、仅参数变化，Vue Router 复用组件实例，`onMounted` 不会再次执行，所以没有发请求。修法：`watch(() => route.params.id, load, { immediate: true })`；同时删掉原来的 `onMounted` 调用，避免首次进入请求两次。

### 情境 2：面包屑点了最后一层，页面重新加载

用户点面包屑最后一层「手机数码」，发现页面闪了一下，列表重新加载，滚动位置回到顶部。

**问**：为什么会这样，怎么改？

**答**：最后一层被渲染成了 `RouterLink`，指向当前 URL，触发了一次同路由跳转，导致组件重新渲染、数据重新请求。修法：最后一层不传 `to`，组件内部渲染成 `span` 并加 `aria-current="page"`。

### 情境 3：连续切换分类，最后显示的是错的

测试同学手速很快，连续点了「手机」「电脑」「家电」，最后停在「家电」，但商品列表显示的是「电脑」的商品。

**问**：为什么？给出两种修法。

**答**：三个请求并发，先发的可能后返回，「电脑」的响应晚于「家电」，把列表覆盖了。修法一：序号比对，请求返回时比对当前序号，只有最新的才写入。修法二：给请求加 `AbortController` 的 `signal`，切换时 abort 上一个请求，并注意被取消的请求不要走全局错误提示。

## 五、代码阅读（3 题）

### 题 1

```js
const route = useRoute()
const list = ref([])

onMounted(async () => {
  list.value = (await getListAPI(route.params.id)).result
})
```

**问**：这段代码在什么场景下会失效？为什么？

**答**：在同一路由内切换参数（`/category/1` → `/category/2`）时失效。组件被复用，`onMounted` 不会再次执行，`list` 保持上一次的数据。

### 题 2

```js
watch(() => route.params.id, async (id) => {
  const { result } = await getTopCategoryAPI(id)
  category.value = result
}, { immediate: true })
```

**问**：这段代码缺了什么保护？什么情况下会出问题？

**答**：缺少竞态保护。快速切换分类时，旧请求可能后返回并覆盖新数据。应加序号比对，或在写入前确认 `route.params.id === id`。

### 题 3

```html
<XtxBread>
  <XtxBreadItem to="/">首页</XtxBreadItem>
  <XtxBreadItem :to="`/category/${category.id}`">{{ category.name }}</XtxBreadItem>
</XtxBread>
```

**问**：这段代码有什么问题？

**答**：最后一层（当前分类）被做成了链接，指向当前页。点击会触发同路由跳转，导致数据重新加载、滚动位置丢失；对读屏用户也是冗余。应去掉 `to`。

## 六、延伸思考（2 题）

1. 为什么 Vue Router 选择「参数变化时复用组件」而不是「一律重建」？请从体验、性能与状态三个角度说明，并指出这个选择带来的代价。

   **思路**：体验上避免整页闪白与滚动位置丢失；性能上少一次组件树创建与图片重新加载；状态上保留用户输入与展开状态（比如筛选面板）。代价是「数据不会自动刷新」，需要开发者显式声明依赖——也就是 `watch` 或 `onBeforeRouteUpdate`。这是一次「把隐式行为变成显式代码」的交换，和 React `useEffect` 的依赖数组是同一类设计。

2. 如果产品要求「从分类页返回时保留滚动位置和已加载的列表」，你会怎么做？和本章「参数一变就重新取数」的做法冲突吗？

   **思路**：不冲突，两者解决的是不同问题。「参数变」对应的是「内容必须换」，「返回」对应的是「恢复现场」。常见做法是用 `<KeepAlive>` 缓存列表页，配合 `onActivated`/`onDeactivated` 决定是否刷新；同时给需要恢复的滚动容器记录位置。要注意 `KeepAlive` 与「参数变化 watch」会叠加：缓存命中时 `watch` 不会重新执行，需要在 `onActivated` 里判断「参数是否与缓存时一致」。这也是为什么很多项目只在列表页开 `KeepAlive`、详情页不开。

## 自测标准

- 能解释「同一组件、不同参数」为什么不重建，并写出 `watch + immediate` 的修法：合格
- 能独立完成面包屑、Banner 复用与导航高亮，且避开包含匹配的坑：良好
- 能处理连点切换的竞态，并把取数与参数变化拆成可复用的 composable：优秀
