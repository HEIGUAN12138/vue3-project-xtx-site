# 订单页 · 白话版

> 结算页是「我想买」和「我真的买了」之间的那道门槛。跨过去之前，一切都还能反悔。

## 一、结算页的位置：从购物车到订单的那一步

点外卖的时候，你会在结算页停留最久：看看点的对不对、地址改没改、有没有优惠券、一共多少钱。这一页叫「确认订单」，它只回答三个问题——**买什么、送到哪、付多少**。

注意它**不负责下单**。下单是按下「提交订单」之后的事。

这个界线为什么重要？因为你可能在这一页反复来回：发现少点了一份小吃，退回去加；发现地址写错了，切一个。如果一进来就自动下单，你可能什么都没确认，桌上已经多了三份外卖。

所以结算页的数据不是前端自己拿购物车算的，而是**拿着购物车里的东西去问仓库一遍**：现在什么价、还有没有货、运费多少、能减多少。仓库（服务端）回一份「预订单」。

为什么要问这一遍？因为东西放到购物车里之后，价格可能变了。你在车里看到 199 元，隔了一晚商家调到 219 元。如果页面还按 199 算，到付款时才告诉你 219，你会怎么想？**结算页的数字必须和最后扣款的数字一致**，这一条比任何交互细节都重要。

## 二、路由与接口：一次请求拿全结算信息

进结算页只发一个请求，这个请求什么参数都不带。

听起来很奇怪：不带参数，服务器怎么知道要结算什么？因为它知道你是谁（登录态），也知道你购物车里勾了哪些。这把「谁要买什么」的判断放在了服务端，好处是地址栏干净、刷新不丢数据、手机和电脑看到的一样。

代价也很明显：**用户可以自己敲地址进这一页**。如果购物车里一件没勾，进来就是一个空页面。

这就像你推开一家餐厅的门，服务员发现你没点菜。正确的做法不是让你坐在空桌子前发呆，而是说一句「您还没选菜」，然后把你领回点菜的地方。

所以这一段代码是必须的：

```js
if (!result.goods || result.goods.length === 0) {
  ElMessage({ type: 'warning', message: '请先在购物车中选择商品' })
  router.replace('/cartlist')
  return
}
```

还有一个细节：默认地址要「找一找」。可能有一个标着默认的，也可能一个都没有（用户把默认的删了），甚至可能有多个（系统没管好）。所以顺序是：有默认就用默认，没有就用第一个，都没有就先空着。

另外，「当前选中的地址」要单独存一份，不能直接去改地址簿里那条记录的「默认」标记。理由很生活：你在餐厅指着菜单说「这个」，这个动作不该改变菜单本身。

## 三、渲染三块数据：地址、商品、金额

页面分三块，像一张纸单：上面写寄给谁，中间列买了什么，下面算钱。

**地址那块。** 收件人、电话、完整地址。地址被拆成了「省市区」和「详细门牌」两半，不是后端偷懒——因为运费要按区域算，省市区得能单独取出来。前端把它们拼起来显示就行，别自己去拆字符串。

**商品那块。** 图片、名称、规格、单价、数量、小计。这里有一个容易被产品经理挑战的点：**为什么结算页不能改数量？**

因为改数量要重算金额，而金额里有优惠、有运费阶梯、有会员价——这些都在服务端。你在前端改完，数字和服务端又对不上。正确做法是「要改就回购物车改」，让用户多走一步，但保证他看到的每一个数字都算数。

**金额那块。** 商品总额、运费、优惠、应付。四个数字全部直接用接口给的，**一个都不要自己算**。

这一条和购物车那章刚好相反：购物车里的合计可以前端算，因为那里没有优惠规则；结算页的应付必须服务端算，因为规则在服务端。判断标准就一句话：**谁能保证这个数字对，就让谁算**。

## 四、地址弹窗：v-model 控制与激活态

地址列表像你在填表时翻出的那本通讯录：翻开、用手指点一个、再合上。

这中间有三个状态，缺一个就会出毛病：

1. **弹窗开没开**
2. **我手指点在哪一条上**（高亮）
3. **最后到底用了哪一条**（生效）

很多人会图省事只留两个：点哪条就直接生效。这样做的后果是——你点错了想反悔，可「取消」按钮已经没用了，因为地址早就改了。

所以流程必须是：打开弹窗时，先把「高亮」对齐到「当前生效」；点击只改「高亮」；点确定才把「高亮」变成「生效」。

```
打开 → 高亮 = 生效
点击 → 高亮 = 你点的那个
确定 → 生效 = 高亮
取消 → 什么都不做
```

`el-dialog` 的开合用 `v-model` 控制。可以把它理解成「一个会自动同步的开关」：你改开关，弹窗跟着开关；弹窗被自己关掉（比如按了右上角的叉），开关也会跟着改。知道这一点，就不会在「点了叉但变量没变」时怀疑组件有 bug。

还有一个小遗憾：课程版本里，地址项是用 `div` 加点击事件做的。鼠标能点，**键盘选不中**。这就像电梯按钮只认手指不认盲杖——真实项目里应该换成真正的单选按钮，或者补上键盘支持。

## 五、提交订单：请求体里该放什么

按下「提交订单」，等于把这张纸单交给后厨。交上去的内容必须刚好够用，多一个字段都可能是隐患。

要交的东西是：配送时段、支付方式、支付渠道、留言、商品清单、地址编号。

商品清单里**只放两样：哪件、几件**。

为什么不放价格？因为请求是能从浏览器里改的。有人装个小插件，把「199 元」改成「1 元」，如果服务端信了，商家就得倒贴。所以价格必须由服务端自己从库里取——前端传来的价格只用来显示，不参与算账。

这也是为什么代码里要把商品「重新映射一遍」：

```js
goods: checkInfo.value.goods.map(item => ({ skuId: item.skuId, count: item.count }))
```

购物车里那份数据带着图片、名称、规格、价格一大堆字段。把这些原封不动传上去，等于给了后端一个「误用前端字段」的机会。**只传必要的，是接口契约的一部分。**

留言这个字段也有讲究：可以不填，但不能「什么都不传」。有的后端会把它当必填，收到 `undefined` 就回 400。所以传空字符串，是给它一个「明确的空」。

## 六、幂等与重复提交：最容易被忽略的一步

你在电梯里按了一下按钮，没反应，于是又按了三下。电梯只来一趟，没问题。

但下单不是电梯。手快连点两下「提交订单」，就是两张订单、两次扣款、两份快递。

防这件事有三道门，一道比一道硬。

**第一道：按钮自己拦住。** 点下去之后按钮变灰、转圈，不让再点。这道门防的是「手抖」，成本最低。

**第二道：给这次请求一个身份证号。** 进结算页时生成一串随机字符，提交时带上。服务端看到同一个身份证号的第二次请求，直接把第一次的结果还给你，不再新建订单。这道门防的是「网络超时了但其实成功了，用户又点了一次」——这是最隐蔽的一种重复。

**第三道：服务端自己查。** 比如「同一个人五分钟内不能重复下同一单」。这道门在浏览器被绕过、被篡改时仍然有效，是最后的底线。

三道都要有，因为它们防的不是同一种情况。

## 七、从订单 ID 到支付页：query 与路由设计

订单创建成功，服务端给你一个编号，页面带着这个编号去支付页。

编号怎么带？放在地址栏问号后面：`/pay?id=12345`。

为什么不像密码那样「藏着传」？因为**它需要能刷新、能被找回来**。用户支付失败，客服发一条链接给他，点开就能回到同一张订单——这只有把编号写在地址里才做得到。藏在内存里的参数，一刷新就没了。

跳过去用 `push` 还是 `replace`？这里**用 `push`**，和登录页刚好相反。

判断标准只有一个：**用户按返回键，会看到一个「有意义的页面」还是「一个会让他重复操作的页面」？**

- 登录成功回登录页：毫无意义，还容易让他再登一次。所以用 `replace`，把登录页从历史里抹掉。
- 支付页返回结算页：有意义。他可能想改地址、想再看一眼。所以用 `push`，允许回去。

当然，回到结算页时那张订单已经存在了，页面得会说一句「您有一张待支付的订单，要继续支付吗」，而不是傻乎乎再建一张。

最后一句提醒：这个订单号虽然来自服务端，但到了前端就属于「不可信的输入」。它不能拿去拼 HTML，也不能用来判断「这单是不是我的」——那是后端该回答的问题。

## 八、工程实践与常见坑

**一、页面一加载就下单。** 用户每按一次刷新就多一张订单。下单只能由「点击提交」触发。

**二、把价格传给后端。** 请求能被改，等于把定价权交出去。

**三、留言传了 `undefined`。** 后端按必填校验，直接 400。

**四、没处理「购物车是空的」。** 用户从收藏夹里点进来，看到一个空白的结算页，以为网站坏了。

**五、默认地址没兜底。** 一个地址都没有时，提交时报「地址不存在」。要三段兜底，并禁用提交按钮。

**六、切换地址直接改了地址簿。** 用户点取消也回不去了。

**七、弹窗只维护两个状态。** 「高亮」和「生效」混成一个，取消按钮形同虚设。

**八、提交按钮没有 loading。** 连点两次，两张订单。

**九、接口超时后没有幂等键。** 用户重试，重复下单。

**十、金额在前端重算。** 优惠、运费、会员价任何一处和服务端不一致，都会变成「显示的和扣的不一样」。

**十一、列表用下标当 `:key`。** 顺序一变就渲染错位，删一个地址可能显示成另一个。

## 一句话总结

结算页只做三件事：**问服务端要一份预订单、让用户确认地址与清单、按下提交时只交「哪件几件」**——金额一律服务端算、下单只能由点击触发、按钮与幂等键一起挡住重复提交。
