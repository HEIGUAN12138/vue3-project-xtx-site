# 订单页 · 练习与自测

> 题量：是非 10 / 选择 10 / 配对 8 / 情境 3 / 代码阅读 3 / 延伸思考 2。答案紧跟各区块。

## 一、是非题（10 题）

1. 结算页应该在 `onMounted` 里创建订单，这样用户少点一次。
2. 结算页的应付金额可以由前端用购物车数据算出来。
3. `/member/order/pre` 这类接口的作用是给出一份报价，而不是创建订单。
4. 提交订单时应该把每件商品的 `price` 一起传给后端，方便对账。
5. `buyerMessage` 可以不填，但最好传空字符串而不是 `undefined`。
6. 切换地址弹窗里，高亮项与生效地址应该是同一个状态。
7. 提交订单成功后应立刻跳转到支付页，而不是停留在结算页。
8. 订单号放在 `query` 里比放在 `params` 里更容易被刷新保留。
9. 订单号是服务端返回的，所以可以直接用来判断「这张订单是不是我的」。
10. 只要是 `POST` 请求，天然就是幂等的。

### 答案解析

1. **错**。`onMounted` 里下单会让用户每刷新一次生成一张订单。
2. **错**。优惠、运费、会员价都在服务端，前端算出来必然可能与实际扣款不一致。
3. **对**。它是预订单（checkout preview），只有 `POST /member/order` 才创建订单。
4. **错**。前端可改价格，等于把定价权交给用户；只传 `skuId` 与 `count`。
5. **对**。部分后端会按必填校验，收到 `undefined` 直接 400。
6. **错**。「高亮」与「生效」必须是两个状态，否则「取消」失效。
7. **对**。这也是 Post/Redirect/Get 的思路：写操作结束后落到一个只读地址。
8. **对**。`query` 在地址栏里，刷新与分享都保留；`params` 依赖内存中的路由状态。
9. **错**。归属校验必须在服务端做，前端判断等于没判断。
10. **错**。`POST` 是非幂等的，这正是需要幂等键与去重的原因。

## 二、选择题（10 题）

1. 结算页的金额应该来自？
   A. 购物车合计　B. 服务端预订单接口　C. 前端重新计算　D. URL 参数

2. 用户直接访问 `/checkout` 且购物车为空，正确处理是？
   A. 渲染空表格　B. 报错白屏　C. 提示并跳回购物车　D. 自动加一件

3. 默认地址的兜底链应该是？
   A. 只用 `isDefault`　B. `isDefault` → 第一项 → 空对象　C. 随机一项　D. 必须后端保证唯一

4. 提交订单的 `goods` 字段应只包含？
   A. `skuId` 与 `count`　B. 完整商品对象　C. 商品名与价格　D. 图片与规格

5. 提交按钮加 `loading` 的作用是？
   A. 美观　B. 防重复提交　C. 加快请求　D. 替代校验

6. 幂等键主要防的是？
   A. 用户手抖　B. 网络超时后的重试　C. SQL 注入　D. 越权访问

7. 支付页用 `router.push` 而不是 `replace`，理由是？
   A. 性能更好　B. 返回结算页是有意义的　C. `replace` 有 bug　D. 便于埋点

8. 地址弹窗需要几个状态？
   A. 1 个　B. 2 个　C. 3 个　D. 不需要

9. 列表渲染的 `:key` 应该用？
   A. `index`　B. 唯一 ID（如 `skuId`）　C. `name`　D. 随机数

10. 服务端只按 `req.query.id` 查订单的风险是？
    A. 性能差　B. 越权访问（IDOR/BOLA）　C. 类型错误　D. 缓存失效

### 答案解析

1. **B**。只有服务端知道当前价格、运费与优惠。
2. **C**。空态必须给下一步，否则用户以为网站坏了。
3. **B**。可能没有默认、也可能有多个，必须三段兜底。
4. **A**。金额由服务端按库内价格重算，这是防篡改的第一道门。
5. **B**。连点两下就是两张订单，这是最常见的一类事故。
6. **B**。手抖由按钮防，重试由幂等键防，绕过由服务端去重防。
7. **B**。用户可能想回去改地址或再看一眼，返回结算页是有意义的。
8. **C**。弹窗开关、弹窗内高亮、页面上生效，三者职责不同。
9. **B**。`index` 在顺序变化时会导致错位复用。
10. **B**。编号可枚举且无归属校验，就是最典型的 IDOR。

## 四、情境分析（3 题）

### 情境 1：用户刷新一次，多了一张订单

运营发现同一个用户五分钟内出现了三张内容完全一样的订单，收货地址与商品都相同。

**问**：最可能的原因与三道修法。

**答**：最可能是「创建订单被写在了页面初始化逻辑里」，或者「提交成功后没有离开结算页」，用户刷新即重新提交。修法：一，下单只由点击触发；二，提交成功后立刻 `router.push('/pay?id=...')`，让地址变成只读页；三，提交时带幂等键、按钮加 `loading`，服务端对同键去重。

### 情境 2：显示应付 199，实际扣款 219

用户截图显示结算页「应付总额 ¥199.00」，付款页显示「应付 ¥219.00」，投诉价格欺诈。

**问**：技术上的成因，以及该在哪一层修。

**答**：结算页的金额大概率是前端用购物车旧价格算的，或者缓存了上一次的预订单；而支付页拿到的是服务端按当前价格重算的结果（可能含运费变化或优惠过期）。修法在接口层：结算页与支付页都必须用服务端返回的金额，前端不重算；若两次金额不一致，应在进入支付页前提示「价格有变动，请确认」并要求用户重新确认，而不是静默替换。

### 情境 3：地址切换点了取消，地址却变了

用户在弹窗里点了一个新地址，觉得不对，点了「取消」，结果页面上的地址已经变成新的了。

**问**：状态设计上缺了什么？

**答**：缺了「高亮」与「生效」的分离。点一下就写 `curAddress`，导致取消无效。正确设计是三状态：`showDialog`、`activeAddress`、`curAddress`；打开弹窗时 `activeAddress = curAddress`，点击只改 `activeAddress`，点确定才提交给 `curAddress`。

## 五、代码阅读（3 题）

### 题 1

```js
onMounted(async () => {
  const res = await createOrderAPI(payload)
  router.push('/pay?id=' + res.result.id)
})
```

**问**：这段代码会造成什么后果？

**答**：每次进入结算页就创建一张订单：刷新、前进后退、从支付页返回，都会新建。应改为由「提交订单」按钮触发，并在 `onMounted` 里只调用 `getCheckoutInfoAPI()` 获取预订单。

### 题 2

```js
const createOrder = () => {
  createOrderAPI({
    goods: checkInfo.value.goods,
    addressId: curAddress.value.id,
    buyerMessage: undefined,
  })
  router.push('/pay')
}
```

**问**：四处问题。

**答**：一，`goods` 传了完整对象，包含价格等不该由前端决定的字段；二，`buyerMessage` 为 `undefined`，可能触发后端必填校验；三，没有 `await` 也没有处理失败，请求还没回来就跳转了，`/pay` 也没有订单号；四，没有防重复提交与错误提示。

### 题 3

```js
const switchAddress = (item) => {
  curAddress.value = item
  showDialog.value = false
}
```

**问**：这段代码与「弹窗 + 确定按钮」的设计相比，差在哪里？

**答**：少了一次确认，点击即生效，用户无法反悔；也缺少高亮态，用户点错后没有任何视觉反馈。若产品明确要求「点选即关闭」，至少应保留高亮态与「撤销」入口，否则误操作无法挽回。

## 六、延伸思考（2 题）

1. 「结算页的价格必须和服务端一致」这条规则，会不会与「页面要快」冲突？你会怎么平衡？

   **思路**：会冲突——每次进结算页都要请求一次预订单，首屏必然比纯前端计算慢。可用的平衡手段有三：预订单接口做缓存但带短 TTL；进入页面时先用购物车快照做骨架展示（价格处显示占位而非旧价），拿到预订单后再替换；对「价格变动」做显式提示而不是静默更新。核心判断是：**可以让页面慢 200ms，不能让数字错 1 元**。

2. 幂等键应该由谁生成、存在哪、什么时候丢弃？如果用户关闭页面后再打开，同一个键还能用吗？

   **思路**：键应由客户端在「进入结算页」时生成并持久化（如 `sessionStorage`），这样刷新或重新打开同一会话时仍能复用；服务端保存键与结果通常 24 小时，超时后自动清理。若用户在另一个设备上继续，键不同，就会重新创建订单——这正是「服务端去重」存在的理由。设计时要回答的不是「幂等键怎么存」，而是「什么算同一次业务意图」，这个定义决定了键的生命周期。

## 自测标准

- 能说清报价与下单的分工，并让结算页只依赖预订单接口：合格
- 能正确处理地址弹窗的三态、提交体的字段裁剪与空态兜底：良好
- 能用按钮禁用 + 幂等键 + 服务端去重三层防住重复下单，并说明订单号在 URL 里的安全边界：优秀
