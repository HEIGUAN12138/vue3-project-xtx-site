# 订单页

> 结算页是「意愿」变成「承诺」的那一页。用户在购物车点结算时还有退路，到了这一页按下提交，就产生了一张有编号、有金额、有履约义务的订单。

## 一、结算页的位置：从购物车到订单的那一步

把整条链路摊开看，用户的钱是这样一步步被推进的：购物车（想买）→ 结算页（确认买什么、送到哪、付多少）→ 订单（生成编号）→ 支付页（付钱）→ 支付结果（成交或失败）。

结算页（checkout）正好卡在中间，它要回答三个问题，且只回答这三个：

1. **买什么**——用户勾选的商品、数量、单价、小计
2. **送到哪**——收货地址，以及要不要改
3. **付多少**——商品总额、运费、优惠、应付

它**不负责**下单，下单是提交按钮之后的事。这个边界很重要：结算页是「可反复进入」的，用户可以在这一页停留、改地址、退回去加一件商品；而订单一旦创建，就进入了不可回退的履约流程。把「创建订单」写在 `onMounted` 里，会让用户每刷新一次就多一张订单——这是真实项目里出过的事故。

所以路由与数据的关系是：**结算页的数据是从服务端「预计算」出来的，不是前端拼的**。前端把购物车里勾选的 `skuId + count` 交给后端，后端返回一份完整快照：

```js
export const getCheckoutInfoAPI = () => {
  return request({ url: '/member/order/pre' })
}
```

`pre` 这个词很讲究——它是「预订单」，接口文档里常写作 pre-order 或 checkout preview。它返回的结构通常包含三块：

```js
{
  userAddresses: [...],   // 可选的收货地址列表
  goods: [...],           // 结算商品（含实时价格与库存）
  summary: { goodsCount, totalPrice, postFee, discount, payMoney }
}
```

**为什么要服务端算一遍？** 因为价格会变、库存会变、优惠规则在服务端。如果前端拿购物车里的旧价格算合计，用户看到的可能是「¥199」，实际应付「¥219」——这个差异一旦在支付页才暴露，投诉率极高。

## 二、路由与接口：一次请求拿全结算信息

结算页挂在 `Layout` 下（它有顶部导航与页脚），路径是 `/checkout`：

```js
{
  path: 'checkout',
  component: () => import('@/views/Checkout/index.vue'),
}
```

从购物车点「下单结算」时，通常不传商品参数，而是让后端根据「当前用户购物车中已勾选的项」来算。这个设计有好处也有代价：

- **好处**：URL 干净，刷新不丢数据，服务端是唯一真相。
- **代价**：用户可以复制 URL 直接访问，此时如果购物车为空，结算页就是空的——必须处理这个空态，把用户送回购物车。

```js
onMounted(async () => {
  const { result } = await getCheckoutInfoAPI()
  if (!result.goods || result.goods.length === 0) {
    ElMessage({ type: 'warning', message: '请先在购物车中选择商品' })
    router.replace('/cartlist')
    return
  }
  checkInfo.value = result
  curAddress.value = result.userAddresses.find(a => a.isDefault) || result.userAddresses[0] || {}
})
```

这里有两个细节值得单独说。

**第一，空态不是 `v-if` 一下就算了。** 直接渲染一个空页面，用户会以为网站坏了。正确做法是「提示 + 跳回购物车」，让他知道下一步该做什么。

**第二，默认地址的兜底链。** `isDefault` 可能一个都没有（用户删了默认地址），也可能有多个（后端没做唯一约束）。所以是「优先 `isDefault`，其次第一项，再次空对象」。三段兜底看起来很啰嗦，但它挡住了「地址为空导致渲染 `undefined.id`」的报错。

`curAddress` 必须是**独立的一份状态**，而不是直接改 `checkInfo.userAddresses` 里的 `isDefault`：

```js
const checkInfo = ref({})
const curAddress = ref({})
```

理由和购物车的 `selected` 一样：用户点「切换地址」是一种**选择**，而不是对地址簿的修改。把选择写回地址簿，会让「取消」变得不可能——用户改了地址又想改回去，得重新找人问哪个是默认地址。

## 三、渲染三块数据：地址、商品、金额

三块数据对应三个渲染区域，各有各的坑。

**地址区。** 它要显示收件人、电话、完整地址，还要有一个「切换地址」的入口。

```vue
<div class="current">
  <h4>{{ curAddress.receiver }}</h4>
  <p>{{ curAddress.contact }}</p>
  <p>{{ curAddress.fullLocation }}{{ curAddress.address }}</p>
  <el-button size="large" @click="showDialog = true">切换地址</el-button>
</div>
```

`fullLocation` 与 `address` 是两个字段：前者是「省市区」拼好的字符串，后者是详细门牌。后端拆成两个字段，是为了让「同城配送」「区域运费」这类规则能在服务端按区计算。前端直接拼起来展示即可，不要自己去拆。

**商品区。** 一个列表，每行显示图片、名称、规格、单价、数量、小计。数量在这一页**不可改**——改了订单金额就要重算，而重算涉及优惠与库存，属于服务端的事。如果产品坚持要能改，正确做法是「改完回购物车改」，而不是在结算页开一个口子。

```vue
<tr v-for="i in checkInfo.goods" :key="i.skuId">
  <td><img :src="i.picture" /></td>
  <td>{{ i.name }}</td>
  <td>{{ i.attrsText }}</td>
  <td>¥{{ i.price }}</td>
  <td>× {{ i.count }}</td>
  <td class="red">¥{{ (i.price * i.count).toFixed(2) }}</td>
</tr>
```

**金额区。** 商品总额、运费、优惠、应付总额。四个数字都应该直接用接口返回的值，不要在页面上重算：

```vue
<p>商品件数：{{ checkInfo.summary.goodsCount }} 件</p>
<p>商品总价：¥{{ checkInfo.summary.totalPrice.toFixed(2) }}</p>
<p>运费：¥{{ checkInfo.summary.postFee.toFixed(2) }}</p>
<p>应付总额：<span class="red">¥{{ checkInfo.summary.payMoney.toFixed(2) }}</span></p>
```

这是第 10 章那条规矩的延伸：**派生值该由谁算，取决于谁能保证它正确**。购物车里「选中的合计」前端算没问题，因为数据都在前端；结算页的「应付」必须服务端算，因为优惠规则、运费模板、会员折扣都在服务端。

如果产品要求「应付金额」有个跳变动画，正确做法是前端做一个展示层的过渡，而不是自己算一遍再和服务端对账。

## 四、地址弹窗：v-model 控制与激活态

地址切换是一个弹窗，里面列出全部地址，点选一个，再点确定。

```vue
<el-button @click="showDialog = true">切换地址</el-button>

<el-dialog v-model="showDialog" title="切换收货地址" width="30%" center>
  <div
    v-for="item in checkInfo.userAddresses"
    :key="item.id"
    class="text item"
    :class="{ active: activeAddress.id === item.id }"
    @click="switchAddress(item)">
    <ul>
      <li><span>收货人：</span>{{ item.receiver }}</li>
      <li><span>联系方式：</span>{{ item.contact }}</li>
      <li><span>收货地址：</span>{{ item.fullLocation }}{{ item.address }}</li>
    </ul>
  </div>
  <template #footer>
    <el-button @click="showDialog = false">取消</el-button>
    <el-button type="primary" @click="confirmAddress">确定</el-button>
  </template>
</el-dialog>
```

三个状态，缺一个就会出错：

```js
const showDialog = ref(false)       // 弹窗开关
const activeAddress = ref({})       // 弹窗里高亮的那一项
const curAddress = ref({})          // 页面上真正生效的地址
```

**为什么必须三个？** 因为「高亮」和「生效」是两件事。只有两个状态时（比如点一下就改 `curAddress`），用户点错了想取消，`curAddress` 已经被改了——弹窗的「取消」按钮就没有意义了。

所以正确的流程是：**打开弹窗时把 `activeAddress` 初始化为 `curAddress`**，点击只改 `activeAddress`，确定时再把 `activeAddress` 赋给 `curAddress`：

```js
function openDialog() {
  activeAddress.value = curAddress.value
  showDialog.value = true
}

function switchAddress(item) {
  activeAddress.value = item
}

function confirmAddress() {
  curAddress.value = activeAddress.value
  showDialog.value = false
}
```

`el-dialog` 的 `v-model` 绑的是 `showDialog`，这个 prop 在 Element Plus 里是 `modelValue`，配合 `update:modelValue` 事件。所以 `v-model="showDialog"` 等价于「`:model-value="showDialog"` + `@update:model-value="showDialog = $event"`。理解这一点，就不会在「点了关闭按钮但 `showDialog` 没变」时以为组件有问题。

还有一个无障碍细节：列表项用 `div` + `@click` 时，键盘用户无法选中。要么用 `<button>` / `<input type="radio">`，要么补 `tabindex="0"` + `@keydown.enter`。课程版本没做，真实项目里这是无障碍审计的常见扣分项。

## 五、提交订单：请求体里该放什么

提交订单的请求体，是整个项目里字段最容易漏的地方：

```js
const createOrder = async () => {
  const res = await createOrderAPI({
    deliveryTimeType: 1,
    payType: 1,
    payChannel: 1,
    buyerMessage: '',
    goods: checkInfo.value.goods.map(item => ({
      skuId: item.skuId,
      count: item.count,
    })),
    addressId: curAddress.value.id,
  })
  const orderId = res.result.id
  router.push({ path: '/pay', query: { id: orderId } })
}
```

逐个字段看它的用途：

- `deliveryTimeType`：配送时段类型（如「仅工作日」「任意时间」）。默认值必须由产品定义，不能前端随手写 1。
- `payType`：支付方式（在线支付/货到付款）。这一页通常固定为在线支付，真正的渠道选择在支付页。
- `payChannel`：支付渠道（支付宝/微信）。这里传 1 只是占位，实际以支付页选择为准。
- `buyerMessage`：买家留言。可为空字符串，但不能是 `undefined`——有的后端会把它当必填校验。
- `goods`：**只传 `skuId` 与 `count`**，绝不能传价格。价格由服务端按当前价重新计算，这是防篡改的第一道门。
- `addressId`：当前选中的地址 ID，不是整个地址对象。

**为什么不能传价格？** 因为请求体在前端是可改的。用户装个浏览器插件就能把 `price: 199` 改成 `price: 1`。金额必须由服务端从数据库重新取，前端传过来的价格只用于展示，不参与结算。这是电商最基本的一条安全规则。

**`goods` 用 `map` 重新映射，而不是直接把 `checkInfo.goods` 传上去。** 因为 `checkInfo.goods` 里带着图片、名称、规格等一堆字段，全传上去会让请求体变大，也给了后端「误用前端字段」的机会。只传必要的两个字段，是接口契约的一部分。

## 六、幂等与重复提交：最容易被忽略的一步

用户手快，点两下「提交订单」，会生成两张订单。这不是理论问题，是真实项目里最常见的工单之一。

三道防线，从轻到重：

**第一道，按钮禁用。** 提交中禁用按钮，并显示 loading：

```js
const submitting = ref(false)

const createOrder = async () => {
  if (submitting.value) return
  submitting.value = true
  try {
    /* ... */
  } finally {
    submitting.value = false
  }
}
```

**第二道，请求幂等键。** 前端在进入结算页时生成一个 UUID，提交时放在请求头或请求体里：

```js
const idempotencyKey = crypto.randomUUID()

await createOrderAPI({ ...payload, idempotencyKey })
```

服务端收到同一个 key 的第二次请求，直接返回第一次的结果，不再创建新订单。这是支付、下单这类接口的标准做法，通常叫幂等令牌（idempotency token）。

**第三道，服务端去重。** 例如「同一用户 5 分钟内未支付订单不允许重复创建」，或「同一购物车快照只能生成一张订单」。这道防线在前端完全失效时仍然有效，是最后一道。

三道都要做，因为它们防的是不同的事：第一道防手抖，第二道防网络重试，第三道防恶意或异常。

还要注意一个侧面问题：**网络超时但订单其实创建成功了**。用户看到「提交失败」，又点了一次，于是有了两张订单。幂等键正是为这种情况准备的——第二次请求带着同一个 key，服务端返回第一次的订单 ID，用户被正常带到支付页。

## 七、从订单 ID 到支付页：query 与路由设计

创建成功后，页面跳到 `/pay?id=xxx`：

```js
router.push({ path: '/pay', query: { id: orderId } })
```

用 `query` 而不是 `params`，理由有三个：

- **可刷新**：`/pay?id=123` 刷新后参数还在；`params` 在刷新后会丢（因为它只存在于内存中的路由状态里）。
- **可分享/可回访**：用户从支付页失败后，客服发一条链接就能让他回到同一张订单。
- **可观测**：埋点、日志、错误上报里带上订单号，排查问题快得多。

为什么不用 `push` 而不用 `replace`？这里**应该用 `push`**——与登录页相反。因为用户从支付页按返回，回到结算页是合理的（他想改地址），虽然那张订单已经创建了。此时结算页需要处理「已有未支付订单」的情况，通常提示「您有一张待支付订单，是否继续支付？」，而不是再创建一张。

```js
// 支付页：用 replace 还是 push，取决于「返回」意味着什么
router.push(`/pay?id=${orderId}`)     // 允许返回结算页
router.replace(`/pay?id=${orderId}`)  // 不允许返回结算页
```

判断标准始终是同一个：**用户按返回键，应该看到一个有意义的页面，而不是一个会造成重复动作的页面**。结算页有意义（可以改地址再看一遍），所以 `push` 可以接受；支付页返回登录页没有意义，所以登录用 `replace`。

还有一点：`orderId` 来自服务端，是**不可信输入**的一种（虽然通常不可伪造）。支付页拿到它之后不能直接拼进任何 HTML，也不该用它做权限判断——权限校验必须在服务端，「这张订单是不是你的」由后端回答。

## 八、工程实践与常见坑

**第一，在 `onMounted` 里创建订单。** 用户每刷新一次就多一张订单。创建订单只能由明确的点击触发。

**第二，提交时把价格传给后端。** 前端可改，等于把定价权交给用户。

**第三，`buyerMessage` 传 `undefined`。** 部分后端会按必填校验直接 400。用空字符串兜底。

**第四，没处理「结算页没有商品」。** 用户直接访问 `/checkout` 看到一个空页面。应提示并跳回购物车。

**第五，默认地址没有兜底。** `userAddresses` 为空时 `curAddress.id` 是 `undefined`，提交直接 400。要三段兜底并禁用提交按钮。

**第六，切换地址改的是原地址簿。** 用户点「取消」回不去。选择状态要独立。

**第七，弹窗里只维护两个状态。** 「高亮」和「生效」混为一个，取消按钮失效。

**第八，提交按钮没有 loading。** 用户连点生成两张订单。

**第九，接口超时后没有幂等保护。** 用户重试导致重复下单。

**第十，金额在前端重算。** 优惠、运费、会员价任何一处不一致，都会变成「显示的金额和扣款不一样」。一律用接口返回值。

**第十一，商品列表用 `index` 作 `:key`。** 地址或商品顺序变化时出现错位渲染。用 `skuId` / `id`。
