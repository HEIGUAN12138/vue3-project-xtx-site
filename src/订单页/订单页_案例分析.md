# 订单页 · 案例分析

> 四个案例，分别对应本章四件「看起来是小事、出事都不小」的设计：预订单从哪来、为什么会重复下单、重复提交的历史解法、以及订单号暴露在 URL 里的代价。

## Case 1：结算页的「预订单」——从航空业的运价报价到今天的下单前校验

### 背景

1960 年，美国航空与 IBM 合作推出 Sabre 系统，第一次把机票的座位与运价放进实时系统里。它的核心能力不是「卖票」，而是**报价（fare quote）**：给定航线、日期、舱位，立刻算出价格与余票。这个动作必须在「出票」之前单独存在，因为价格随时在变，而旅客需要一个可以确认的报价。

今天的电商结算页，做的就是同一件事：先给一份报价（pre-order / checkout preview），用户确认后才生成真正的订单。

### 事件经过

航空公司很快发现两件必须分开的事：

- **报价是廉价的、可重复的。** 用户可以反复查价、改行程、再查价，系统不产生任何履约义务。
- **出票是昂贵的、不可重复的。** 一旦出票就占座、产生结算、进入退改流程。

把这两件事混在一起，会出现「每刷新一次就多一张票」。所以整个行业的标准做法是把「quote（报价）」与「book（预订）」拆成两个动作，且后者必须由一次明确的提交触发、带幂等保护。

电商的结算页与订单页，是这条链条的直接继承者：`/member/order/pre` 是 quote，`POST /member/order` 是 book。这也解释了本章第一节为什么强调「结算页的数据是从服务端预计算出来的」——它是报价，不是承诺。

### 与本章的关系

本章第二、三节的所有细节，都建立在这个分工上：结算页拿一份服务端算好的快照（含实时价格、运费、优惠），前端只负责展示；金额一律以接口返回为准，因为只有服务端知道当前的运价规则。

理解「报价 vs 预订」还有一个附带好处：你会自然明白为什么结算页要处理「商品已下架/库存不足」。报价的时候是可以失败的——它本来就是一次询问。如果结算页直接创建订单，这种失败就会变成「订单创建了但发不出货」的灾难。

### 参考资料

- [Sabre（computer system）](https://en.wikipedia.org/wiki/Sabre_(computer_system)) —— 1960 年代的实时订座与运价系统，报价与出票分离的历史起点。
- [Amadeus 开发者文档：Flight Offers Price](https://developers.amadeus.com/self-service/category/flights/api-doc/flight-offers-price) —— 现代 API 里「报价」是一个独立端点的直观例证。
- [Stripe 文档：Checkout Sessions](https://docs.stripe.com/api/checkout/sessions) —— 把「结算会话」与「支付」分成两个对象的工业设计。

## Case 2：幂等（idempotent）这个词，是从 HTTP 规范里来的

### 背景

1999 年，HTTP/1.1 的规范 RFC 2616 明确了方法的语义，其中一条是：`GET`、`HEAD`、`PUT`、`DELETE` 是**幂等（idempotent）**的，`POST` 不是。

「幂等」的数学含义是：同样的操作执行一次与执行多次，结果相同。放回 HTTP 语境里：`PUT /user/1 {name:"A"}` 调十次，用户还是叫 A；`POST /orders` 调十次，就会有十张订单。

2014 年的 RFC 7231 保留了这套语义，并把它写得更清楚：幂等性描述的是**服务端状态的效果**，而不是响应本身。

### 事件经过

问题在于，这个语义在 1999 年定下来的时候，大家默认「客户端不会重复发请求」。而移动网络、超时重试、用户连点，让「重复发送」成了常态。

2017 年前后，Stripe 公开并推广了 `Idempotency-Key` 这套做法：客户端为每一次「业务意图」生成一个唯一键，放在请求头里；服务端把键与第一次的结果一起存下来，之后收到同键请求就直接返回存下的结果。

```js
await createOrderAPI(payload, {
  headers: { 'Idempotency-Key': idempotencyKey },
})
```

这套做法后来被大量支付与订单系统采用，原因很朴素：**只有客户端知道「这是不是同一次意图」**。服务端看到的两个请求长得一模一样，无法判断是用户点了两次，还是网络重试了一次。把判断权交给生成键的一方，问题就解了。

代价也很明确：服务端要存键与结果（通常 24 小时），要处理「同键但请求体不同」的冲突（标准做法是返回 422），还要考虑键的存储与清理。

### 与本章的关系

本章第六节把幂等列为「第二道防线」，并强调它防的是「网络超时但其实成功了」这一类。这正是 RFC 7231 与 Stripe 实践共同指向的场景：`POST` 天生不幂等，而网络天生不可靠，所以必须由业务层补一个幂等键。

三道防线的分工也因此说得通：按钮禁用防手抖（客户端），幂等键防重试（协议层），服务端去重防绕过（业务层）。少了任何一道，都会留下一类特定的重复订单。

### 参考资料

- [RFC 7231：HTTP/1.1 Semantics and Content](https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2) —— 幂等性的规范定义，第 4.2.2 节。
- [Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests) —— 幂等键的完整用法，包括冲突处理与保留时长。
- [MDN：HTTP 请求方法](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Methods) —— 各方法的幂等与安全属性一览表。

## Case 3：重复提交这件事，Web 在 2004 年就给过一次标准答案

### 背景

在表单时代，用户提交订单后按 F5，浏览器会弹一句「是否重新提交表单」，然后真的再提交一次。这在 2000 年代初是电商的经典事故来源。

解法叫 **Post/Redirect/Get（PRG）**：表单 `POST` 成功后，服务端不直接返回结果页，而是返回一个 `302` 重定向到结果页的 `GET` 地址。这样浏览器地址栏停在一个 `GET` 页面上，刷新只是重新 `GET`，不会再提交。

### 事件经过

PRG 模式在 2004 年前后被写入 Web 开发的最佳实践，Ruby on Rails、Django、Spring MVC 等框架都把它做成了默认行为（Rails 的 `redirect_to` 几乎总是跟在 `create` 之后）。

它解决的不只是「刷新重复提交」，还顺手解决了三个问题：地址栏可收藏、结果页可分享、前进后退不会触发写操作。

到了 SPA 时代，这套思路以另一种形式保留了下来：

```js
// 提交成功后，路由替换/推进到一个「结果地址」，而不是停留在提交页
router.push({ path: '/pay', query: { id: orderId } })
```

地址变了，说明「提交」这个动作已经结束；刷新支付页只是重新拿订单详情，不会再创建订单。这就是 PRG 在单页应用里的等价物。

### 与本章的关系

本章第七节讨论「用 `push` 还是 `replace`」，本质上就是 PRG 的现代版本：**写操作结束后，必须把用户带到一个只读的地址上**。

如果提交成功后仍停在 `/checkout`，那么刷新、前进、后退都会回到一个「可能再次提交」的状态。这时候只能靠按钮禁用与幂等键兜底——而 PRG 的思路是把问题在路由层就消灭掉。

课程版本的实现是对的：提交成功后立刻 `router.push` 到 `/pay?id=xxx`。值得补上的一步是「回到 `/checkout` 时提示已有未支付订单」，否则用户在支付页按返回，会看到一份仍可提交的结算单。

### 参考资料

- [Wikipedia：Post/Redirect/Get](https://en.wikipedia.org/wiki/Post/Redirect/Get) —— 模式的由来、适用场景与现代变体。
- [MDN：HTTP 重定向](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Redirections) —— 302 与 303 的差别，以及为什么表单提交后该用 303。
- [RFC 7231：303 See Other](https://datatracker.ietf.org/doc/html/rfc7231#section-6.4.4) —— 「用 GET 去取结果」的规范定义。

## Case 4：订单号放在 URL 里，代价是什么

### 背景

把订单号放进 `/pay?id=12345` 是合理的设计：可刷新、可回访、可排查。但它同时把「一个资源标识」暴露给了用户。

如果服务端只用这个 ID 去查订单，而不校验「这张订单是不是当前登录用户的」，就构成了**越权访问（IDOR，Insecure Direct Object Reference）**。OWASP 在 2019 年把它单列为 API 安全的第一类风险，后来改称「对象级授权失效（BOLA, Broken Object Level Authorization）」。

### 事件经过

2019 年 5 月，安全记者 Brian Krebs 披露了美国第一美国金融公司（First American Financial）的一起泄露：其网站用递增的文档编号提供文件下载链接，任何人只要改一个数字，就能看到别人的保单文件——涉及约 8.85 亿份文件，时间跨度可追溯到 2003 年。

事件的技术本质极其朴素：**编号可枚举，且服务端没有校验归属**。没有 SQL 注入、没有零日漏洞，只有一个「直接引用对象」的 URL。

同年，OWASP API Security Top 10 把 BOLA 排在第一位，并在文档里写明：这是 API 最常见的漏洞，也是危害最大的一类，因为它不需要任何特殊技巧。

### 与本章的关系

本章第七节末尾那句提醒——「订单号到了前端就属于不可信输入，权限校验必须在服务端」——就是这条教训的浓缩版。

它落到代码上只有一句话，但必须写在服务端：

```js
// 错误：只按 ID 查
const order = await Order.findById(req.query.id)

// 正确：带上当前用户
const order = await Order.findOne({ id: req.query.id, userId: req.user.id })
```

前端能做的部分有三件：不要在页面上暴露其他用户的订单号（比如从列表接口里多返回了别人的数据）；跳转时不要拼接未经校验的参数；发现 403/404 时不要「静默重试」成别的 ID——那是把探测行为自动化了。
