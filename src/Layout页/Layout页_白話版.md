# Layout 页

> 这一章讲的是「一间商场怎么盖外壳」：外墙、扶梯、指示牌一次做好，里面的店铺换多少家都不用改。

## 一、Layout 的职责：一个壳子管住全站

逛商场时你注意过一件事：不管走进哪家店，门外的走廊、头顶的指示牌、脚下的地砖都是一样的。商场不会为了每家店重新铺一次地砖。

网站也一样。首页、分类页、详情页、购物车，它们的头部长得一模一样：一条导航、一个搜索框、一个购物车图标。如果每个页面各自复制一遍这套东西，改一次导航就要改十个文件，还容易出现「这个页面的头部比那个矮两像素」这种谁也说不清的问题。

Layout 就是这层外壳。它把大家共用的部分做好，中间留一块空地（`router-view`），路由决定往这块空地放哪个页面。首页放首页、分类页放分类页，外壳一动不动。

哪些页面不套这层壳？登录页、支付页、会员中心。判断标准很简单：**这个页面要不要顶部导航**。付款的时候不该让用户到处乱点，所以支付页整页自己排版，不套壳。

外壳里要分成几块？至少四块：导航、头部、底部、吸顶条。为什么不能写成一个文件？因为它们的变化节奏不同：导航内容来自后台、头部要显示购物车里有几件、底部基本不动、吸顶条有自己的出现时机。混在一起，改任何一块都要在一大坨代码里翻。

## 二、组件结构快速搭建：目录与插槽

放文件有个简单规矩：**只给一个页面用的，跟着那个页面走；两个以上页面都要用的，才放进公共组件库**。

Layout 的那四块，只有 Layout 自己用，所以就放在 Layout 的文件夹里。如果把它们塞进公共组件库，那个库很快会变成杂物间——什么都有一点，谁也不敢删，新人翻十分钟找不到自己要的。

外墙要不要留口子（插槽）？一般不要。每留一个口子，就多一个「这个页面为什么和别人不一样」的疑问。只有在明确需求时才留，比如某个品牌专区要在头部插一条横幅，那就留一个「横幅位」，别的页面不填就不显示。

布局用「竖着排」的方式最省心：头、内容、尾从上到下。有个细节一定要写：内容区要能「撑满剩下的高度」。不写的话，内容少的页面（比如空购物车）会把底部顶到屏幕中间，下半屏一大片空白。这是几乎所有项目都会踩一次的视觉 bug。

## 三、字体图标：为什么用 iconfont 而不是 svg 组件

导航上有几十个小图标：首页、分类、购物车、用户。做图标有三种老办法，可以拿刻章来类比。

第一种是**提前刻好一整套图案的印版**（雪碧图）：要换颜色就得重新刻一套，改一次设计重新走一遍流程，太笨。

第二种是**每个图案做成独立的贴纸**（SVG 组件）：质量最好，但每贴一张都要单独拿一次，而且换颜色得用专门的指令，团队里容易用得不一致。

第三种是**把图案做成字模**（字体图标）：就像打字一样，字号变大变小、换颜色，全都是改字体属性和颜色，一个文件装几十个图案，体积还小。小兔鲜选的就是这一种。

用的时候有三个小地方要注意。

第一，`<i>` 标签天生是斜的，图标会跟着歪，必须把它掰直。第二，每个图案对应一个「字」，这个字是从图标平台下载时抄来的，不要自己猜。第三，图标和文字并排时经常差一两像素，用「居中对齐」把它们的腰线对齐就好。

什么时候不该用字体图标？图案需要多种颜色、需要渐变、或者本身很复杂的时候。字模天生是单色的，这时候就得回到贴纸方案。

## 四、一级导航渲染：分类数据的消费方

导航上的分类不是写死的，是从后台拿的。流程三步：拿数据、挑出要显示的、排成链接。

这里有个产品决策藏在代码里：分类可能有二十个，但导航条放不下。代码里写「只取前九个」，看起来是个技术细节，其实是「导航上放几个」这个决定落在了代码里。如果不做这个决定，让样式去溢出隐藏，用户就会看到半个被切掉的分类。

导航高亮不需要自己写。页面跳转的链接组件有个自带本事：当前地址和它匹配时，会自动给它加一个标记类。你只要给这个类写个颜色，高亮就出来了。

但这里有个坑：它的匹配是「包含式」的。你访问「分类/101」，指向「分类」的那个链接也会被认为匹配，于是两个都亮。要精确匹配，得用专门的设置。

还有一个更重要的事：这份分类数据，不要在这里单独请求。因为导航要、分类页的侧边栏要、面包屑也要。三处各请求一次，就是三次白跑。这件事第六节专门讲。

## 五、吸顶交互：滚动监听与状态切换

往下滚的时候，导航条要贴在屏幕顶上；滚回顶部，它又滑回原位。小兔鲜的做法是准备一个「影子导航」，平时藏着，滚过某个高度就滑下来。

判断「滚了多远」用现成的工具（`useScroll`）就行，它会告诉你当前滚到哪了。我们的逻辑就是一句话：超过某个高度就显示。

写法上有两种。一种是把元素「抽出来」固定在屏幕上（`fixed`），另一种是让它「到边上就贴住」（`sticky`）。前者会把元素从原来位置拿走，下面的内容会往上跳一下，得额外补一块占位；后者保留原位置，滑下来更自然。小兔鲜选后者。

三个实现细节。

第一，那个「某个高度」是头部的实际高度，写死一个数字很容易出错，最好统一定义成常量。第二，滚动事件一秒钟能触发几十次，必须做「限流」，否则页面会卡。现成的工具内部已经处理了，自己手写就要记得加。第三，如果哪天吸顶突然不工作了，先去看它的外层容器——只要外层的祖先元素带了「变形」或「滤镜」这类样式，固定定位就会失效或错位。这是最难查的一类问题，因为代码一个字没改。

为什么吸顶条要复制一份结构，而不是直接用原来的头部？因为它们长得不一样：吸顶条更矮，只保留导航和搜索。硬要用一个组件加开关，组件里会塞满「如果是吸顶模式就……」的判断，改一处影响两处。复制结构、共用数据，更省心。

## 六、Pinia 优化重复请求：把请求搬到 store

三个人同时饿了，都想点同一家外卖。如果各打一个电话，店家要接三单、做三份。聪明的做法是：一个人打，其他人等他的结果。

分类数据就是这份外卖。导航要、分类页要、面包屑要。如果三处各写一次请求，用户从首页点到分类页，同一个接口被调了好几次。

改法分两步。第一步把请求搬进仓库（store），页面只管喊一声「我要分类数据」。仓库里加一句「如果已经有了，直接给」，第二个、第三个人就不用再打电话了。

第二步要解决一个更隐蔽的问题：**同时挂载**。首页和外壳几乎是同一瞬间渲染的，两边同时喊。这时候仓库里还是空的，第一个请求还在路上，第二个人一看「没有啊」，又打了一个电话。代码里那句「已经有了就返回」拦不住这种情况，因为「同时」意味着两个人都还没看到结果。

真正的解法是：把「正在进行的那个电话」记下来。后来的所有人都等这同一个电话的结果，打完再一起回家。这比「缓存结果」更实用，因为用户经常在数据还没回来时就点第二下。

还要留个后手：如果某个页面确实需要最新数据（比如后台改了分类），不能靠再喊一次，因为会被「已经有了」挡住。所以要单独提供一个「强制刷新」的入口，把「读」和「刷新」分开。

## 七、行为拆分：把滚动逻辑抽成 composable

第 2 章说过仓库负责「怎么拿数据」，页面负责「什么时候要」。这里多出第三类东西：**好几个页面都要复用的一段行为**。

它既不该进仓库（它不是全局数据），也不该抄进每个页面（会越抄越不一样）。这类东西单独放一个抽屉，叫「组合式函数」（composable）。

「滚到某高度就显示」就是典型。它内部要装监听、要提供结果、还要在页面离开时把监听拆掉。抽出来之后，任何页面想要这个效果，一行就够了。

判断一段逻辑该放哪，问三个问题：有没有跨页面共享的数据？有就进仓库。是不是纯算数、不碰外部？是就进工具文件夹。是不是「装上去就要记得拆」的东西（监听、定时器、订阅）？是就进组合式函数。

第三类最容易被写散。倒计时、图片懒加载、规格选择，都属于这一类。它们的共同点是：装的时候不清理，就会留下后患——用户离开页面了，定时器还在跑，内存一直涨。

有个关键细节：那个「页面离开时清理」的语句，必须写在函数里面，而且这个函数必须在页面初始化时就被调用。如果把它延迟到某个回调里才调用，那一刻页面已经初始化完了，清理就绑不上，东西永远不会被拆掉。

## 八、工程实践与常见坑

**一、底部浮在中间。** 内容少的页面下半屏一片空白。原因是内容区没有「撑满剩下的高度」。

**二、图标歪着。** 因为 `<i>` 天生斜体，要给它掰直。

**三、吸顶不动。** 先查外层容器有没有带变形或滤镜；再查滚动的是不是整个窗口；最后查是不是被别的层盖住了。

**四、两个导航同时高亮。** 链接的匹配是包含式的，要用精确匹配的设置。

**五、同一个接口请求好几次。** 请求写在了各个页面里。搬进仓库，并且记住「正在进行的请求」，而不是只记结果。

**六、滚动监听没拆。** 切页面后内存一直涨。能用现成工具就用，手写一定要「装了记得拆」。

## 一句话总结

Layout 就是商场的外壳：四块结构各管各的，只给一个页面用的东西跟着页面走；图标用字模省事；导航数据只请求一次，而且要连「正在路上的请求」一起记住；滚动这类「装了要记得拆」的行为，统一收进组合式函数，别散落在页面里。
