# 购物车 · 白话版

> 购物车是超市里的那辆推车。你往里放东西的时候没人管你，但结账前得知道车里有几件、哪些要买、一共多少钱。

## 一、购物车的三种状态：本地、接口、以及两者之间

逛超市有两种推车。一种是门口自取的实车，推着走；一种是手机上先加进「待购清单」，到店再提货。

实车就是**本地购物车**：数据放在你自己的浏览器里，不登录也能用。好处很实在——用户还没注册就能先把东西挑好，这是转化率最高的那批人。坏处也实在：换台电脑就没了，商家也没法给他发「你车里那件降价了」。

「待购清单」存在商家系统里，就是**接口购物车**：跨设备、能运营、能查库存，但前提是你得先有账号。

第三种情况才是麻烦：**两者之间**。绝大部分人的路径是「先往实车里放东西，然后去注册，回来发现车空了」。课程版本的做法是「登录后直接改用服务端的车」，于是本地那几件凭空消失——这不是 bug，是设计上就没做「合并」。

所以这一章要一直记着一句话：**换数据源不等于合并数据源**。

好在不管用的是哪辆车，收银员（组件）只认一套口令：「加一件」「减一件」「勾上」「全勾」。背后是数组还是接口，收银员不用知道。

## 二、加购：以 skuId 为唯一键

在超市里，你拿两盒一模一样的牛奶，收银员会算「2 盒」，而不是摆两个位置。购物车也一样：同一件东西再加一次，数量加一，不新增一行。

判断「是不是同一件」用什么？这里最容易错。想象一件 T 恤，有黑、白两色，各有 S、M、L。

- 用**商品编号**（`id`）判断，黑 M 和白 M 会被当成同一件，合成一行，数量变成 2。
- 用**规格编号**（`skuId`）判断，它们就是两件不同的东西，各占一行。

必须用 `skuId`。因为价格可能不同、库存各自独立、发货时仓库也要知道该拿哪一件。

还有一个细节：刚加进来的东西，默认该是**勾上的**。不然用户进购物车页，看到「已选 0 件、合计 ¥0」，第一反应是「我是不是没加上」，接着又点了一次。

最后是数量的兜底。详情页那边如果只传了「哪件」没传「几件」，数量加一就变成了「加了个 undefined」——界面上显示空白，而且**什么都不报错**。这种错误最难查，因为它不吵。所以加的时候要先把数量确认成一个正常的数字，没有就当 1。

## 三、头部购物车：一个 50px 的弹层与它的联动

头部那个小车图标，鼠标一放上去就弹出一层，像便利店门口的自动门：靠近就开，走开就关。

这个门**不用 JavaScript 控制**，纯靠 CSS 的 `:hover`：

```scss
.cart:hover .layer { opacity: 1; transform: none; }
```

用 CSS 的好处很实际：不用记「现在开没开」这个状态，不用处理「鼠标从图标移到弹层中间的缝隙」这种边角情况，也不用在页面关掉时清定时器。代价是手机上没有「hover」这回事，得另做一套「点一下展开」。

弹层上有两个数字很有意思：图标上的角标显示「几行」，下面的合计写「共几件」。

- 角标按行数算：用户觉得「我加了 3 样东西」。
- 合计按件数算：用户觉得「我买了 10 件」。

两个数字不一样是**故意的**，但它们都必须对。要是角标写 3、下面写 7，用户会以为算错了——哪怕两个都「没错」，只是口径不同。

弹层里每行有个删除的小叉。这个叉必须**自己处理掉点击**，不能让它继续往上冒——因为它待在一个「点击就跳转到详情页」的链接里。不拦，用户点删除，结果是既删了东西又跳走了页。这就是「事件冒泡」的经典事故。

## 四、列表购物车：一行表格里的四个决定

购物车页是一张表，可以想成超市小票：品名、单价、数量、小计、要不要。

四个格子，四件要拿定主意的事。

**第一个格子：勾选框。** 它不该直接绑到数据上，而应该「数据说她勾没勾，我来显示；我变了，我告诉外面」。这个区别听起来绕，理由却很实际：用户点一下，背后可能要发一次请求告诉服务器，直接绑数据就没有这个「中间环节」。

**第四个格子：数量。** 加号减号能改数，但不能一直加——上限得是**库存**。不然用户加到 999，结算时才被告知「只有 5 件」。这跟第 8 章讲的是同一句话：**能被提前预知的失败，不要留给用户去撞**。

**小计那一格：现算。** 就是单价乘以数量，别存。存了就要在每次数量变的时候记得更新，而「每次都记得」这件事，在多人协作的项目里从来不成立。

**空的购物车：要给出口。** 小票空白的时候，不能只写「空」两个字就完了。得有个「随便逛逛」的按钮，把用户送回货架前。**空购物车不是终点，是下一次挑选的起点。**

## 五、单选与全选：两个方向的状态同步

全选和单选，像教室里的灯：讲台一个总开关，天花板上一排灯。

**总开关按下 → 所有灯一起亮。** 这就是全选：遍历每一行，把它的勾选状态改成和总开关一样。

**所有灯都亮了 → 总开关该是亮的。** 这就是反方向：看是不是每一行都勾了，是就显示全选。

关键在那个「怎么算全选了」的判断上。代码里写的是「每一行都勾着」，看起来天衣无缝——但**空数组上空转一圈，结果是「是」**。也就是说，购物车是空的时候，全选框会自动变成勾上的。

用户看着一个勾着的框，旁边写着「购物车为空」，这画面很荒诞。所以判断得改成：「至少有一行，并且每一行都勾着」。

还有一条纪律：**总开关不自己记状态**。它只负责「按下时通知所有灯」，自己亮不亮由灯决定。要是它也自己记一个「我亮了」，就会出现「灯全灭了、总开关还亮着」这种自相矛盾——两份状态，必然有一次不同步。

## 六、统计：四个派生值

小票底部要写四个数字：共几件、共多少钱、已选几件、已选多少钱。

四个数字没有任何一个是「存」起来的，全是**当场算**出来的。理由和上一节一样：存就要同步，同步就会漏。

算的时候有三个容易翻车的点。

**第一，空车要能算。** 求和的写法如果没给「从 0 开始」这个起点，空数组直接就报错白屏——而空车正是最常见的状态之一。

**第二，别在算的时候就把钱格式化成两位小数。** 因为格式化完就变成文字了，文字加数字会拼接而不是相加：`12` 加 `"3.00"` 得到 `"123.00"`。格式化要在**显示的最后一步**做。

**第三，小数会飘。** `0.1 + 0.2` 不等于 `0.3`，这是所有用二进制表示小数的语言共有的毛病。表面上用「保留两位」能盖住，真正的解法是**后端用「分」当单位传整数**，前端只在显示时除以 100。这个决定要在项目一开始就定，后期改要动所有接口。

## 七、登录前后：同一份 store，两套数据源

上一节说「换车不等于合并车」，这一节说清楚为什么会掉东西。

用户的真实动作是：没登录时往车里放了三样 → 去注册 → 登录成功 → 回到购物车。这时候服务端的车是空的，而本地那三样还在硬盘上。程序如果只管「现在登录了，那就从服务器取」，取回来的自然是空车——本地三样东西并没有被删掉，只是**没人去看它们了**。

要做得对，就得在登录成功那一刻做一次「搬车」：把本地车里的东西一件一件放到服务端的车里，再以服务端的清单为准。

但一件一件搬有两个问题：一是东西多了要来回跑很多次；二是搬到一半断网，就变成「一半在车上、一半在地上」。工程上的解法是让商家提供一个**合并接口**：前端把整份本地清单一次性交上去，服务端负责去重、查库存、返回合并后的清单。一次请求，也就没有「搬一半」这回事。

还有一件必须做的事：**退出登录时要清空车**。不清的话，下一个在这台电脑上登录的人，会看到上一个人挑的东西。这不是体验问题，是数据泄露。

## 八、工程实践与常见坑

**一、删除删错了东西。** 「找到它在第几个」找不到时返回 -1，而「删掉第 -1 个」在 JS 里等于「删掉最后一个」。用户点第 1 行的叉，第 5 行消失了。修法是先判断「找到了没有」，或者干脆用「保留所有不是它的」这种写法。

**二、用商品编号合并。** 两个颜色合成一行，数量混在一起。

**三、新加的东西没有默认勾选。** 用户以为没加上，又加了一遍。

**四、数量成了 `NaN`。** 少传了数量，加上去变成「非数字」，界面空白且不报错。

**五、空车全选框是勾上的。** 因为「每一行都勾着」在空车时恒为真。

**六、金额算的时候格式化了。** 后面相加变成字符串拼接。

**七、求和不给起点。** 空车直接报错白屏。

**八、删除的叉没拦点击。** 既删了东西又跳走了页。

**九、数量没有上限。** 用户加到 9999，结算才被拒。

**十、退出登录不清车。** 下一个人看到上一个人的购物车。

**十一、本地存的旧数据缺字段。** 上线后给商品加了字段，老用户的本地数据里没有，渲染出一片空白。读取时要给字段兜底，或者做一次数据迁移。

## 一句话总结

购物车这一章真正要记的只有三句：**用 skuId 认东西、能算的绝不存、换数据源的那一刻必须想清楚「本地那些怎么搬过去」**——其余的坑，都是这三句话的边角料。
