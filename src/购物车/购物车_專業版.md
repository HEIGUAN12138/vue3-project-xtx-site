# 购物车

> 购物车是全站唯一一个「数据同时存在两个地方」的模块：未登录时在浏览器里，登录后在服务器上。这一章的全部复杂度，都来自这个分叉。

## 一、购物车的三种状态：本地、接口、以及两者之间

购物车在真实项目里有三种形态，理解这三者的差别，比记住任何一段代码都重要。

**本地购物车（local cart）**：数据只存在浏览器里，通常是 Pinia + 持久化。优点是不登录也能用，转化率最高的那批用户（先加购、再犹豫、最后注册）不会被拦在门外；缺点是换设备就没了，也无法参与「降价提醒」「库存校验」这类服务端能力。

**接口购物车（server cart）**：数据存在服务器上，以用户 ID 索引。优点是跨设备、可运营、可校验；缺点是必须有登录态，且每次增删都要打接口。

**两者之间**：绝大多数电商的做法是「未登录写本地，登录后上传并合并」。小兔鲜的课程版本只做了「按登录态切换数据源」，**没有做合并**——这是一个真实的取舍，也是本章第一节就要说清的事：切换不等于合并，切换会让用户在登录那一刻丢掉本地购物车。

代码层面，三种状态最终收敛到同一个 store 接口上：组件永远只调 `addCart`、`delCart`、`singleCheck`、`allCheck`，不关心背后是数组还是接口。这层抽象决定了后面所有讨论的前提：

```js
export const useCartStore = defineStore('cart', () => {
  const cartList = ref([])
  const userStore = useUserStore()
  const isLogin = computed(() => !!userStore.userInfo.token)

  return { cartList, isLogin }
}, { persist: true })
```

`isLogin` 用 `computed` 而不是独立 `ref`，是第 9 章留下的规矩：派生状态不要存，现算。

还有一个容易被忽略的问题：**「未登录」这个状态本身需要被识别**。如果 store 里同时存在 `cartList`（本地）和 `updateNewList()`（接口返回的列表），两个来源会写同一个字段，就会出现「登录后看到的还是本地的旧数据」。所以切换数据源时，必须有一处统一入口把服务端结果写回 `cartList`：

```js
const updateNewList = async () => {
  const { result } = await getCartListAPI()
  cartList.value = result
}
```

## 二、加购：以 skuId 为唯一键

加购的规则只有一句话：**同一个 skuId 只增数量，不新增行**。这句规则的实现依赖一个前提——商品详情页传过来的对象里必须带 `skuId`。

```js
const addCart = async (goods) => {
  const { skuId, count } = goods
  if (isLogin.value) {
    await insertCartAPI({ skuId, count })
    await updateNewList()
    return
  }
  const item = cartList.value.find(item => item.skuId === skuId)
  if (item) {
    item.count += count
  } else {
    cartList.value.push({ ...goods, selected: true })
  }
}
```

这里有三个决定值得展开。

**用 `skuId` 而不是 `id`。** `id` 是「商品」的标识，`skuId` 是「具体规格组合」的标识。同一件衣服的黑 M 与白 M 是两个 sku，价格可能不同、库存独立计算。用 `id` 合并会把两种颜色合成一行，用户改数量时根本不知道自己买的是哪件。

**用 `find` 而不是 `findIndex`。** 前者拿到对象引用后直接改属性，Vue 的响应式能追踪到（因为 `cartList` 是 `ref([])`，数组元素被代理）；后者拿到下标，还要再 `cartList.value[idx]` 一次，多一步且容易写错。

**新增项要补 `selected: true`。** 用户刚加进来的商品，默认应该是勾选状态，否则用户进了购物车页发现「合计 ¥0」，会以为加购失败。接口返回的数据通常自带这个字段，本地新增必须自己补。

`count` 的默认值也有讲究。详情页的数量选择器初始是 1，用户点「加入购物车」时传的是 `{ skuId, count: 1 }`；如果详情页传的是 `skuId` 而没传 `count`，`item.count += undefined` 会让数量变成 `NaN`——而 `NaN` 在界面上显示为空白，且不会报错。这类 bug 在真实项目里非常常见，防御方式是给参数兜底：

```js
const count = Number(goods.count) > 0 ? Number(goods.count) : 1
```

## 三、头部购物车：一个 50px 的弹层与它的联动

头部购物车是 `Layout` 里的一个小图标，鼠标悬停展开一层浮层。它的结构很简单：图标 + 数量角标 + 商品列表 + 合计 + 结算按钮。

```vue
<a class="curr" href="javascript:;">
  <i class="iconfont icon-cart"></i><em>{{ cartStore.cartList.length }}</em>
</a>
```

角标显示的是**行数**还是**件数**，是一个产品决定。显示行数（`cartList.length`）会让用户觉得「我只加了 3 件」，显示件数（`allCount`）会让用户觉得「我买了 10 件」。小兔鲜的角标用了行数，合计区用了件数——两个数字不一致是有意的，但它们必须都正确，否则用户会疑惑「为什么角标 3、下面写 10 件」。

浮层的展开靠 CSS `:hover`，不靠 JS：

```scss
.cart:hover .layer { opacity: 1; transform: none; }
.layer {
  opacity: 0;
  transform: translateY(-200px) scale(1, 0);
  transition: all .4s .2s;
}
```

用 CSS 而不是 `mouseenter/mouseleave` 的好处是：不需要维护 `visible` 状态、不需要处理「从图标移到浮层」中间的间隙、也不需要清理定时器。代价是移动端没有 hover，得另做一套点击展开——这是移动端先行的项目里很常见的一处返工。

**删除按钮必须阻止冒泡。** 浮层里每一项都包在 `<RouterLink>` 里，点删除图标如果不加 `.stop`，会同时触发跳转：

```vue
<i class="iconfont icon-close-new" @click.stop="cartStore.delCart(i.skuId)"></i>
```

这个坑在第 5 章 Home 页的轮播里出现过一次，这里是第二次。

## 四、列表购物车：一行表格里的四个决定

列表购物车是一张表：全选框、商品信息、单价、数量、小计、操作。四列各有各的坑。

**第一列，选择框。** 它不能用 `v-model="i.selected"`。原因不是「不能直接改 store」，而是**改完还要做别的事**——比如登录态下要调用接口同步服务端的选中状态。用 `:model-value` + `@change` 把「读」和「写」分开：

```vue
<el-checkbox :model-value="i.selected" @change="selected => singleCheck(i, selected)" />
```

**第四列，数量。** 课程版本直接用了 `v-model="i.count"`：

```vue
<el-input-number v-model="i.count" :min="1" :max="i.inventory" />
```

这在本地购物车下能跑，但它绕过了 action：登录态下服务端并不知道数量变了。正确做法是 `:model-value` + `@change` 走 store，由 store 决定「直接改」还是「调接口再刷新」。另外 `:max` 必须绑库存，否则用户能把数量加到 999，结算时才被后端拒绝——这是第 8 章 SKU 章节那条「不要把可预判的失败推给用户」的同一个原则。

**小计列。** 一定在渲染时算，不要在数据里存：

```vue
<p class="f16 red">&yen;{{ (i.price * i.count).toFixed(2) }}</p>
```

存一份 `subtotal` 到数据里，就要在每次数量变化时同步更新它，而「每次变化都记得更新」这件事，在多人协作里从不成立。派生值现算，是这一章反复出现的主题。

**空态。** 表格下面要有一行 `cartList.length === 0` 的空态，且这一行必须 `colspan="6"`，否则会挤在第一列里变形。空态里要有「随便逛逛」的出口，把用户送回首页——**空购物车是一段旅程的终点，必须给下一步**。

## 五、单选与全选：两个方向的状态同步

勾选这件事有两个方向，写错任何一边都会出现「全选后单个没勾」或「单个全勾了但全选框是空的」。

**方向一：全选框 → 所有单选框。** 一个 action 遍历：

```js
const allCheck = (selected) => {
  cartList.value.forEach(item => { item.selected = selected })
}
```

**方向二：所有单选框 → 全选框。** 这不是 action，而是计算属性：

```js
const isAll = computed(() => cartList.value.length > 0 && cartList.value.every(item => item.selected))
```

`length > 0` 这个判断不能省。空数组上 `every` 返回 `true`（数学上「对所有元素成立」在空集上恒真），于是**空购物车的全选框会是勾上的**，用户看着一个勾着的框和「购物车为空」并存，非常怪。

单向数据流在这里的体现是：`isAll` 不存、不可写，只由 `cartList` 算出；用户点全选框时只调 `allCheck`，然后 `isAll` 自然跟着变。如果给 `el-checkbox` 用 `v-model="isAll"`，Vue 会尝试给一个只读的计算属性赋值，控制台直接报错。

登录态下这两个动作都要同步服务端，接口参数是「skuId 数组 + selected」：

```js
const checkAllCart = async (selected, skuIds) => {
  await checkCartAPI({ selected, ids: skuIds })
  await updateNewList()
}
```

批量接口的关键是**一次请求改完所有行**，而不是循环发 N 个请求。后者在购物车有 30 件商品时会打出 30 次请求，且没有事务性——第 17 个失败时，前 16 个已经改了，界面与服务端不一致。

## 六、统计：四个派生值

购物车要显示四个数字：总件数、总金额、已选件数、已选金额。四个都是 `computed`：

```js
const allCount = computed(() => cartList.value.reduce((sum, i) => sum + i.count, 0))
const allPrice = computed(() => cartList.value.reduce((sum, i) => sum + i.price * i.count, 0))
const selectedCount = computed(() =>
  cartList.value.filter(i => i.selected).reduce((sum, i) => sum + i.count, 0))
const selectedPrice = computed(() =>
  cartList.value.filter(i => i.selected).reduce((sum, i) => sum + i.count * i.price, 0))
```

四个细节：

**`reduce` 的初始值必须写 `0`。** 不写时，空数组会抛 `TypeError: Reduce of empty array with no initial value`——而空购物车正是最常见的场景之一。

**先 `filter` 再 `reduce`**，不要写成 `reduce` 里判断 `selected` 再加。前者可读性更好，且两个语义（筛选、求和）分开表达；性能差异在这个数据量下可以忽略。

**金额不要在计算时 `toFixed`。** `toFixed` 返回字符串，`sum + '9.90'` 会变成字符串拼接。要在**渲染时**格式化：`allPrice.toFixed(2)`。这是 JS 里最经典的隐式类型转换坑之一。

**浮点误差要认。** `0.1 + 0.2 !== 0.3`，金额累加会出现 `19.900000000000002`。`toFixed(2)` 在展示层能盖住大部分问题，但真正的修复是**后端以分为单位传整数**，前端只在展示时除 100。这个决定必须在项目起步时定，后期改要动所有接口。

## 七、登录前后：同一份 store，两套数据源

第七节回到第一节的分叉。切换数据源的关键不是 `if/else`，而是**切换时机**。

用户的真实路径是：未登录加了三件 → 去登录 → 登录成功 → 回到购物车。此时本地那三件还在 `localStorage` 里，而 store 已经改从接口取数——三件商品凭空消失。课程版本的行为就是「消失」，因为它在登录后的第一次 `updateNewList()` 里把 `cartList` 整个覆盖掉了。

更完整的做法是在登录成功后做一次合并：

```js
// 登录成功后，把本地购物车逐条上传
const mergeLocalCart = async () => {
  const local = cartList.value.slice()
  for (const item of local) {
    await insertCartAPI({ skuId: item.skuId, count: item.count })
  }
  await updateNewList()
  cartList.value = cartList.value.filter(() => true)  // 触发一次视图同步
}
```

这段代码有两个明显的问题，正好用来说明「合并」为什么比「切换」难：一是逐条上传是 N 次请求，且中途失败会留下半份数据；二是本地商品可能已经下架或库存不足，上传会 400。工程上的做法通常是让**服务端提供一个合并接口**，前端把本地购物车整份 POST 上去，服务端负责去重、校验库存、返回合并后的列表——前端只发一次请求，也就没有「半份数据」的问题。

另一个细节是**退出登录**。退出时必须清空 `cartList`，否则下一个登录的人会看到上一个人的购物车——这是数据泄露，不是体验问题。

```js
const clearCart = () => { cartList.value = [] }
```

## 八、工程实践与常见坑

**第一，`splice(idx, 1)` 在 `idx === -1` 时删掉最后一项。** `findIndex` 找不到返回 `-1`，`splice(-1, 1)` 删除的是最后一个元素——用户在头部浮层点删除，删掉的却是另一件商品。修法：先判断 `if (idx > -1)`，或直接用 `filter`：

```js
cartList.value = cartList.value.filter(item => item.skuId !== skuId)
```

**第二，用 `id` 合并购物车。** 两个颜色被合成一行，数量加在一起。必须用 `skuId`。

**第三，新增项忘了 `selected`。** 用户加购后被送到购物车页，发现合计 ¥0，以为失败又加了一次。

**第四，`count` 为 `undefined`。** 详情页漏传 `count`，`item.count++` 得到 `NaN`，界面空白且不报错。

**第五，空数组上 `every` 返回 `true`。** 空购物车的全选框是勾上的。加 `length > 0`。

**第六，金额在计算属性里 `toFixed`。** 后续相加变成字符串拼接。

**第七，`reduce` 不写初始值。** 空购物车直接抛错，白屏。

**第八，删除按钮没加 `.stop`。** 点删除的同时跳转到详情页。

**第九，数量输入框没有 `:max`。** 用户可以加到 9999，结算时才被后端拒绝。

**第十，退出登录没清购物车。** 下一个登录的人看到上一个人的数据。

**第十一，持久化的旧数据结构。** 上线后给 `cartItem` 加了字段，老用户的 `localStorage` 里没有这个字段，渲染时 `undefined`。修法：读取时做一次版本迁移，或在 store 里给每个字段兜底。
