# 购物车 · 案例分析

> 四个案例，分别对应本章四件最容易出错的事：为什么必须允许游客加购、本地数据与服务端数据怎么接、负索引与 `NaN` 从哪来、以及钱为什么不能用浮点数算。

## Case 1：购物车为什么必须允许「不登录也能加」

### 背景

1990 年代中期，电商刚刚成型，主流做法是「先注册再购物」——网站需要用户 ID 才能把商品和人对上。1994 年 Netscape 发明 cookie 之后，技术上有了一条新路：给匿名访客发一个临时身份，先把购物车挂在临时身份上，等他真的下单时再要求注册。

### 事件经过

1998 年，Amazon 为一套「一键下单」流程申请了专利（US 5,960,411，1999 年授权）。专利的核心不是「点一下就买」，而是**把已保存的地址与支付信息绑定到用户身份上，让复购路径缩到一次点击**。同年 Barnes & Noble 上线了名为「Express Lane」的类似功能，Amazon 提起诉讼，1999 年双方和解，Barnes & Noble 调整了实现方式。

这场专利战把一件事钉在了行业共识里：**结算路径的长度直接决定成交率**。此后二十多年，「未登录也能加购」「登录后再合并购物车」成为电商的默认设计。

数据层面也有印证。Baymard Institute 汇总了数十份公开研究，长期统计的购物车放弃率（cart abandonment rate）稳定在 70% 左右——也就是说，每 10 个把商品放进车里的人，只有 3 个真正下单。「要求先注册」是其中被反复列出的主要原因之一。

### 与本章的关系

本章第一节把购物车分成「本地」与「接口」两种形态，正是这条行业共识的技术投影。本地购物车的存在理由不是「省一个接口」，而是**不让登录这道门挡在加购动作之前**。

理解了这一点，就能解释本章第七节为什么「切换数据源」是不够的：用户的真实路径是「先加购、后登录」，如果登录时不做合并，那三件商品就白加了——而这三件商品，正是转化率最高的那部分意图。

### 参考资料

- [Baymard Institute：Cart Abandonment Rate Statistics](https://baymard.com/lists/cart-abandonment-rate) —— 长期跟踪的弃购率数据与原因分布。
- [US 5,960,411：Method and system for placing a purchase order via a communications network](https://patents.google.com/patent/US5960411A/en) —— Amazon 一键下单专利原文。
- [RFC 6265：HTTP State Management Mechanism](https://datatracker.ietf.org/doc/html/rfc6265) —— cookie 的现代规范，理解「匿名身份」是怎么被记住的。

## Case 2：本地购物车与服务端购物车之间的那道缝

### 背景

2000 年代的购物车几乎都是纯服务端的：每加一件就打一次接口，数据存在数据库里，靠 session 认出是谁。这条路在「未登录」时也得走——服务器会创建一个匿名 session，等用户登录后再把匿名 session 的购物车挂到账号上。这个「挂过去」的动作，就是最早的购物车合并。

2010 年代前后，前后端分离与 `localStorage` 普及，前端开始自己存一份购物车。好处是加购零延迟、断网也能操作；代价正是本章反复提到的那个缝：**同一份购物车，同时存在两个地方**。

### 事件经过

行业里演化出三种合并策略，各有各的代价。

**其一，登录时逐条上传。** 前端把本地每一件 POST 一次，然后拉取服务端列表。实现最简单，问题是 N 次请求，且中途失败会留下「一半在服务器」的状态。

**其二，登录时整份提交，服务端合并。** 前端把本地购物车序列化成一次请求，服务端负责去重（同一个 skuId 数量相加或取大）、校验库存与上下架、返回合并后的完整列表。这是主流电商的做法——把「合并」这件复杂事放在有事务能力的一侧。

**其三，不做合并，直接丢弃本地。** 课程版本就是这个策略。它简单、可预测，代价是用户会疑惑「我刚才加的东西呢」。很多项目在早期都这么干，等到弃购数据不好看时才补上合并逻辑。

还有第四个问题常被漏掉：**退出登录时要不要清空**。不清的话，同一台设备换个人登录，就会看到上一个人的购物车。这不是体验瑕疵，是数据泄露——2020 年前后多起「共享设备泄露购物车/浏览记录」的投诉，都属于这一类。

### 与本章的关系

本章第七节的两段代码，一段演示「逐条上传」为什么不够好，一段演示「退出清空」为什么不能省。这一节把它们放进历史脉络里：合并策略的选择不是技术品味，而是**对「用户在哪个时刻可能丢数据」的判断**。

判断依据可以压缩成一句：合并必须是一次有事务性的操作，因此它属于服务端；而「什么时候发起合并」属于前端，答案永远是「身份发生变化的那一刻」。

### 参考资料

- [RFC 6265：HTTP State Management Mechanism](https://datatracker.ietf.org/doc/html/rfc6265) —— 服务端会话与匿名身份的基础。
- [MDN：Window.localStorage](https://developer.mozilla.org/zh-CN/docs/Web/API/Window/localStorage) —— 本地存储的能力与限制（同源、同步阻塞、约 5MB）。
- [OWASP：Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) —— 会话切换时必须做什么，「换人登录要清状态」的理论依据。

## Case 3：`-1` 与 `NaN`——两个 1985 年前后的决定如何在购物车里咬你

### 背景

1985 年，IEEE 发布 754 浮点运算标准，定义了 `NaN`（Not a Number）与「`NaN` 不等于自身」这条规则。同年之后的三十多年里，它成了几乎所有语言的默认行为。

关于负数索引，则是另一条线：JavaScript 的 `Array.prototype.splice` 沿用了「负下标从末尾数」的约定，`splice(-1, 1)` 表示「删掉最后一个」。这条约定在字符串与数组 API 里反复出现，方便了切片，也埋了雷。

### 事件经过

购物车删除的实现，教科书式写法是：

```js
const idx = cartList.value.findIndex(item => item.skuId === skuId)
cartList.value.splice(idx, 1)
```

`findIndex` 找不到时返回 `-1`。于是 `splice(-1, 1)` 删掉了**最后一个元素**——用户点了第 1 行的叉，第 5 行消失。

这条 bug 的可怕之处在于它**不会报错**，而且只在「找不到」时触发：重复点击、并发请求后数据已被刷新、`skuId` 类型不一致（`1` 与 `"1"`），都会让 `findIndex` 返回 `-1`。

`NaN` 的路径类似。详情页如果漏传 `count`：

```js
item.count++          // undefined++ → NaN
```

`NaN` 参与任何算术都得 `NaN`，显示在界面上是空白字符串，`toFixed(2)` 返回 `"NaN"`，也不抛错。而 `NaN !== NaN`，所以 `if (item.count === NaN)` 这种校验永远为假——必须用 `Number.isNaN()`。

### 与本章的关系

本章第八节的前四个坑，全部是这两条底层规则的投影：`splice(-1)` 删错行、`findIndex` 不判 `-1`、`count++` 得到 `NaN`、`Number(undefined)` 得到 `NaN`。

修法都很短，但值得记住的是**它们为什么会发生**：负数索引的语义是语言给的，`NaN` 的传染性是 IEEE 754 给的，两者都不会因为「业务上不可能」而消失。防御方式是在边界处显式校验——`if (idx > -1)`、`const count = Number(goods.count) > 0 ? Number(goods.count) : 1`。

- [MDN：Array.prototype.splice](https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Reference/Global_Objects/Array/splice) —— 负索引的处理方式，官方写得很明确。
- [MDN：NaN](https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Reference/Global_Objects/NaN) —— 「`NaN` 不等于自身」以及 `Number.isNaN()` 的用法。
- [IEEE 754-2019 标准页](https://standards.ieee.org/ieee/754/6210/) —— 浮点运算标准的现行版本，`NaN` 的出处。

## Case 4：钱为什么不能用浮点数算

### 背景

IEEE 754 用二进制表示小数，而 0.1 在二进制里是无限循环小数。因此 `0.1 + 0.2` 得到 `0.30000000000000004`，`19.9 * 3` 得到 `59.699999999999996`。这不是 JavaScript 的毛病，C、Java、Python 都一样。

1982 年，温哥华证券交易所（Vancouver Stock Exchange）上线了一个新的指数计算程序。指数初始值定为 1000.000，程序在每次迭代后把结果截断到三位小数。问题在于它把 1000.000 截成了 1000——看起来只是少了三个零，实际每次迭代都在丢精度。

### 事件经过

指数从 1000 点开始运行，一路下跌。起初没人觉得异常，因为市场确实在跌。等到 1983 年 11 月有人复核时，指数已经跌到 524.81，接近腰斩。真正的市场跌幅远没有这么夸张——**指数凭空蒸发了约一半的市值**。

修复花了很长时间：程序改回正确的截断逻辑后，指数不是「弹回去」，而是要重新计算历史数据、逐步校正，前后耗时约两年。这个事件后来被反复引用在「浮点数与金融计算」的教材里。

工程上的标准解法不是「用更高精度」，而是**根本不用小数**：

- 后端以「分」为单位传整数（1990 元记作 `199000`），前端只在渲染时除以 100。
- 或者用定点小数库（如 `decimal.js`、`big.js`），代价是每次运算都要包一层。
- 货币的最小单位由 ISO 4217 定义：人民币与美元是 2 位，日元是 0 位，科威特第纳尔是 3 位——**「除以 100」这个假设本身都不是通用的**。

### 与本章的关系

本章第六节的四个统计值里，`allPrice` 与 `selectedPrice` 都是金额。课程版本用 `toFixed(2)` 在渲染层盖住了误差，这在教学项目里够用；但第八节仍然把它列为坑，因为**一旦金额参与业务判断**（比如「满 199 减 20」），浮点误差就会变成「差一分钱不满足条件」的真实事故。

同一节的另一条规矩——「不要在计算属性里 `toFixed`」——也来自这里：`toFixed` 返回字符串，`sum + '9.90'` 会变成拼接，那就不只是精度问题，而是类型问题了。
