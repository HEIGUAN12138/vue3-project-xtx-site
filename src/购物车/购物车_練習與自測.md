# 购物车 · 练习与自测

> 题量：是非 10 / 选择 10 / 配对 8 / 情境 3 / 代码阅读 3 / 延伸思考 2。答案紧跟各区块。

## 一、是非题（10 题）

1. 购物车合并商品时应该用商品的 `id` 作为唯一键。
2. 新加入购物车的商品默认应该处于勾选状态。
3. 空数组调用 `every` 返回 `false`。
4. 头部购物车的角标数量与合计件数必须严格相等。
5. `reduce` 不传初始值时，空数组会抛错。
6. 金额可以在计算属性里直接 `toFixed(2)`，不影响后续计算。
7. 数量输入框的 `max` 应该绑定当前 SKU 的库存。
8. 登录后如果不做合并，未登录时加入的本地购物车会消失。
9. 退出登录时不需要清空本地购物车。
10. `findIndex` 找不到元素时返回 `0`。

### 答案解析

1. **错**。`id` 是商品标识，`skuId` 才是具体规格组合的标识，用 `id` 会把不同颜色/尺码合成一行。
2. **对**。否则用户进购物车页看到「已选 0 件、合计 ¥0」，会以为加购失败。
3. **错**。返回 `true`——「对所有元素成立」在空集上恒真。所以全选判断必须加 `length > 0`。
4. **错**。角标通常按行数、合计按件数，两者口径不同，但各自都必须正确。
5. **对**。`TypeError: Reduce of empty array with no initial value`。
6. **错**。`toFixed` 返回字符串，后续相加会变成字符串拼接。
7. **对**。否则用户能把数量加到远超库存，结算时才被拒。
8. **对**。`updateNewList()` 会整个覆盖 `cartList`，本地那几件就没人看了。
9. **错**。不清会使下一个登录的人看到上一个人的购物车，属于数据泄露。
10. **错**。返回 `-1`，而这个值直接传给 `splice` 会删掉最后一项。

## 二、选择题（10 题）

   A. `selected: true`　B. `count: 0`　C. `subtotal`　D. `checked`

   A. `cartList.every(i => i.selected)`　B. `length > 0 && every(...)`　C. `some(...)`　D. `filter(...).length`

4. 全选框在空购物车时被自动勾上，原因是？
   A. 组件 bug　B. 空数组上 `every` 返回 `true`　C. 默认值写错　D. CSS 样式问题

5. `selectedCount` 的语义是？
   A. 购物车行数　B. 已勾选商品的件数之和　C. 商品种类数　D. 库存总数

6. 金额格式化（保留两位小数）应该放在？
   A. 数据存储时　B. 计算属性里　C. 渲染时　D. 接口请求前

7. 头部购物车浮层用 CSS `:hover` 展开的主要代价是？
   A. 性能差　B. 移动端没有 hover　C. 无法美化　D. 与路由冲突

8. 登录后切换数据源最容易被忽略的一步是？
   A. 拉取接口列表　B. 合并本地购物车　C. 清空本地存储　D. 刷新页面

9. `item.count++` 且 `count` 为 `undefined`，结果是？
   A. 0　B. 1　C. `NaN`　D. 抛错

10. 批量修改勾选状态时，正确做法是？
    A. 循环发 N 个请求　B. 发一个批量接口　C. 只改本地　D. 让用户逐个点

### 答案解析

1. **B**。价格与库存都绑在 SKU 上。
2. **A**。接口返回的数据通常自带，本地新增必须自己补。
3. **B**。`A` 在空数组上返回 `true`，是经典错误。
4. **B**。数学上「空集上全称命题为真」。
5. **B**。是 `filter` 后 `reduce(count)`，不是行数。
6. **C**。在计算里格式化会把数字变成字符串。
7. **B**。触屏没有悬停状态，需要另做点击展开。
8. **B**。切换只是换数据来源，合并才保住用户已有的加购。
9. **C**。`undefined` 参与算术得 `NaN`，界面显示空白且不报错。
10. **B**。循环发 N 个请求没有事务性，中途失败会导致前后端不一致。

## 四、情境分析（3 题）

### 情境 1：点第一行的删除，第五行消失了

用户在购物车页点第一行的「删除」，刷新后发现自己想买的那件还在，第五行（正好是他不想要的那件）没了。

**问**：原因与修法。

**答**：`findIndex` 返回 `-1`（`skuId` 类型不一致或数据已被并发刷新），`splice(-1, 1)` 删掉了最后一项。修法是先判断 `if (idx > -1)`，或改用 `filter(item => item.skuId !== skuId)` 整体替换数组。更根本的做法是在页面上用行内唯一键（`skuId`）作为 `:key`，避免复用错位。

### 情境 2：登录之后，购物车空了

用户在未登录状态下加了三件商品，去登录，回到购物车，发现一件都没有。

**问**：原因、以及「修到什么程度算够」。

**答**：登录后 store 改走接口，`updateNewList()` 用服务端返回的空列表覆盖了 `cartList`，本地那三件还在 `localStorage` 里但没人读。最小修法是在登录成功后先读本地列表、逐条上传、再拉取服务端列表；更稳的修法是让服务端提供合并接口，前端一次提交、服务端负责去重与库存校验。判断标准是：用户登录前后的「已选件数」不应减少。

### 情境 3：合计金额显示 ¥0.00，但用户明明勾了商品

用户勾了两个商品，单价 9.9 和 19.9，页脚合计显示 `¥0.00`。

**问**：两种可能原因。

**答**：一是 `selected` 字段不存在（本地新增时忘了补、或接口字段名不同），`filter(i => i.selected)` 结果为空；二是 `price` 是字符串（接口返回 `"9.90"`），`sum + '9.90'` 变成字符串拼接，再被 `toFixed` 处理成 `NaN` 或 `0.00`。排查顺序：先打印 `cartList`，确认字段名与类型，再确认 `filter` 结果长度。

## 五、代码阅读（3 题）

### 题 1

```js
const delCart = (skuId) => {
  const idx = cartList.value.findIndex(item => item.skuId === skuId)
  cartList.value.splice(idx, 1)
}
```

**问**：什么情况下会删错商品？如何改？

**答**：`skuId` 不存在时 `idx` 为 `-1`，`splice(-1, 1)` 删除最后一项。改法：

```js
const delCart = (skuId) => {
  cartList.value = cartList.value.filter(item => item.skuId !== skuId)
}
```

用 `filter` 的好处是「找不到就什么也不做」，天然幂等。

### 题 2

```js
const allPrice = computed(() =>
  cartList.value.reduce((sum, i) => sum + i.price.toFixed(2) * i.count, 0))
```

**问**：两个问题。

**答**：一是 `toFixed` 返回字符串，`sum + '9.90'` 会做字符串拼接（此处再乘 `count` 会得到 `NaN`）；二是没有处理空数组以外的情况——初始值 `0` 写了，这点是对的。正确写法是 `sum + i.price * i.count`，格式化留到渲染层：`{{ allPrice.toFixed(2) }}`。

### 题 3

```js
const addCart = (goods) => {
  const item = cartList.value.find(item => item.skuId === goods.skuId)
  if (item) item.count++
  else cartList.value.push(goods)
}
```

**问**：这段代码在「已登录」时会出什么问题？还缺什么？

**答**：已登录时应调用 `insertCartAPI` 并刷新服务端列表，否则刷新页面后加购丢失。此外：新增项没有补 `selected: true`；`goods.count` 可能不存在，`item.count++` 会得到 `NaN`；`goods` 直接 `push` 会把外部对象引用塞进 store，外部改动会连带影响购物车（应浅拷贝 `{ ...goods }`）。

## 六、延伸思考（2 题）

1. 「本地购物车」与「服务端购物车」各自的成本在哪里？如果你只能选一种，会怎么选，为什么？

   **思路**：本地的成本在「跨设备不可用、无法运营、无法校验库存」，收益是零登录门槛与零延迟；服务端的成本在「登录门槛、每次操作一次请求、离线不可用」，收益是可运营、可校验、跨端一致。只能选一种时，看业务阶段：冷启动期转化优先，选本地；有复购与营销需求后必须转服务端，并把本地作为「离线缓冲」。真正的答案通常是「两者都要，但合并策略要提前设计」。

2. 购物车的金额计算，前端算与服务端算各有什么风险？你会把「合计」交给谁？

   **思路**：前端算的优点是即时反馈，风险是精度、优惠规则、并发改价导致与服务端不一致；服务端算的优点是唯一真相，风险是多一次请求、界面出现「先显示后跳变」。合理分工是：前端用「分」为单位做展示级合计（乐观更新），下单时以服务端返回的金额为准，并在金额不一致时提示用户「价格有变动」而不是静默替换。判断依据是「谁承担错误金额的后果」——如果是钱，就必须服务端说了算。

## 自测标准

- 能说清本地购物车与接口购物车的分叉，以及登录时为什么必须考虑合并：合格
- 能正确实现加购、删除、单选、全选与四个统计值，并避开 `-1` 与 `NaN`：良好
- 能解释金额精度问题的来源与工程解法，并把「派生值不存」贯彻到所有统计上：优秀
