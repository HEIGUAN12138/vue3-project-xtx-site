# Pinia 入门

> 这一章讲的是「数据放在哪里，才能让很多页面一起用」，全程不写复杂代码，先把道理说通。

## 一、为什么是 Pinia：Vuex 之后的官方选择

想象一家老式单位食堂。你想多要一勺饭，不能直接跟打饭阿姨说，得先填一张申请表，交给组长签字，组长再转给食堂主任，主任批了阿姨才给。这张申请表就是 Vuex 里的 `mutation`，组长是 `action`，阿姨是 `state`。规矩是有了，但你只是想多一勺饭。

Pinia 把三道窗口拆了，改成自助餐。你端着盘子自己走到菜前面，想拿什么拿什么。收银台（DevTools）照样盯着你，谁拿了什么都有记录，只是不用再递申请表了。

这个区别在小项目里感觉不出来，但在电商项目里差别很大。加入购物车要做三件事：同一个商品数量加一、否则新增一行、金额重新算。用老式食堂的办法，这三件事要拆进两个文件夹、写三张表。用自助餐，你写一个函数就完了。

要说清的一点是：Pinia 不是 Vuex 的新版本，是重做了一遍。Vuex 里那种「所有修改必须走一道手续」的可靠感，Pinia 换了个方式给你——不是不许你改，而是你改了之后记账 App 会自动记下来，还标出是哪一步改的。规矩从「代码里管着你」变成了「工具里看着你」。

## 二、安装与注册：app.use(pinia) 之后发生了什么

开店有个顺序：先装修、再装收银台、最后才挂「营业中」的牌子。装 Pinia 就是装收银台，必须在开门迎客之前完成。如果先挂了营业牌子（`app.mount`）再去装收银台，第一批客人（组件）冲进来要结账时就会发现没有收银台，当场卡住。

报错信息叫 "getActivePinia was called with no active Pinia"，翻译过来就是「结账的时候找不到收银台」。看到这句话，九成的情况是把 `app.use(createPinia())` 写在了 `app.mount()` 后面，或者干脆忘了写。

`createPinia()` 还悄悄做了一件事：它给整个仓库配了一个「总电闸」。以后所有跟着 Pinia 走的自动计算、自动监听，都接在这一个电闸下面。哪天你要把整个应用关掉（`app.unmount`），拉一下总闸，所有接在上面的设备一起停，不会留下几个还在偷偷耗电的。如果是做服务端渲染，每个用户都要发一个自己的仓库，否则张三的购物车会跑到李四的页面上——这就是为什么它非得给你一个「总电闸」而不是全局单例。

还有个小知识：你在文件里写 `defineStore`，并不等于现在就造了一个仓库，只是登记了「我们有这么一种仓库」。真正的仓库是组件第一次喊「我要用」的时候才建的。所以就算很多文件互相引用，也不会一开机就打架。

## 三、定义 store：defineStore 的两种写法

每个仓库都得挂个工号牌，这个牌子上写的字就是 `defineStore` 的第一个参数。工号牌必须全世界唯一。如果两个仓库挂了同样的工号，系统会以为它们是同一个人，你打开自己的柜子，里面放的却是别人的东西——症状是「我明明没动过这个数据，它怎么变了」。

仓库有两种装修风格。第一种叫「选项式」，一个抽屉放数据（`state`），一个抽屉放自动计算（`getters`），一个抽屉放动作（`actions`），和老式食堂的布局很像，从 Vuex 搬过来的人会觉得亲切。

第二种叫「组合式」，就是一个普通的函数：要数据就写 `ref`，要自动计算就写 `computed`，要动作就写普通函数，最后把它们一起交出去。它最大的好处是能直接借用在别处写好的现成工具，比如「滚动到底部才加载」的那个工具函数，拿来就能用。

有一种错误特别常见：把 `state` 写成一坨现成的数据，而不是一个「每次调用都新发一本账本」的函数。写成现成的，就等于全公司共用一本账，两个人同时记账必然串号。所以规矩是 `state: () => ({ ... })`，每次要账本就新发一本。

一个项目里两种风格混着用完全没问题。小兔鲜就是用户仓库用选项式、分类仓库用组合式，各自顺手就行，不用非得统一。

## 四、state 的读写：直接改、$patch 与 $reset

仓库里的数据有两种改法：改一个抽屉，或者说「这几样一起改」。

改一个，直接赋值就行，跟在自家改 `ref` 一样自然。这在老式食堂里是绝对不允许的，必须走手续；Pinia 里可以，因为你改完总会有记录。

要一次改好几样，用 `$patch`。可以递一张写着「这几栏改成什么」的单子，也可以递一个「你自己按这几栏去改」的说明。递单子的好处是只触发一次刷新，不会出现「改了名字还没改头像」的中间状态被页面看到。

还有一种叫 `$reset`，可以理解成「把账本撕了重发一本空白的」。退出登录的时候最有用：一键把登录状态、用户信息全清掉，不用一个一个手动抹，省得漏掉哪个字段留下后患。

但这里有个坑必须知道：只有第一种风格（选项式）的仓库自带 `$reset`，第二种风格（组合式）没有。你去调它，会报「没有这个方法」。组合式想要重置，得自己写一个函数，把每样数据挨个赋回初始值。

还有个更隐蔽的坑：如果你给仓库接了「自动存到浏览器本地」的插件，`$reset` 只清内存里的账本，不清本地备份。表现为你明明退出登录了，刷新一下又变成登录状态。这时候要在重置之后额外把本地存储也清一遍。

## 五、getters：派生状态与缓存

仓库里有一类东西叫「推出来的答案」，不用单独存，随时能算。购物车总金额就是典型：它由「勾选了哪些」「每样多少钱」「买几个」推出来，你不需要在某个地方单独记一个「总金额」变量。

`getters` 就是干这个的，本质上是一台体重秤。体重秤有三个特点：放上去才读数、同一个状态不用反复称、只告诉你结果不管你怎么吃。对应过来就是：用到时才计算、结果会缓存、不许在里面偷偷改数据或发请求。

缓存这件事很实惠。购物车页面上，总金额要显示在结算按钮、底部汇总栏、优惠提示三个地方。如果没有缓存，每显示一次就重新把所有商品乘一遍加一遍；有了缓存，只在商品或勾选状态真的变了才重算。

要特别注意一种写法：让 `getters` 返回一个函数，比如「按 id 找某个商品」。这种写法看起来很方便，但缓存就失效了，因为每次调用都是一个新函数，体重秤认不出这是同一个读数。找商品这种小事没关系，但如果里面还有累加计算，就不该这么写。

`getters` 最大的价值其实不是省代码，而是「钱只有一个算法」。购物车页、订单页、支付页读的是同一台秤，就不会出现「购物车显示 199，付款时变成 189」这种事。凡是把算钱逻辑抄到好几个页面的项目，最后都会花大量时间查这种差价。

## 六、action：同步、异步与职责边界

`actions` 就是仓库里的「动作」，比如「去把用户资料取回来」「把商品加进购物车」。它和普通函数没什么区别，可以是立刻做完的，也可以是等一会儿才做完的（比如等网络返回）。

以前在 Vuex 里调一个动作要 `dispatch('xxx')`，像喊一句暗号。Pinia 里直接喊名字就行：`store.xxx()`，跟在组件里调自己方法一模一样。

等一会儿才做完的动作有个好处：它能直接把结果交给你。比如「去取用户资料」，取回来之后你当场就能拿到，不用再去仓库里翻一遍。这让组件写起来更像普通的异步函数。

动作之间还能互相串门。购物车要结算，得先问用户仓库「登录了没」，这在动作里直接问就行，不用绕出去。但有个顺序上的死规矩：这个「问」必须写在动作里面，不能写在整个文件的最外面。写在最外层，等于仓库还没建好就跑去问，必然报错——而且报错信息很含糊，很难一眼看出问题在哪。

怎么分工才不打架？记住一句话：**动作负责「把货补满」，页面负责「什么时候需要补货」**。动作只管怎么从服务端拿、拿完放哪；至于「进页面时要拿」，那是页面自己的事。这样同一个动作能被首页、分类页、详情页一起用。

这正好解释了小兔鲜的一个优化：为什么打开好几个页面，分类数据只请求了一次？因为「取分类」这个动作里加了一句「如果仓库里已经有了，直接给，不再跑一趟」。三个页面喊的是同一个动作，实际只出门了一趟。

## 七、storeToRefs：为什么不能直接解构

这是全章最容易栽跟头的地方，用一个比喻说清楚。

仓库里挂着很多块「实时显示屏」，上面滚动着最新数字。你站在屏幕前看，数字变了你就看到新数字。但如果你掏出手机**给屏幕拍了张照片**，照片上的数字就永远定格在拍摄那一刻了。

`const { token } = userStore` 这句就是拍照。你把 `token` 从这个盒子里拿出来的时候，取的是当时的值，一个普通字符串；之后仓库里的 `token` 换成新的，你手里那张「照片」不会变，页面自然也不更新。这就是「改了数据但界面没反应」的根因。

正确的做法是装一台「实时摄像头」：`storeToRefs`。它不给你拍照，而是给你一条通往屏幕的专线，屏幕上是几你就是几。所以读取数据和自动计算出来的值，要用它包一下。

另一类东西不需要包：动作。动作是「你会做的某件事」，不是「墙上的数字」，包成实时摄像头毫无意义，而且包了之后直接调用还会出错。所以规矩是——数据和计算结果用 `storeToRefs`，动作直接拿。

还有个更省事的写法：如果你只想看一两个字段，干脆别拆，在模板里直接写 `userStore.token`。这本身就是实时显示，天然会跟着变。只是字段一多，模板里到处是 `userStore.` 会比较啰嗦，那时候再用 `storeToRefs`。

## 八、工程实践与常见坑

**一、把账本写成公用的。** 两个人看到同一份数据、互不影响的需求失效了。原因是 `state` 写成了现成对象。记住每次新发一本账本：`state: () => ({})`。

**二、在文件最外层就跑去问仓库。** 刷新页面时控制台冒出「找不到收银台」。原因是问的时间早于收银台装好。把仓库之间的调用挪进动作里面就好。

**三、拍照片代替看屏幕。** 改了数据界面不动。凡是 `const { x } = store` 的地方都要么改用 `storeToRefs`，要么改成直接点。

**四、给组合式仓库按重置键。** 报「没有 $reset 这个方法」。这类仓库没有自带的重置键，自己写一个把数据挨个归零的函数。

**五、动作没有「只认最新一单」的保护。** 快速切换分类标签时，列表内容突然对不上。原因是先发的请求后回来，把后发的结果盖掉了。打个比方：你连着寄了两单货，第一单走得慢、第二单走得快，结果第二单先到，第一单后到又把货架换了一遍。解法是每单编号，回来的货对不上最新编号就扔掉。

**六、每个页面各自弹一遍错误框。** 一处接口出错，五个页面各写一套提示。这属于「补货的事让每家店自己处理」，太浪费。应该在出门采购的那一层统一处理（请求拦截器），动作只管成功之后怎么摆货，真出事了再往上报给页面做局部兜底。

## 一句话总结

Pinia 就是一个「放东西的公共仓库」，数据用 `ref` 或者账本函数放进去，算出来的结果用 `computed` 推，动作就是普通函数；读数据要装实时摄像头不能拍照片，动作直接拿；只有一点不能忘——仓库必须先建好再问它要东西。
