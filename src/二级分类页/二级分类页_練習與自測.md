# 二级分类页 · 练习与自测

> 题量：是非 10 / 选择 10 / 配对 8 / 情境 3 / 代码阅读 3 / 延伸思考 2。答案紧跟各区块。

## 一、是非题（10 题）

1. 二级分类页的 `id` 是一级分类的 id。
2. Vue Router 4 中，静态段比参数段更具体，因此匹配优先级更高。
3. 筛选条件属于「可分享状态」，理想做法是写进 URL 的 query。
4. 列表一次只取 20 条时，前端 `filter` 得到的结果等于全量筛选结果。
5. 价格排序可以由前端对当前 20 条排序得到正确结果。
6. 分面搜索里每个筛选项后面的数字，需要后端统计后返回。
7. 无限加载必须在 `hasMore` 为 false 时停止，否则会无限请求。
8. `useIntersectionObserver` 默认以视口为根，滚动容器变化时应传 `root`。
9. 切换筛选时只需把 `page` 重置为 1，不必清空列表。
10. `onUnmounted(stop)` 用于在离开页面时清理观察器。

### 答案解析

1. **错**。是二级分类的 id；一级页「查看全部」为了复用页面才可能传一级 id。
2. **对**。Vue Router 4 按具体程度打分；Vue Router 3 按注册顺序。
3. **对**。搜索词、筛选、排序、页码都属于可分享状态。
4. **错**。前端过滤只能处理已取到的 20 条，会漏掉后端其余数据。
5. **错**。只排当前页，得不到「全部商品里最便宜的」。
6. **对**。计数依赖全量数据，必须由后端算。
7. **对**。页面不够长时哨兵一直在视口内，会循环请求。
8. **对**。`root` 指定交叉计算的参照容器。
9. **错**。还要清空列表、重置 `hasMore` 与 `total`。
10. **对**。组件卸载时观察器要停止，否则泄漏。

### 答案解析

10. **B**。`replace` 不新增历史记录。

## 四、情境分析（3 题）

### 情境 1：一进二级页就崩

访问 `/category/sub/1005001`，控制台报错，`route.params.id` 的值是字符串 `sub`。

**问**：原因与修法。

**答**：路由以 Vue Router 3 的方式注册，更宽泛的 `/category/:id` 写在前面，抢先匹配并吞掉了 `sub`。修法：把更具体的 `/category/sub/:id` 放到前面；或升级到 Vue Router 4，它按路径具体程度匹配，顺序无关。

### 情境 2：只有 8 个商品的分类，接口被刷了 60 次

某分类商品很少，一屏就显示完。Network 面板显示同一个接口被连续调用了 60 多次。

**问**：原因与修法。

**答**：列表短，哨兵始终在视口内，`IntersectionObserver` 的回调在每次状态变化后都会触发，而代码没有「到底了」的判断，于是不断请求下一页。修法：用 `list.length >= total` 设置 `hasMore = false`，回调里先判断 `loading` 与 `hasMore`。

### 情境 3：切了品牌，列表里还是混着别的品牌

用户选中「Apple」，列表里仍然有 Android 机型。检查发现筛选是前端 `filter`。

**问**：为什么错，怎么改？

**答**：列表分页，一次只取 20 条，前端过滤只作用于这 20 条，既漏数据又容易和下一页结果混在一起。修法：把 `brandId` 作为请求参数发给后端，切换时重置 `page`、清空列表后重新请求。

## 五、代码阅读（3 题）

### 题 1

```js
const load = async () => {
  const { result } = await getSubCategoryAPI({ categoryId: id, page: page.value })
  list.value = result.items
  page.value++
}
```

**问**：如果这是「无限加载」的加载函数，有两个明显问题，分别是什么？

**答**：一是用 `=` 覆盖而不是 `push`，第二页会把第一页顶掉；二是没有判断是否还有更多，`page` 无条件自增，会一直请求到空页。另外也没有 `loading` 防重入。

### 题 2

```js
const brandId = ref(null)
const shown = computed(() => list.value.filter(g => !brandId.value || g.brandId === brandId.value))
```

**问**：这段代码在什么前提下是正确的？

**答**：只在「`list` 是全量数据」时正确，比如数据量很小、一次取完。一旦分页，`list` 只是当前页，过滤结果就不等于全量筛选结果。

### 题 3

```js
useIntersectionObserver(sentinel, ([entry]) => {
  if (!entry.isIntersecting) return
  loadMore()
})
```

**问**：补全这段代码缺少的保护，并说明每个保护解决什么问题。

**答**：缺三样。`if (loading.value) return`：防止一次请求未返回时重复触发；`if (!hasMore.value) return`：防止取完后无限请求；`onUnmounted(stop)`：防止离开页面后观察器泄漏。另外 `loadMore` 内部要在 `finally` 里复位 `loading`。

## 六、延伸思考（2 题）

1. 把筛选条件写进 URL 会带来哪些好处与代价？请给出一个「值得写」和「不值得写」的具体例子。

   **思路**：好处是可分享、可刷新还原、可后退，也便于埋点分析「用户常用哪些筛选」。代价是要处理「地址变 → 请求」的同步、默认值不该出现在地址里（否则链接很长）、以及 `replace` 与 `push` 的选择。值得写：商品列表的品牌/价格/排序。不值得写：鼠标悬停高亮、侧边栏展开、某个 tab 的临时滚动位置——这些是纯 UI 状态，写进 URL 只会让链接变脏。

2. 无限滚动与分页器，在「用户体验」「性能」「可访问性」三个维度上各自的取舍是什么？如果你只能选一个，会选哪个，为什么？

   **思路**：体验上无限滚动更顺滑，但缺少「终点感」与「位置记忆」；分页器位置明确，但每次翻页要等。性能上无限滚动 DOM 持续增长、需要虚拟列表配合；分页器每次只渲染一页，内存平稳。可访问性上分页器对键盘与读屏用户更友好，无限滚动需要额外处理焦点与「加载更多」按钮兜底。只选一个的话，「商品列表」类场景我会选分页器或「加载更多按钮」——它保留了明确终点，也不依赖滚动事件；真正适合无限滚动的是「没有明确终点」的信息流。
