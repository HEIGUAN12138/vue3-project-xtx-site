# 二级分类页 · 案例分析

> 四个背景：无限滚动为什么会流行又为什么被反思、分面筛选从哪来、哨兵模式解决了什么，以及「状态该不该写进 URL」。

## Case 1：无限滚动——一个发明者的反思

### 背景

传统列表用分页器：一页 20 条，底部有「上一页 / 下一页」。它的好处是「位置明确、可回到某处、可被搜索引擎索引」。

2006 年前后，设计师 Aza Raskin 在 Humanized 公司提出「无限滚动」：用户往下滚，内容自动加载，页面上不存在「下一页」这个动作。这个交互在移动端爆发——触摸屏上滚动比点击自然得多。

### 事件经过

2019 年前后，Raskin 在多个访谈里公开表示后悔发明了这个交互。他的核心批评是：无限滚动把「停止」的决定权交给了算法。分页器有一个天然的终点，用户知道「我看完了」；无限滚动没有终点，用户只能靠意志力停下，而这正是社交产品想要的。

与此同时，可用性研究给出了一组具体的代价：

- **页脚消失**。用户永远到不了底部，客服入口、备案信息、相关链接都看不到。
- **位置丢失**。刷新或返回时，回不到刚才那一屏。
- **性能累积**。DOM 节点只增不减，滚动到几百条之后开始卡。

电商的处理方式通常是折中：列表用无限滚动，但在末尾明确写「没有更多了」，并把重要入口（客服、回到顶部）做成浮动按钮。这正好对应本章第七节的两条实现要求——`hasMore` 必须给出明确终点、`onUnmounted` 必须清理。

### 与本章的关系

本章第七节的实现是「无限加载」，但第八节把「滚到底疯狂发请求」列成了坑。把这两件事放在一起看，才能理解为什么 `hasMore` 不是可选优化，而是这个交互模式能不能被接受的前提。

## Case 2：分面筛选从图书馆学走进电商

### 背景

「按品牌、按价格、按是否现货」同时筛选，这个交互有个专业名字：**分面搜索（faceted search）**。它最早出现在图书馆与法律数据库里——一篇文章有「作者、年份、主题、期刊」等多个维度，用户需要同时按多个维度缩小范围。

### 事件经过

1990 年代，Endeca、Verity 等公司把分面搜索商业化，用在电商与企业内网。2000 年代之后，Amazon、eBay 把它变成电商标配：左侧一列筛选项，每个选项后面带一个「(123)」的数字，表示选中后还剩多少件商品。

这个「数字」是分面搜索的精髓，也是最容易被省略的部分。它要求后端在返回列表的同时，返回「每个筛选项命中多少条」——这意味着筛选逻辑必须在后端，前端拿不到全量数据。

小兔鲜的接口只返回商品列表与总数，没有返回每个品牌的计数。这是一个简化：用户点完品牌才知道剩多少。完整实现需要后端配合，属于「知道差距在哪」而不是「必须现在做」。

### 与本章的关系

本章第六节说「筛选必须回后端」，依据就在这里：分面搜索的计数、排序、分页都建立在「后端知道全量数据」这个前提上。前端过滤只能处理「已经取到的 20 条」，能力上就不成立。

## Case 3：哨兵模式——为什么不用 scroll 事件

### 背景

无限加载最早的标准实现是监听 `scroll`，然后判断 `scrollTop + clientHeight >= scrollHeight`。这段代码在 2000 年代的每个「瀑布流」页面里都能找到。

它的问题有三个：`scroll` 每秒触发几十次，判断里要读 `scrollHeight` 会强制同步布局；不同浏览器的 `scrollTop` 取整方式不同，判断会差一两个像素；滚动容器可能不是 `window`，嵌套滚动要单独处理。

### 事件经过

`IntersectionObserver` 在 Chrome 51（2016 年）落地后，社区很快把它用于无限加载：不再算「滚到哪了」，而是在列表末尾放一个空的「哨兵」，观察它是否进入视口。浏览器的合成线程负责计算交叉状态，主线程只在状态变化时被回调。

这个模式被称为 **sentinel pattern**（哨兵模式），在 VueUse、React Query 的文档里都有对应实现。它把「数学计算」换成了「声明一个观察点」，代码量减少一半，边界情况也少很多。

代价是「精度」：`IntersectionObserver` 只能在元素进入视口时通知你，无法告诉你「还有 300px 到底」。所以想做「提前 300px 预加载」，要配 `rootMargin`：

```js
useIntersectionObserver(sentinel, cb, { rootMargin: '0px 0px 300px 0px' })
```

### 与本章的关系

本章第七节直接用了这个模式，并强调四个判断：`isIntersecting`、`loading`、`hasMore`、`unmounted`。前两个解决「重复触发」，后两个解决「无效循环」与「资源泄漏」。这四条不是本章的发明，而是这个模式在社区里踩了几年之后沉淀下来的标准答案。

## Case 4：状态该不该写进 URL

### 背景

单页应用出现之前，URL 就是页面状态的唯一来源：`?page=2&sort=price` 这样的查询串，刷新、分享、后退全都靠它。

单页应用把状态搬进了内存，URL 只保留「路由」。好处是切换快，坏处是「状态不可分享」——用户筛选了半天的结果，刷新一下全没了。

### 事件经过

2011 年，HTML5 History API 引入 `pushState`/`replaceState`，让脚本可以在不刷新页面的情况下修改地址栏。这直接催生了前端路由（Vue Router、React Router 的前身），也让「把状态写进 URL」重新变得可行。

此后社区形成了一个大致共识：**能被分享的状态，应该写进 URL**。搜索关键词、筛选条件、排序方式、页码，都属于这一类；而「侧边栏是否展开」「当前 hover 的是哪一项」属于纯 UI 状态，留在内存即可。

GitHub 的 issue 列表、淘宝的搜索结果页，都是这个共识的典型实现：URL 里有 `q=`、`sort=`、`page=`，复制给别人能还原一模一样的视图。

Vue Router 提供的 `router.replace()` 就是为这件事准备的：它修改地址但不产生历史记录（避免用户按一次后退只退了一个筛选条件）。

### 与本章的关系

本章第三节把「分类 id」与「筛选条件」分开讨论，并明确说「小兔鲜把筛选留在本地状态，是一个可以改进的点」。判断依据就是这段历史：筛选条件属于「可分享状态」，写进 URL 才是完整实现。写的时候用 `replace` 而不是 `push`，再用 `watch(() => route.query, ...)` 驱动请求，就能同时拿到「可分享」与「后退不刷屏」两个好处。
