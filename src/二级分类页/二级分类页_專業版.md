# 二级分类页

> 一级分类页回答「这个分类卖什么」，二级分类页回答「在这些里挑我要的」。一旦要「挑」，就有了筛选、排序与分页——页面从「展示」变成「查询」。

## 一、二级分类页的业务位置：从「一层」到「一个货架」

一级分类页像商场的一层楼：你看到这一层有哪些区域、有哪些商品，但没法再细分。二级分类页是这一层里的一个具体货架：只放某个子类的东西，并且提供「按品牌挑」「按价格挑」「按销量排」的能力。

这两页的数据源完全不同。

一级分类页的数据是「这个分类是什么」——名字、图、子分类。二级分类页的数据是「这个分类下有哪些商品，按什么条件取」——一个带参数的查询。

这个差别决定了本章的三个重点：

1. **参数不止一个**。一级页只有 `id`，二级页有 `id`、页码、排序字段、排序方向、品牌、是否只看有货。它们组合起来才是一次请求。
2. **状态是「查询条件」而不是「页面内容」**。筛选条件一变，等于换了一次查询，不是「把已有列表过滤一下」。
3. **列表是「流」而不是「一页」**。无限加载意味着列表会不断追加，而不是整体替换。

先想清楚这三点，后面每个坑都能找到根。

## 二、路由配置与两级参数的衔接

路由是嵌套在 `/category` 下的三级路径：

```js
{
  path: '/category/sub/:id',
  component: () => import('@/views/Category/sub.vue'),
}
```

`id` 是**二级分类**的 id，不是一级分类的 id。命名上要写清楚，否则半年后没人知道这个 `id` 属于哪一级。

这里有一个历史遗留的坑值得知道。Vue Router 4（Vue 3 配套）按路径的「具体程度」打分，静态段 `sub` 比参数段 `:id` 更具体，所以下面两条同时存在也不会冲突：

```js
{ path: '/category/:id', component: Category },
{ path: '/category/sub/:id', component: SubCategory },
```

但在 Vue Router 3 里，匹配是**按注册顺序**的：如果 `/category/:id` 写在前面，`/category/sub/1005000` 会被它先匹配走，`id` 拿到字符串 `sub`，页面直接报错。所以老项目里常见「把更具体的路由写在前面」的注释。迁移到 Vue Router 4 之后这条规则不再必要，但保留着也无害。

跳转入口通常有两个：

```html
<!-- 一级分类页：子分类区块 -->
<RouterLink v-for="sub in category.children" :key="sub.id" :to="`/category/sub/${sub.id}`">
  {{ sub.name }}
</RouterLink>

<!-- 一级分类页：筛选面板里的「查看全部」 -->
<RouterLink :to="`/category/sub/${category.id}`">查看全部</RouterLink>
```

第二个写法看着奇怪——把一级分类自己的 id 传给二级页。原因是小兔鲜的二级页接口接受任意层级的分类 id，它会返回该分类下的商品与子分类。这样「一级页的查看全部」和「某个子分类」可以复用同一个页面。这是一个务实的取舍：多一个页面就多一套筛选逻辑，不如让页面接受更宽泛的输入。

如果想更严格，也可以让一级页的「查看全部」留在本页、只让子分类进二级页。判断标准是「两种入口的交互是否一致」：如果都只是「列表 + 筛选」，合并更省；如果一级页要展示分类介绍、二级页不需要，就该分开。

## 三、路由参数与查询参数：谁该放哪里

二级页的状态有两类，放在不同地方。

**路径参数**（`/category/sub/:id`）：标识「这是哪个分类」。它决定页面的身份，应该可分享、可收藏、可被搜索引擎索引。

**查询参数**（`?brand=2&sort=price_asc&page=3`）：标识「在这个分类里怎么挑」。它决定同一次查询的视图，也应该可分享。

两者的区别在于「变了之后要不要重新加载整页」。分类变了，面包屑、筛选项、商品列表全换，属于换页面；筛选变了，只是列表换一批，属于换视图。

实际项目里常见的写法是把筛选条件放在本地 `reactive` 对象里，不同步到 URL。这样写省事，但代价是：

- 用户刷新，筛选条件全丢
- 分享链接给别人，对方看到的是未筛选的列表
- 浏览器后退，回不到上一个筛选状态

要做得完整，应该用 `router.replace({ query: {...} })` 把筛选条件写进地址，再用 `watch(() => route.query, ...)` 驱动请求。本章后面按「本地状态」讲，因为小兔鲜原稿是这么做的；但要知道这是一个可以被改进的点，而不是「正确做法」。

## 四、面包屑：三段式与一个接口

二级页的面包屑是三段：首页 / 一级分类 / 二级分类。第二段可点，回到一级页；第三段不可点。

难点在于：二级页只知道自己的 id，怎么拿到父级分类的名字和 id？

答案是一个接口同时返回三层需要的信息：

```js
const { result } = await getCategoryFilterAPI(id)
// result: {
//   name: '手机通讯',
//   parentName: '手机数码',
//   parentId: '1005000',
//   brands: [...],
//   saleProperties: [...],
// }
```

这样一次请求就能渲染面包屑与筛选项，不需要「先查自己、再查父级」两次往返。

```html
<XtxBread>
  <XtxBreadItem to="/">首页</XtxBreadItem>
  <XtxBreadItem :to="`/category/${info.parentId}`">{{ info.parentName }}</XtxBreadItem>
  <XtxBreadItem>{{ info.name }}</XtxBreadItem>
</XtxBread>
```

如果后端只返回 `parentId` 不返回 `parentName`，就得再发一次请求。这时要考虑「值不值得」：面包屑在首屏，两次串行请求会让它晚出现；可以让后端补字段，或者并行发两个请求（自己 + 父级），后者多一次往返但不用改后端。

还有一个边界：**直接访问一个被删除的分类**。接口返回空，面包屑会变成「首页 / / 」。处理方式与上一章一致：名字为空时显示兜底文案，并给返回入口。

## 五、筛选项与商品列表：两套数据、一次渲染

二级页的界面分成两块，数据也来自两处。

**筛选项**来自分类详情接口：品牌列表（`brands`）、销售属性（`saleProperties`，比如「仅看有货」「折扣」）、可选的价格区间。这些数据在页面生命周期内基本不变，取一次即可。

**商品列表**来自商品接口，参数是「分类 + 筛选 + 排序 + 分页」：

```js
const params = {
  categoryId: id,
  page: 1,
  pageSize: 20,
  sortField: 'publishTime',   // 或 praiseCount / saleCount / price
  sortMethod: 'desc',         // 或 asc
  brandId: null,
  onlyDiscount: false,
}
```

注意 `brandId` 与 `onlyDiscount` 是**筛选条件**，`sortField` 与 `sortMethod` 是**排序条件**，`page` 是**位置**。三者混在一个对象里没关系，但在代码里要能一眼分清，因为它们的变化时机不同：

- 排序变化：列表整个换，但用户还在「顶部」，页码回到 1
- 筛选变化：同上
- 页码变化：列表追加，筛选与排序不变

把这三件事写成三个函数，比一个 `load()` 里塞满 `if` 更容易维护：

```js
function resetAndLoad() { page.value = 1; list.value = []; load() }
function onSortChange(field) { sort.value = field; resetAndLoad() }
function onFilterChange() { resetAndLoad() }
function loadMore() { page.value++; load() }
```

`resetAndLoad` 里「清空列表」这一句很容易漏。漏了的话，切换筛选后新旧商品会拼在一起，看起来像「筛选没生效」。

## 六、列表筛选：前端过滤还是后端查询

这是本章最容易被做错的一个判断。

如果列表是一次性取全量（比如只有 30 条），前端 `filter` 完全够用，而且响应快、不耗流量：

```js
const shown = computed(() => list.value.filter(g => !brandId.value || g.brandId === brandId.value))
```

但二级页是分页的，一次只取 20 条。前端过滤只能过滤「已经取到的 20 条」，用户会以为「这个品牌只有 3 个商品」。所以**筛选必须回后端**，作为请求参数发出。

同理，价格区间、是否只看有货，都要传给后端。前端能做的只是「把用户的选择转成参数」。

排序也是一样。价格排序看起来可以前端排，但只排当前 20 条是错的——用户想看的是「全部商品里最便宜的」，那必须后端排。

```js
const sortOptions = [
  { field: 'publishTime', label: '最新' },
  { field: 'praiseCount', label: '人气' },
  { field: 'saleCount', label: '销量' },
  { field: 'price', label: '价格' },
]

function toggleSort(field) {
  if (sortField.value === field) {
    sortMethod.value = sortMethod.value === 'asc' ? 'desc' : 'asc'
  } else {
    sortField.value = field
    sortMethod.value = field === 'price' ? 'asc' : 'desc'
  }
  resetAndLoad()
}
```

价格默认升序（用户想先看便宜的），其他默认降序（最新、最热）。这种「默认值因字段而异」的细节，是产品感的一部分，不是技术难题。

筛选的交互还有一个细节：**多选还是单选**。品牌通常是单选（点一个，再点一个就换），销售属性通常是多选（可以同时「仅看有货」和「有折扣」）。状态形状不同：

```js
const brandId = ref(null)          // 单选
const saleProps = ref([])          // 多选，存 id 数组
```

把单选做成多选，或者反过来，用户都会觉得别扭。这不是代码问题，是一开始就要定清楚的产品规则。

## 七、无限加载：哨兵、状态与「到底了」

二级页不用分页器，用「滚到底自动加载」。实现方式是放一个空的哨兵元素在列表末尾，用 `IntersectionObserver` 观察它：

```html
<ul class="goods-list">
  <li v-for="g in list" :key="g.id"><GoodsItem :item="g" /></li>
</ul>
<div ref="sentinel" class="sentinel"></div>
<p v-if="!hasMore" class="end">没有更多了</p>
```

```js
import { ref, onUnmounted } from 'vue'
import { useIntersectionObserver } from '@vueuse/core'

const sentinel = ref(null)
const loading = ref(false)
const hasMore = ref(true)

const { stop } = useIntersectionObserver(sentinel, ([entry]) => {
  if (!entry.isIntersecting) return
  if (loading.value || !hasMore.value) return
  loadMore()
})

onUnmounted(stop)
```

这段代码有四个必须有的判断，缺一个就出问题。

**第一，`entry.isIntersecting`**。只在哨兵真的进入视口时才加载，否则回调一开始就会触发。

**第二，`loading`**。滚动事件可能在一次请求返回前触发多次，哨兵一直在视口里就会连续发请求。用 `loading` 挡住在途请求。

**第三，`hasMore`**。取完之后哨兵仍然在视口里（页面不够长），会无限请求。必须用「已取数量 ≥ 总数」把它关掉。

```js
async function loadMore() {
  loading.value = true
  try {
    const { result } = await getSubCategoryAPI({ ...params, page: page.value })
    list.value.push(...result.items)
    total.value = result.counts
    hasMore.value = list.value.length < result.counts
    if (hasMore.value) page.value++
  } finally {
    loading.value = false
  }
}
```

注意 `page.value++` 放在「还有更多」的分支里。如果无条件加，最后一次请求完页码还会往后走，虽然不会造成可见问题，但状态是脏的。

**第四，`onUnmounted(stop)`**。用户可能在加载完之前离开，观察器要清理。

还有一个容易被忽略的点：**滚动容器**。`useIntersectionObserver` 默认以视口为根。如果列表在一个 `overflow: auto` 的容器里滚动，哨兵相对视口可能永远不「进入」，或者进入得太早。这时要传 `root`：

```js
useIntersectionObserver(sentinel, cb, { root: scrollContainer.value })
```

小兔鲜的列表是整页滚动，用默认值就够。但只要改一次布局（比如加一个固定高度的内容区），这个默认就会失效——记住这个参数的存在，比记住「默认能用」更重要。

**切换筛选时要重置什么**：`page = 1`、`list = []`、`hasMore = true`、`total = 0`。少重置 `hasMore`，会出现「切了筛选，列表是空的，也不加载」——因为上一轮刚好取完了。

## 八、工程实践与常见坑

**第一，路由被一级页吞掉。** 现象是访问 `/category/sub/1` 时 `id` 变成 `sub`。Vue Router 3 里是注册顺序问题，把更具体的路由写在前面；Vue Router 4 按具体程度匹配，不受影响。知道自己在哪个版本，比背结论重要。

**第二，切筛选后新旧商品混在一起。** 因为没清空 `list`。`resetAndLoad` 里必须 `list.value = []`。

**第三，切筛选后加载不动。** 因为 `hasMore` 还是上一轮的 `false`。重置时要一并复位。

**第四，滚到底疯狂发请求。** 缺少 `loading` 或 `hasMore` 判断。两者都要有。

**第五，同一页请求了两次。** 哨兵在视口里，回调触发一次；`page` 的变化又触发 `watch` 一次。只留一个触发源。

**第六，筛选在「当前 20 条」里过滤。** 表现为「某个品牌只有 2 个商品」，其实后端有 50 个。筛选必须作为请求参数。

**第七，无限加载后切换分类，列表串了。** 旧请求晚回来。沿用上一章的序号比对，或在组件重建时重置。

**第八，滚动容器变了，懒加载失效。** 忘了 `root` 参数。布局一改就要重新确认这个值。
