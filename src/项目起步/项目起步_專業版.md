# 项目起步

> 这一章做的是「地基」：脚手架、别名、组件库、主题、请求层、路由表。地基歪一寸，后面每一页都要返工。

## 一、脚手架与目录：create-vue 生成了什么

`create-vue` 是 Vue 官方脚手架，底层用 Vite。跑 `npm create vue@latest` 之后，交互式选项会依次询问是否需要 Router、Pinia、TypeScript、Vitest、端到端测试、ESLint、Prettier。小兔鲜这类项目通常选 Router + Pinia，其他留空，先把项目跑起来再说。

生成的目录里有四层需要认识清楚。`src/components/` 放全局可复用的组件，`src/views/` 放路由级页面，`src/stores/` 放 Pinia，`src/apis/` 不是脚手架生成的，是我们自己要建的请求层。前三个是约定，第四个是习惯——把请求函数和页面分开，是为了让「改接口地址」只改一处。

```bash
npm create vue@latest xiaotuxian
cd xiaotuxian
npm install
npm run dev
```

整理目录时的第一条原则是「按职责分，不按文件类型分」。新手容易建出 `src/js/`、`src/css/` 这种目录，结果一个功能的三个文件分散在三处。正确做法是 `src/apis/goods.js` 管商品接口、`src/composables/useCountDown.js` 管倒计时逻辑、`src/utils/format.js` 管纯函数，每加一个功能都能找到唯一归属。

第二条原则是删掉脚手架自带的示例代码。Vite 模板里有 `HelloWorld.vue`、`TheWelcome.vue`、一堆 demo 图标，它们会干扰你判断「哪个文件是我写的」。删干净之后再开始，比事后清理省事。

需要保留的是 `vite.config.js`、`jsconfig.json`、`package.json`、`index.html` 四个文件，后面三节都要改它们。

## 二、路径别名：jsconfig.json 与 vite.config.js 的双份配置

项目稍微大一点就会出现 `../../../apis/goods` 这种路径。数不清几个点，挪动文件就全崩。别名解决的就是这件事：用 `@` 指代 `src`。

这里有个高频困惑：为什么要配两个文件？因为 `@` 这个别名在两个不同阶段被解析两次。开发时，Vite 负责把 `import '@/apis/goods'` 解析成真实路径，所以要在 `vite.config.js` 里配 `resolve.alias`。编辑时，VS Code 的 TypeScript 语言服务负责跳转与补全，它读的是 `jsconfig.json` 的 `compilerOptions.paths`。只配一个的后果很具体：只配 Vite，代码能跑但编辑器里 `@` 画红线、点不进定义；只配 jsconfig，编辑器正常但跑起来报「Failed to resolve import」。

```js
// vite.config.js
import { fileURLToPath, URL } from 'node:url'
export default defineConfig({
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
})
```

```json
// jsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  },
  "exclude": ["node_modules", "dist"]
}
```

注意 `jsconfig.json` 与 `tsconfig.json` 的区别：纯 JS 项目用前者，TS 项目用后者。两者的 `paths` 语法完全一致，只是 TS 还会检查类型。小兔鲜是纯 JS，所以用 `jsconfig.json`，VS Code 需要重启一次语言服务（命令面板里 `TypeScript: Restart TS Server`）才会生效，这个「改完没反应」的坑第八节还会提。

`baseUrl: "."` 不能省。`paths` 是相对于 `baseUrl` 解析的，缺了它，`"src/*"` 会被当成相对项目根目录下的 `src`，而 `jsconfig.json` 所在目录恰好就是根目录，看起来能工作，一旦文件被挪到子目录就会失效。

## 三、Element Plus 按需导入：unplugin 的两个插件

Element Plus 全量引入的代价是打包体积增加约 700KB（gzip 后也有 200KB 上下），而项目实际可能只用到四十个组件。按需导入的思路是：只打包你 `import` 过的组件，样式也跟着走。

实现靠两个 unplugin 插件组合。`unplugin-vue-components` 负责识别模板里的组件标签并自动注入 import，`unplugin-auto-import` 负责自动注入 `ElMessage`、`ElMessageBox` 这类函数式 API 的 import。

```bash
npm i element-plus
npm i -D unplugin-vue-components unplugin-auto-import
```

```js
// vite.config.js
import AutoImport from 'unplugin-auto-import/vite'
import Components from 'unplugin-vue-components/vite'
import { ElementPlusResolver } from 'unplugin-vue-components/resolvers'

export default defineConfig({
  plugins: [
    vue(),
    AutoImport({ resolvers: [ElementPlusResolver()] }),
    Components({ resolvers: [ElementPlusResolver()] }),
  ],
})
```

配完之后，模板里直接写 `<el-button>` 即可，不需要 `import { ElButton }`，也不需要 `import 'element-plus/dist/index.css'`。两个插件在构建时把 `ElButton` 的 import 与它对应的样式路径一起插进去，这就是「按需」的实际含义。

有个代价要说清楚：自动导入让「这个组件从哪来」变得不直观。新人接手项目时，看到模板里的 `<el-button>` 找不到它被引入的地方，容易怀疑项目缺依赖。所以在 `src/main.js` 或 README 里写明「Element Plus 由 unplugin 自动导入」，是一句很值的注释。

还有一个常见故障：`ElMessage` 在 `<script setup>` 里直接调用报 `ElMessage is not defined`。原因是 `AutoImport` 的 `resolvers` 只处理了组件，函数式 API 需要确认 `AutoImport` 的配置确实包含 `ElementPlusResolver`，且重启了 dev server。这类「配置写了但没生效」的问题，八成是没重启。

## 四、主题定制：SCSS 变量覆盖的生效链路

Element Plus 的主色是 `#409eff`，小兔鲜要改成品牌色。定制方式有两种：CSS 变量覆盖（运行时）与 SCSS 变量覆盖（编译时）。前者简单但只能改颜色，后者能改圆角、字体、间距等全部设计令牌，代价是需要装 Sass。

SCSS 方案的原理是：Element Plus 的源码用 `@forward 'element-plus/theme-chalk/src/common/var.scss' with ($colors: (...))` 这种写法暴露变量。你在自己的样式文件里用同样的语法提前覆盖，Sass 编译时就会用你的值替换默认值。

```scss
// src/styles/element/index.scss
@forward 'element-plus/theme-chalk/src/common/var.scss' with (
  $colors: (
    'primary': ('base': #ff6b00),
  )
);
```

覆盖之后还要让 Element Plus 的组件在编译时读到这份变量，所以要在 `vite.config.js` 里再配一段 `css.preprocessorOptions.scss.additionalData`，把所有 SCSS 文件的编译都先注入这行 `@use`。

```js
css: {
  preprocessorOptions: {
    scss: {
      additionalData: `@use "@/styles/element/index.scss" as *;`,
    },
  },
},
```

这条链路最容易断在三个地方。第一，`additionalData` 里的路径必须和别名解析一致，写成相对路径 `../styles/...` 在深层组件里会找不到。第二，`additionalData` 是「每个 scss 文件前都插一段」，如果插的是会产出 CSS 的语句（比如直接写变量赋值以外的内容），会导致重复产出，必须只写 `@use`。第三，装了 `sass` 之后要重启 dev server，Vite 的依赖预构建缓存不会自动重建，症状是「改了变量颜色没变」。

如果只是想换个主色、不打算深度定制，用 CSS 变量更省事：在 `:root` 里写 `--el-color-primary: #ff6b00`，五行搞定，还不用装 Sass。两条路的取舍在第八节会再提一次。

## 五、axios 封装：实例、拦截器与统一返回

直接把 axios 用在组件里，会出现三个重复：baseURL 每个请求写一遍、token 每个请求塞一遍、错误提示每个页面弹一遍。封装的目标是把这三件事各收拢到一处。

第一步创建实例，把 baseURL 与超时定死。

```js
// src/utils/request.js
import axios from 'axios'

const instance = axios.create({
  baseURL: 'https://pcapi-xiaotuxian-front.itheima.net',
  timeout: 10000,
})
```

第二步加请求拦截器，统一带 token。这里要注意 Pinia 的 store 不能在模块顶层调用（第 2 章讲过），所以要在拦截器函数内部取。

```js
instance.interceptors.request.use((config) => {
  const userStore = useUserStore()
  if (userStore.token) {
    config.headers.Authorization = `Bearer ${userStore.token}`
  }
  return config
})
```

第三步加响应拦截器，统一处理业务错误码。小兔鲜的接口约定是 HTTP 200 但 `data.code` 可能是业务错误码，这种情况下 axios 不会进 `catch`，必须自己判断。

```js
instance.interceptors.response.use(
  (res) => {
    if (res.data.code === 1) return res.data
    ElMessage.error(res.data.msg || '请求失败')
    return Promise.reject(res.data)
  },
  (err) => {
    if (err.response && err.response.status === 401) {
      const userStore = useUserStore()
      userStore.clear()
      router.push('/login')
    }
    ElMessage.error(err.message)
    return Promise.reject(err)
  }
)
```

注意这里 `return res.data` 而不是 `return res`。这个决定会影响全项目所有调用处的写法：返回 `res.data` 之后，组件里 `const data = await getBannerAPI()` 直接就是数据；返回 `res` 则每次都要 `res.data.result` 三层。选定一种就全项目统一，中途改会让所有接口调用一起出问题。

第四步封装具体接口，只做参数拼装，不做业务判断。

```js
// src/apis/home.js
export const getBannerAPI = (params = {}) => request.get('/home/banner', { params })
export const getNewGoodsAPI = (params) => request.get('/home/new', { params })
```

这样分层之后，改接口地址只动 `apis/`，改错误处理只动 `utils/request.js`，页面里全是「调函数拿数据」。

## 六、路由整体设计：分层与懒加载

路由表是项目的骨架图，写之前先想清楚三件事：哪些页面共享布局、哪些页面需要登录、哪些页面参数不同但复用组件。

小兔鲜的结构是两层：顶层是 `Layout`（顶部导航 + `router-view`），它下面挂首页、分类页、详情页、购物车等；另一支是独立的登录页与会员中心，不套 `Layout`。

```js
// src/router/index.js
const router = createRouter({
  history: createWebHistory(),
  routes: [
    {
      path: '/',
      component: () => import('@/views/Layout/index.vue'),
      children: [
        { path: '', component: () => import('@/views/Home/index.vue') },
        { path: 'category/:id', component: () => import('@/views/Category/index.vue') },
        { path: 'detail/:id', component: () => import('@/views/Detail/index.vue') },
        { path: 'cart', component: () => import('@/views/Cart/index.vue') },
      ],
    },
    { path: '/login', component: () => import('@/views/Login/index.vue') },
  ],
})
```

三个设计点值得单独说。第一，所有页面都用 `() => import()` 懒加载，首屏只加载 Layout 与首页，其余按需下载。如果写成静态 import，打包后是一个巨大的 chunk，首屏白屏时间会明显变长。第二，`children` 里的空路径 `''` 表示「父路径的默认子页面」，访问 `/` 时渲染首页，这是嵌套路由的约定写法。第三，动态段 `:id` 要放在最后，`/detail/create` 与 `/detail/:id` 同时存在时，谁先声明谁优先匹配，写反了会导致 `create` 被当成 id。

路由元信息（`meta`）是权限的落点。需要登录的页面加 `meta: { requiresAuth: true }`，在全局前置守卫里统一判断，而不是在每个页面的 `onMounted` 里各自检查。

```js
router.beforeEach((to) => {
  const userStore = useUserStore()
  if (to.meta.requiresAuth && !userStore.isLogin) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }
})
```

`redirect` 这个参数是关键：登录成功后要跳回用户原本想去的地方，否则用户点「结算」被拦到登录页，登完回到首页，还得重新走一遍流程。

## 七、静态资源与 SCSS 变量自动导入

`src/assets/` 放会被构建处理的资源（图片、字体、全局样式），`public/` 放原样拷贝、不参与构建的文件（favicon、第三方校验文件）。判断标准是：需要被 `import` 或被 CSS 引用的放 `assets`，需要固定 URL 访问的放 `public`。

```js
// 会被构建、可能被压缩、文件名带 hash
import logo from '@/assets/images/logo.png'
// 原样拷贝，路径固定
const icon = '/favicon.ico'
```

在 Vite 里 `assets` 下小于 4KB 的文件会被转成 base64 内联，大于的生成带 hash 的文件名。这意味着你不能在 CSS 里用固定路径引用 `assets` 的图片，必须走相对路径或别名；而 `public` 下的文件可以用根路径直接引用，但换版本时浏览器缓存不会失效。

SCSS 变量的自动导入解决的是另一件事：每个组件都要用 `$brand-color` 这类变量，如果每个 `.vue` 文件都写一遍 `@use '@/styles/var.scss' as *`，几十个文件重复几十行。`additionalData` 就是干这个的——编译每个 SCSS 块之前先注入一行 `@use`。

```js
css: {
  preprocessorOptions: {
    scss: {
      additionalData: `@use "@/styles/var.scss" as *;`,
    },
  },
},
```

注意这与第四节的主题定制是同一个配置项，两行 `@use` 要合并到同一个 `additionalData` 字符串里，用换行分隔。写成两个 `additionalData` 时后者会覆盖前者，症状是「主题色生效了但自定义变量找不到」。

```js
additionalData: `@use "@/styles/element/index.scss" as *;\n@use "@/styles/var.scss" as *;`
```

## 八、工程实践与常见坑

**第一，别名只配了一处。** 现象是代码能跑但编辑器里 `@` 画红线，或反之。原因是 Vite 与语言服务各读各的配置。处理方式：`vite.config.js` 的 `resolve.alias` 与 `jsconfig.json` 的 `paths` 同时配，改完重启 TS 服务。

**第二，自动导入配了但没生效。** 现象是 `ElMessage is not defined` 或 `<el-button>` 样式丢失。原因是 dev server 没重启、依赖缓存没重建。处理方式：删掉 `node_modules/.vite` 再 `npm run dev`。

**第三，主题色改了没变化。** 三个可能：只改了 CSS 变量但组件用的是 SCSS 变量；`additionalData` 路径解析失败；`element/index.scss` 里的 `@forward` 写在了 `@use` 之后（Sass 要求 `@use`/`@forward` 必须在文件最前面）。逐个排查，先看编译有没有报错。

**第四，响应拦截器返回了 `res` 却按 `res.data` 用。** 现象是每个接口都在组件里多写一层，或者报 `Cannot read property 'result' of undefined`。根因是全项目没有统一约定。处理方式：拦截器里 `return res.data`，`apis` 层只透传，组件里直接用。

**第五，路由懒加载写成了静态 import。** 现象是首屏 JS 体积巨大、构建产物只有一个 chunk。处理方式：所有页面级组件用 `() => import()`，全局组件才用静态导入。

**第六，`public` 与 `assets` 混用。** 现象是开发时图片能显示、部署后 404，或者改了图片浏览器还显示旧图。判断标准见第七节，`assets` 走构建、`public` 走固定 URL，二者不要互相引用。
