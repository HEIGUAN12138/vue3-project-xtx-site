# 项目起步 · 案例分析

> 四个真实的技术演进，解释本章每一个配置项背后的选择，以及配错时的真实代价。

## Case 1：Vite 为什么把 webpack 换下首发位置

### 背景

2019 年以前，Vue CLI 与 Create React App 都以 webpack 为打包核心。webpack 的工作方式是「先把整个项目的模块依赖图走一遍，再启动开发服务器」，中大型项目冷启动要 30 秒到 2 分钟，改一行代码热更新要等 3 到 8 秒。这个等待时间直接决定了开发者的手感。

### 事件经过

2020 年 4 月，尤雨溪发布 Vite 的第一个版本。它的核心思路是**利用浏览器原生 ESM**：开发时不打包，浏览器请求哪个模块就现场转换哪个模块；依赖（`node_modules`）用 esbuild 预构建成 ESM，一次搞定后缓存。结果是冷启动从几十秒降到一两秒。2021 年 Vite 2.0 重写了插件体系，生态开始成型；2022 年 Vue 官方脚手架从 `vue-cli` 换成基于 Vite 的 `create-vue`；2023 年 `vue-cli` 进入维护模式。

生产构建方面，Vite 早期用 Rollup，后期引入 Rolldown 作为 Rust 实现。这意味着开发与生产用了两套工具，偶尔出现「开发正常、构建失败」的问题，这是 Vite 方案唯一明显的代价。

### 与本章的关系

本章第一节的脚手架就是 Vite。理解了「开发时不打包」，才能明白为什么 `vite.config.js` 里的 `resolve.alias` 是必须的（浏览器不知道 `@` 是什么），也才能理解为什么「删掉 `node_modules/.vite` 缓存」能解决大部分「配置改了没生效」的问题——那是 esbuild 预构建的缓存目录。

- [Vite 官方文档：依赖预构建](https://cn.vite.dev/guide/dep-pre-bundling.html)

## Case 2：Element Plus 从全量引入走到按需导入

### 背景

Element UI（Vue 2 版）时代，官方推荐的引入方式是 `import ElementUI from 'element-ui'` 加 `Vue.use(ElementUI)`，样式用 `import 'element-ui/lib/theme-chalk/index.css'`。一个中等项目打包后 CSS 常常超过 500KB，JS 增加 400KB 以上，而实际用到的组件可能不到一半。

### 事件经过

Element Plus 是 Element UI 的 Vue 3 版本，2022 年发布 2.0。它同时提供了三条路：全量引入、手动按需（`import { ElButton } from 'element-plus'` 加手动引入对应样式）、自动按需（配合 unplugin）。第三条路依赖两个社区插件：`unplugin-vue-components` 与 `unplugin-auto-import`，它们的 `ElementPlusResolver` 知道每个组件对应哪个样式文件路径，在构建时自动注入 import 与 style 引用。

这套方案的效果是可测量的：同样是四十个组件，全量引入与按需引入的产物体积差通常在 60% 以上。代价是「组件从哪来」在代码里不可见，新人阅读时需要额外说明。

### 与本章的关系

本章第三节的两个插件就是这个演进的产物。案例的价值在于解释了「为什么不能只装一个」：`unplugin-vue-components` 只处理模板里的组件标签，`ElMessage`/`ElMessageBox`/`ElLoading` 这类函数式 API 不在模板里，必须靠 `unplugin-auto-import`。少配一个，就会遇到「按钮能显示但弹消息报 undefined」这种看起来很奇怪的现象。

### 参考资料

- [Element Plus 官方文档：快速开始](https://element-plus.org/zh-CN/guide/quickstart.html)
- [unplugin-vue-components 仓库](https://github.com/unplugin/unplugin-vue-components)
- [unplugin-auto-import 仓库](https://github.com/unplugin/unplugin-auto-import)

## Case 3：小兔鲜把 401 处理收进响应拦截器

### 背景

token 有过期时间。用户逛了半小时准备下单，token 刚好过期，这时点「结算」发出的请求全部返回 401。如果每个页面自己处理，就会出现：购物车页弹「请重新登录」，订单页弹一次，支付页再弹一次，而且三次跳转可能互相打架——用户被连着踢到登录页三次。

### 事件经过

改造的做法是在 `utils/request.js` 的响应拦截器里统一处理 401：清空 user store、提示一次、带着当前路径跳到登录页。页面里不再出现任何 `if (status === 401)` 的代码。

实施中出现了两个细节问题。第一，拦截器里要取 user store，而 `useUserStore()` 不能在模块顶层调用（第 2 章讲过），必须写在拦截器回调内部。第二，跳转时要用 `router.push` 而不是 `location.href`，否则整页刷新会丢掉当前路由的 query 参数，登录回来后无法回到原位置。

与此配套的是请求拦截器统一加 token。两者合起来让「身份」这件事只有两个落点：写 token 在登录页，读与清 token 在拦截器。任何页面自己拼 Authorization 头，都是架构上的倒退——因为一旦 token 格式从 `Bearer xxx` 改成 `x-token: xxx`，你要改 N 个文件。

### 与本章的关系

本章第五节把「请求拦截器带 token」「响应拦截器处理 401」写在了一起，依据就是这次改造。它也解释了为什么封装要分四步：实例、请求拦截、响应拦截、接口函数。四层各管一件事，改任何一层都不会牵动其他层。

## Case 4：路径别名「编辑器不认」的长期困扰

### 背景

Vue CLI 时代，`@` 别名是开箱可用的：`vue.config.js` 里配一次，webpack 负责解析，VS Code 靠 Vue 官方插件（Vetur/Volar）也能推断出 `@` 指向 `src`。所以很多人从没意识到「别名要在两个地方配」。

### 事件经过

换成 Vite + `create-vue` 之后，脚手架默认生成 `jsconfig.json`，里面只有 `paths: { "@/*": ["./src/*"] }`，但 `baseUrl` 是不是需要、Vite 那边是不是需要 `resolve.alias`，在不同版本之间有过变化。社区里长期存在两类提问：一类是「代码能跑但编辑器红线」，另一类是「编辑器正常但 `npm run dev` 报 Failed to resolve import」。

到了 TypeScript 项目，问题会变成 `tsconfig.json` 与 `tsconfig.app.json` 的 `paths` 是否被继承。Vue 官方在 `create-vue` 里把 TS 配置拆成多份（`tsconfig.json`、`tsconfig.app.json`、`tsconfig.node.json`），新手把 `paths` 写进根 `tsconfig.json` 却发现不生效，原因是根文件只做 references，真正的编译选项在 `tsconfig.app.json`。

### 与本章的关系

本章第二节之所以把「两份配置」单独列一节，就是因为这是读者反馈最多的一个问题。判断方法很实用：如果编辑器红线但能跑，缺的是 `jsconfig.json`；如果能跑但构建报错，缺的是 `vite.config.js`；如果两份都配了还不生效，去重启 TS 语言服务或删 `.vite` 缓存。
