# 小兔鲜电商：从首页到支付的全链路

> 跨主题集成分析 — 一个用户，七个页面，一条会掉钱的数据流

## 事件概述

一个用户从打开首页到支付成功，平均会经过 7 个页面、触发 20 次以上接口请求、产生 3 份状态副本（服务端、Pinia、组件本地）。这条链路上任何一处状态算错，用户看到的金额就和实际扣款不一致——这是电商前端最典型的「技术问题变成钱的问题」。

这篇分析不复述各章知识点，而是沿着**一笔真实订单的时间线**，看每一章负责哪一段，以及段与段之间靠什么衔接。读懂这条线，你就知道为什么学习顺序是「Vue3 → Pinia → 项目起步 → 页面 → 交易」。

## 事件背景

电商前台有三个绕不开的约束，它们决定了整个项目的架构：

**约束一：状态必须跨页面存活。** 用户在详情页加购，跳到购物车还要能看到；在购物车勾选了三件，进订单页不能重新勾一遍。组件本地的 `ref` 活不过路由跳转，所以必须有跨页面的状态容器。

**约束二：URL 就是状态。** 分类页的「品牌 + 价格区间 + 排序 + 页码」如果只存在内存里，用户一刷新就全丢，分享链接也带不过去。所以筛选条件必须写进 query，页面变成 URL 的投影。

**约束三：金额只能有一个真源。** 单价、数量、优惠、运费四者相乘相加的地方越多，出错概率越高。工程上的做法是：金额只在 Pinia 的 getter 里算一次，所有页面读同一个结果。

## 事件经过

### 阶段一：进入首页（Home页）

用户打开 `/`，Layout 渲染顶部导航与 `router-view`，Home 页开始并发请求：轮播图、分类楼层、猜你喜欢。三个接口互不依赖，用 `Promise.all` 并发，首屏时间取决于最慢的那个。

这里的关键决策是**请求边界**：一个楼层一个接口，而不是一个「首页聚合接口」。前者失败可以局部降级（该楼层显示骨架），后者一失败整页空白。代价是请求数变多，需要懒加载与缓存配合。

### 阶段二：浏览到详情（一级分类页 → 二级分类页 → 商品详情）

用户点导航进入 `/category/101`。一级分类页从 `route.query` 读出筛选条件，拼成请求参数；用户改排序，页面把新的 `sort` 写回 query，路由变化触发重新请求。**页面不保存筛选状态，它只是 URL 的渲染结果。**

点击商品进入 `/detail/2001`。详情页请求商品详情与 SKU 规格树，用户选颜色、选容量，选中组合决定价格与库存。这里的状态是派生的：选中项 → SKU → 价格/库存/按钮可用性，全部用 `computed` 串联，不允许「选颜色时手动改价格」这种命令式写法。

### 阶段三：被拦截的登录（登录页）

用户点「加入购物车」，路由跳到 `/cart`，但购物车页需要用户身份。路由守卫检查本地 token，没有就重定向到 `/login?redirect=/cart`。

登录成功后写入 token，再跳回 `redirect` 指定的地址。这一步的顺序不能反：**先拿到 token，再跳转**。如果先跳转再异步写 token，购物车页的请求拦截器会读到一个空 token，表现为「刚登录就 401」。

请求拦截器统一给请求头加 token，响应拦截器统一处理 401（清 token + 回登录页）。这两个拦截器是全项目唯一允许处理身份的地方，页面里不应该出现手写 token 的代码。

### 阶段四：加入购物车（商品详情 → 购物车）

加购时写入 Pinia 的 cart store：如果该 SKU 已存在则数量累加，否则新增一条。购物车页读同一份 store，因此详情页加购后，导航栏的角标和购物车列表会自动更新——这不是「通知」，而是同一个响应式数据被两处读取。

购物车页最容易出错的是三件事：全选/半选的联动、只汇总选中项、数量变化后重新计算。三件事都应该是 `computed`，一旦用 `watch` 手动维护，就会出现「偶尔差一块钱」。

### 阶段五：确认订单（订单页）

点击结算，前端把选中条目提交给服务端生成订单草稿，跳到 `/order`。订单页展示地址、商品清单、金额，用户点「提交订单」。

这里必须处理**幂等**：用户手抖点两次，不能生成两笔订单。前端手段是按钮点击后立即置灰，并在请求返回前忽略重复点击；服务端手段是幂等键。前端置灰只能降低概率，真正的保证在服务端——这一点在订单页的专业版里会展开。

### 阶段六：支付（支付页）

提交订单后跳到 `/pay/:id`，页面展示应付金额与倒计时，用户选择支付方式。前端轮询查询支付结果，直到成功、失败或超时。

这一页是全项目最需要「清理」的地方：离开页面必须停掉轮询与倒计时，否则用户在别的页面会看到「支付成功」的弹窗，甚至重复发起请求。定时器在 `onUnmounted` 里清理，是这一章唯一不能偷懒的地方。

### 阶段七：回到会员中心

支付完成后进入 `/member/order`，按状态分页展示订单。切换状态时必须把页码重置为 1，否则会出现「切到待发货，显示第 5 页空白」。

## 按章节拆解

### Home页：请求编排

负责「多个接口怎么排」。判断标准是依赖关系：互不依赖的并发，有依赖的串行。首页三个楼层互不依赖，所以并发；分类页的「筛选选项」必须先于「商品列表」，所以串行。

### 一级分类页：URL 作为单一真源

负责「状态放哪」。筛选、排序、分页全部写进 query，组件内不保留副本。好处是刷新不丢、分享可用、浏览器前进后退天然正确。代价是每次改动都要走一次路由跳转，需要防抖。

### 二级分类页：复用与监听

负责「同组件不同参数」。`/category/101` 和 `/category/102` 复用同一个组件，`setup` 只执行一次，因此必须监听路由参数。这是 Vue3 入门第八节的坑，在真实项目里第一次显形。

### 商品详情：派生状态

负责「选中的东西怎么变成价格」。规格树 → 可用组合 → 当前 SKU → 价格库存，是一条 `computed` 链。链上任何一环用 `watch` 手动同步，就会出现「点了颜色价格不变」。

### 登录页：身份的唯一入口

负责「token 从哪来、到哪去」。写入、读取、清理三件事分别落在登录页、请求拦截器、响应拦截器。任何页面自己判断登录状态，都是架构上的倒退。

### 购物车：同一份状态的多个视图

负责「一处修改、多处反映」。购物车列表、导航角标、结算按钮数量读的是同一个 store。这也解释了为什么购物车必须先学 Pinia：用 props 传三层，改一次要动五个文件。

### 订单页：不可逆操作的边界

负责「什么时候允许提交、提交后怎么办」。前端能做的是防重复点击与状态提示，真正的幂等必须靠服务端。前端如果把幂等当成自己的责任，一定会漏。

### 支付页：异步状态机

负责「等待中的状态怎么表达」。待支付、支付中、成功、失败、超时，五个状态互斥，用状态机描述比用一堆布尔值可靠。轮询必须有终止条件，否则就是一本书里最贵的 bug。

## 经验教训

**第一，状态的位置比状态的写法重要。** 同一个 `count`，放组件里、放 store 里、放 URL 里，行为完全不同。选错位置，后面所有代码都在为这个错误买单。

**第二，能派生就不要同步。** 金额、全选、库存可用性都是派生值。凡是「在 A 变化时记得去改 B」的代码，都是未来的 bug。

**第三，异步资源必须有生命周期。** 定时器、轮询、事件监听、第三方实例，装的时候就要想好什么时候拆。支付页只是把这个问题放大到「会重复扣款」的程度。

**第四，前端的边界要认清。** 幂等、金额校验、库存扣减，最终都要服务端兜底。前端做的是体验，不是保证。
