# 支付页 · 练习与自测

> 题量：是非 10 / 选择 10 / 配对 8 / 情境 3 / 代码阅读 3 / 延伸思考 2。答案紧跟各区块。

## 一、是非题（10 题）

1. 支付页应该在 `onMounted` 里创建订单，这样用户就不用手动提交了。
2. 支付页的订单号应该放在 `route.params` 里，因为它比 `query` 更「正规」。
3. `route.query.payResult` 拿到的值是布尔类型。
4. 只要 `payResult=true`，就可以认定这张订单已经支付成功。
5. 金额一定要用服务端返回的 `payMoney`，前端不能重算。
6. 拼接支付地址时，`redirect` 参数的值必须经过 `encodeURIComponent`。
7. 微信支付在 PC 端可以直接用一个 `a` 标签跳转到收银台。
8. 倒计时的起点应该由前端写死为 30 分钟。
9. `setInterval` 的回调在后台标签页里仍然会严格按每秒一次执行。
10. 支付成功后跳转应该用 `router.replace` 而不是 `router.push`。

### 答案解析

1. **错**。用户每刷新一次就会多一张订单，这是最典型的一类生产事故。创建订单只发生在订单页的提交按钮里。
2. **错**。`params` 依赖内存中的路由状态，刷新之后参数就丢了，页面会白屏。`query` 在地址栏里，刷新与分享都能保留。
3. **错**。URL 参数永远是字符串，拿到的是 `'true'` / `'false'`。
4. **错**。地址栏用户可以随意编辑，必须以服务端返回的订单状态为准。
5. **对**。价格、运费、优惠都只有服务端知道；前端重算等于把定价权交给用户。
6. **对**。`redirect` 的值本身是一个 URL，里面可能带 `?` 与 `&`，不编码就会被外层参数切碎。
7. **错**。PC 端微信支付需要扫码，那个 `a` 标签的 `href` 只能是 `javascript:;`，真实现要换成二维码。
8. **错**。起点必须来自服务端的订单过期时间，否则用户刷新就能无限续期。
9. **错**。Chrome 88 起对后台标签页的链式定时器实施重度节流，最短间隔被拉长到 1 分钟。
10. **对**。否则用户按返回键会回到「请尽快完成支付」那一屏。

   A. 报错　B. 只生效最后一个　C. 两个定时器同时减，倒计时倍速消失　D. 无影响

10. `dayjs.unix(1799).format('mm分ss秒')` 显示为？
    A. `29分59秒`　B. `1799秒`　C. `00分00秒`　D. `59分29秒`

### 答案解析

1. **B**。只读语义，路径带 id，天然幂等。
2. **C**。配合 `?.` 才能在首屏数据未到时安全渲染；`null` 会在 `payInfo.payMoney` 处直接抛错。
3. **B**。可选链，在值为 `undefined` / `null` 时短路返回 `undefined`，而不是抛异常。
4. **B**。这是「这笔钱」与「这张订单」之间唯一的关联凭据。
5. **C**。把整串 URL 里的 `:`、`/`、`?`、`=` 都转义，使其可以安全地作为一个外层的参数值。
6. **C**。`Boolean('false')` 是 `true`，字符串非空即为真值。
7. **C**。回跳参数只能做乐观渲染，最终以账本为准。
8. **B**。同时要把 `time.value` 归零，避免出现负数显示。
9. **C**。两个 `interval` 各减一次，1 秒实际掉了 2 秒。
10. **A**。`unix(1799)` 是「距纪元 1799 秒」，`mm` 取分、`ss` 取秒。

## 四、情境分析（3 题）

### 情境 1：改个地址栏就变成了「支付成功」

用户反馈：付款时网络断了，页面跳回 `/paycallback?payResult=false`，直接显示失败。他顺手把 `false` 改成 `true` 回车，页面显示「支付成功」，但订单列表里依然是「待付款」。

**问**：页面为什么会这样？这算 bug 吗？该在哪一层修？

**答**：`/paycallback` 只读了地址栏参数做渲染，所以改地址栏就能改结果——这是预期内的，因为回跳参数本来就不可信。不算严重 bug 的前提是：**订单状态没有被真的改成已支付**。这个案例里订单列表仍是「待付款」，说明服务端没有跟着地址栏走，这是正确的。

要修的是前端的显示逻辑：进页面后用 `getOrderAPI(route.query.orderId)` 查一次真实状态，用它的结果覆盖乐观渲染；同时可加一条提示「状态确认中…」。真正的订单状态变更只由服务端之间的异步通知完成。

### 情境 2：用户切了个标签页，倒计时慢了五分钟

用户投诉：订单倒计时还剩 25 分钟时去别的标签页看了会儿商品，回来发现还剩 24 分 55 秒。实际已经过去 5 分钟了。

**问**：成因是什么？两种修法。

**答**：成因是 Chrome 88 起对后台标签页的链式定时器做了重度节流，回调间隔最长可达 1 分钟；而代码是「每触发一次就减一」，回调次数少了，减的次数自然少了。

修法一（推荐）：改成差值式，每次回调都用 `expireAt - Date.now()` 重算剩余秒数，这样即使回调被延迟，算出来的值依然正确。

修法二：监听 `visibilitychange`，页面重新可见时立即重算一次并重启定时器。两种可以叠加使用，前者保证数值正确，后者保证回来的瞬间就显示正确值。

### 情境 3：生产环境的回跳地址写成了 localhost

上线后用户付款成功，支付宝那边显示「支付完成」，但用户回到网站后看到的是空白页，控制台里报 `ERR_CONNECTION_REFUSED`。

**问**：最可能的原因？上线前该怎么避免？

**答**：`backURL` 还是开发环境的 `http://127.0.0.1:5173/paycallback`，用户浏览器被送回了自己机器的 5173 端口，那里什么都没有。

避免方式有三条：一，把 `baseURL` 与 `backURL` 放进环境变量（`.env.production`），不要硬编码在组件里；二，回跳域名必须与后端在支付平台登记的白名单一致，部署前逐项核对；三，在构建时加一条断言或 CI 检查，生产包里出现 `127.0.0.1` 或 `localhost` 就直接失败。

## 五、代码阅读（3 题）

### 题 1

```js
const start = (currentTime) => {
  time.value = currentTime
  timer = setInterval(() => {
    time.value--
  }, 1000)
}
```

**问**：这段代码有四处问题，分别是什么？

**答**：一，没有在开头 `clearInterval(timer)`，重复调用会叠加多个定时器；二，没有终止条件，会减到负数；三，参数是「剩余秒数」而不是「过期时间」，起点由调用方随意决定，容易被写死；四，没有任何到 0 后的回调，外部无从得知订单已超时。

### 题 2

```vue
<span class="tit">支付{{ $route.query.payResult ? '成功' : '失败' }}</span>
```

**问**：为什么这行代码永远显示「成功」？

**答**：`query` 里的值都是字符串。当 `payResult=false` 时，`$route.query.payResult` 是字符串 `'false'`，而任何非空字符串在条件判断里都是真值，所以三元表达式永远走「成功」分支。应改为 `$route.query.payResult === 'true'`，并且最终以服务端订单状态为准。

### 题 3

```js
const payUrl = `${baseURL}pay/aliPay?orderId=${route.query.id}&redirect=${backURL}`
```

**问**：这里省掉了什么？会造成什么问题？

**答**：省掉了 `encodeURIComponent(backURL)`。当 `backURL` 带查询参数（如 `?from=pc`）时，其中的 `?` 与 `&` 会被支付服务当成自身的参数分隔符，`redirect` 被截断成前半段，用户回跳后丢失参数；更糟的是可能把 `from=pc` 变成一个意外生效的外部参数。应改为 `redirect=${encodeURIComponent(backURL)}`。

## 六、延伸思考（2 题）

1. 如果支付的「异步通知」延迟了，用户已经在结果页看到「支付成功」，而服务端还认为订单未支付。这个不一致该怎么处理？

   **思路**：这属于最终一致性，正常存在，通常持续几秒到几十秒。处理方式分三层：展示层给一个「支付结果确认中」的过渡态，而不是直接钉死「成功」；轮询层在结果页用较短间隔（如 2 秒、最多 5 次）查询订单状态，拿到权威结果后停止；兜底层由服务端在收到通知后主动推送/标记，前端刷新时自然纠正。关键判断是——**「用户看到什么」可以乐观，「系统认定什么」必须等到账**，两者之间要留一个诚实的中间状态。

2. 为什么说「支付页不创建订单」这件事，直到今天仍然是很多团队的线上事故来源？你觉得根源在框架、在人，还是在流程？

   **思路**：技术上这是极其容易犯的错——把 `createOrderAPI` 写在 `onMounted` 里，代码看起来完全合理，测试时也不报错。根源主要在流程：这类 bug 只在「用户刷新」「从支付页返回」这些非主干路径上触发，手工点一遍主流程根本走不到，必须靠「幂等键 + 服务端去重」这种不依赖前端自觉的兜底。所以成熟的团队不会去争论「前端要不要写得更小心」，而是让重复提交在服务端不可能生效——把正确性从前端的纪律，变成系统的约束。

## 自测标准

- 能说清支付页为什么不创建订单、订单号为何必须在 URL 里：合格
- 能正确拼接带编码的回跳地址，并用服务端订单状态复核支付结果：良好
- 能写出不漂移、不泄漏、可重复启动的倒计时，并解释后台节流为何让「每秒减一」失效：优秀
