# 支付页

> 支付页是整条链路上唯一会被「别的网站」接管的一环。用户在这里离开你的应用，去一个你不拥有的收银台，然后再被送回来。这一章要讲的就是：怎么把他送出去、怎么确认他付了、以及在这段时间里那个数字为什么在往下掉。

## 一、支付页的位置：链条上唯一被外部接管的一环

前面几章的链路是闭合的：购物车、结算页、订单页，数据都在自己的应用里流动。到了支付页，这条链第一次被切开：

```
购物车 → 结算页 → 订单（生成编号）→ 支付渠道（跳出应用）→ 回到支付结果页 → 订单状态变成「已支付」
```

中间那一步「支付渠道（payment channel）」——支付宝、微信、银联——不属于你。用户点击「支付宝支付」之后，浏览器离开你的单页应用，进到支付宝的收银台，在那里完成鉴权与扣款，然后被重定向回你事先指定的一个地址。

这个事实决定了本章所有细节的形状：

1. **支付页本身是只读的。** 它不创建订单，只在订单已存在的前提下展示「应付多少、还剩多久、可以怎么付」。
2. **它必须能刷新还在。** 用户在收银台付款失败返回、或者手动刷新，页面都得能重新加载出来——所以订单号必须放在 URL 里。
3. **它不能相信从外部回来的任何参数。** 回跳的地址栏是用户可编辑的，`payResult=true` 这串字符谁都能手动敲上去。

订单页在提交成功后做了 `router.push({ path: '/pay', query: { id } })`，支付页就是接住这个 `id` 的地方。这个分工是本章的骨架。

## 二、路由与接口：订单号从 URL 来，数据从服务端来

支付页最简的形态只需要一个接口：

```js
// apis/pay.js
import request from '@/utils/http'

export const getOrderAPI = (id) => {
  return request({ url: `/member/order/${id}` })
}
```

注意它是 `GET`，路径里带订单 id。语义上就是「把编号为 xxx 的订单拿给我看」，天然幂等，刷多少次结果都一样——这与上一章下单那个 `POST` 形成对照。

组件里取数据：

```vue
<script setup>
import { onMounted, ref } from 'vue'
import { useRoute } from 'vue-router'
import { getOrderAPI } from '@/apis/pay'

const route = useRoute()
const payInfo = ref({})

const getPayInfo = async () => {
  const res = await getOrderAPI(route.query.id)
  payInfo.value = res.result
}

onMounted(() => getPayInfo())
</script>
```

三件事要说清楚。

**第一，`route.query.id` 而不是 `route.params.id`。** 上一章选择了 `query`，理由是刷新与分享都保留；这里就是兑现那个选择的地方。如果当初用了 `params`，刷新之后 `id` 就没了，页面直接白屏。

**第二，`payInfo` 的初始值必须是 `{}` 而不是 `null`。** 模板里要写 `payInfo.payMoney?.toFixed(2)`，如果初始值是 `null`，第一次渲染就会在 `payInfo.payMoney` 上抛错；给个空对象再加上可选链，首屏才安全。

**第三，`onMounted` 里没有判空。** 用户直接在地址栏敲 `/pay` 进来时 `route.query.id` 是 `undefined`，请求会打到 `/member/order/undefined`，后端返回 400 或 404。健壮的写法要先拦截：

```js
onMounted(() => {
  if (!route.query.id) {
    ElMessage({ type: 'warning', message: '订单不存在，请重新下单' })
    router.replace('/')
    return
  }
  getPayInfo()
})
```

这类「入口参数缺失」的处理在前面几章已经出现过（一级分类页的 `id`、商品详情的 `id`），套路是一致的：**先校验入口参数，再发请求**。

## 三、渲染：一笔订单需要展示的四个字段

支付页的模板看起来很长，其实真正有信息量的只有四处：

```vue
<div class="pay-info">
  <div class="tip">
    <p>订单提交成功！请尽快完成支付。</p>
    <p>支付还剩 <span>{{ formatTime }}</span>, 超时后将取消订单</p>
  </div>
  <div class="amount">
    <span>应付总额：</span>
    <span>¥{{ payInfo.payMoney?.toFixed(2) }}</span>
  </div>
</div>
```

逐个看：

| 字段 | 来源 | 容易写错的地方 |
|---|---|---|
| 应付金额 `payMoney` | 服务端返回的订单快照 | 前端不能重算，这是上一章定下的规矩在这一页的延续 |
| 倒计时 `formatTime` | 订单创建时间 + 超时时长 | 不能前端写死 30 分钟，否则用户刷新就能续命 |
| 支付渠道列表 | 静态模板 | 微信不能直接跳转，只能出二维码 |
| 订单号 | `route.query.id` | 只用于请求，不必展示，但要在排查时能拿到 |

金额那句 `payInfo.payMoney?.toFixed(2)` 值得停一下。`toFixed` 是渲染层的格式化，只负责显示两位小数；真正的金额计算必须发生在服务端，且用「分」为单位的整数（购物车那一章已经讲过浮点误差的来历）。前端调 `toFixed` 只是为了让 `199` 显示成 `199.00`。

支付方式的模板是半静态的：

```vue
<div class="item">
  <p>支付平台</p>
  <a class="btn wx" href="javascript:;"></a>
  <a class="btn alipay" :href="payUrl"></a>
</div>
```

微信那个 `href="javascript:;"` 意味着「点了什么也不做」——因为微信支付在 PC 端需要扫码，不能靠一个链接跳过去。支付宝那个用 `:href="payUrl"` 绑定，因为它的地址是动态拼的。这两个 `a` 标签的区别，就是「什么时候可以跳转」的分界线。

## 四、跳转支付：拼一个能回来的地址

真正发起支付靠的是一串 URL：

```js
const baseURL = 'http://pcapi-xiaotuxian-front-devtest.itheima.net/'
const backURL = 'http://127.0.0.1:5173/paycallback'
const redirectUrl = encodeURIComponent(backURL)
const payUrl = `${baseURL}pay/aliPay?orderId=${route.query.id}&redirect=${redirectUrl}`
```

拆成三段看：

1. **`baseURL`** 是支付服务的地址，指向教学环境的沙箱网关。它和你自己的域名不同——这就是为什么必须整页跳转（第五节）。
2. **`orderId`** 把「付哪一张单」告诉支付服务。这里是唯一能让服务端把「这笔钱」和「这张订单」关联起来的凭据。
3. **`redirect`** 告诉支付服务「付完之后把人送回哪儿」。它必须是完整 URL，而且必须 `encodeURIComponent`。

**为什么必须编码？** `redirect` 的值本身是 `http://127.0.0.1:5173/paycallback`，干干净净，看起来不编码也能用。可一旦回跳地址自己要带参数——比如 `http://127.0.0.1:5173/paycallback?from=pc&lang=zh`——不编码就变成：

```
...&redirect=http://127.0.0.1:5173/paycallback?from=pc&lang=zh
```

服务端按 `&` 切分参数，于是 `redirect` 只拿到 `http://127.0.0.1:5173/paycallback?from=pc`，后半截 `lang=zh` 被当成了网关自己的参数。回跳地址被悄悄截断，用户在结果页上会丢掉一个参数。

编码之后，`?`、`&`、`=` 都变成 `%3F`、`%26`、`%3D`，整串才是一个不可分割的值：

```js
const backURL = 'http://127.0.0.1:5173/paycallback?from=pc&lang=zh'
// 编码后：http%3A%2F%2F127.0.0.1%3A5173%2Fpaycallback%3Ffrom%3Dpc%26lang%3Dzh
```

这是一个通用规则：**任何 URL 参数的值如果本身是 URL，就必须编码**。前面登录页的 `redirect` 参数、一级分类页的 `path` 参数，都遵循同一条。判断标准只看一句话：这个值里会不会出现 `&`、`=`、`?`、`#`、`+` 或空格——只要有一个，就必须编码；而「现在恰好没有」不构成理由，因为回跳地址明天就可能加上参数。

还有一条工程约束：`backURL` 的域名通常要和后端在支付平台上登记的「回调白名单」一致。教学环境里写 `127.0.0.1:5173` 能用，是因为沙箱允许；线上如果写错域名，网关会直接拒绝跳转，用户点了支付什么都不发生。

## 五、为什么是整页跳转，而不是 ajax

这一节回答一个初学者常问的问题：既然我们全程在用 axios，为什么不能 `await payAPI()` 就完事？

因为**支付渠道是第三方域**（third-party domain）。浏览器的同源策略（Same-Origin Policy）不允许你的脚本读取 `alipay.com` 的响应，更不允许你把用户输入的支付密码送到你自己的服务器上。所以支付这一步在协议层面只有两种可能：

- **表单 POST 到第三方域**：整页提交，浏览器跳走。
- **跳转到第三方页面**：整页跳转，浏览器跳走。

两种都会让当前文档卸载。区别只在于是 `GET` 还是 `POST`。

这直接引出了几个工程后果：

| 后果 | 原因 |
|---|---|
| 跳走前必须把状态存好 | 文档卸载，内存里的 ref 全没了 |
| 回来时不能指望组件状态 | 回来是一次全新的页面加载 |
| 订单号必须能重新取到 | 只能靠 URL 里的 `query` 或服务端订单记录 |
| 支付结果必须重新查 | 跳走期间发生了什么，前端一无所知 |

所以那一串 `payUrl` 不是「为了省事才用 a 标签」，而是唯一的可行路径。同样的道理，很多支付集成要求把用户信息以隐藏表单字段的形式 `POST` 出去：

```html
<form id="payForm" action="https://gateway.example.com/pay" method="POST">
  <input type="hidden" name="orderId" value="123">
  <input type="hidden" name="amount" value="19900">
  <input type="hidden" name="redirect" value="https://shop.example.com/paycallback">
</form>
```

`POST` 的好处是参数不出现在地址栏，也不会被浏览器历史记录与代理日志留存。教学项目用 `GET` 是因为沙箱简化，但工业级集成里 `POST` 才是常态。

## 六、支付结果页：`'true'` 是字符串，而且不能信

支付回来之后，用户落到 `/paycallback`。这个路由的路径**必须与后端约定的完全一致**，因为支付服务只认那个字符串：

```js
{
  path: 'paycallback',
  component: () => import('@/views/Pay/PayBack.vue'),
}
```

页面上的成败判断写在模板里：

```vue
<span class="iconfont icon-queren2 green" v-if="$route.query.payResult === 'true'"></span>
<span class="iconfont icon-shanchu red" v-else></span>
<p class="tit">支付{{ $route.query.payResult === 'true' ? '成功' : '失败' }}</p>
```

这里有第一个坑：**`query` 里的值永远是字符串**。`$route.query.payResult` 拿到的不是布尔 `true`，而是字符串 `'true'`。写 `v-if="$route.query.payResult"` 会得到一个更糟的结果——字符串 `'false'` 在 JavaScript 里是真值，于是支付失败也会显示成功。

第二个坑更严重：**这串参数不可信**。任何人都可以在地址栏把 `payResult=false` 改成 `payResult=true`，页面立刻显示「支付成功」。如果后端也只凭这个参数就把订单标成已支付，那就是一个可以直接白拿商品的漏洞。

正确的做法是两条都要：

```js
onMounted(async () => {
  // 1. 先用 query 做一次乐观渲染（只是给用户一个即时反馈）
  const payResult = route.query.payResult === 'true'

  // 2. 再用订单状态做权威判定
  const res = await getOrderAPI(route.query.orderId)
  orderInfo.value = res.result
  isPaid.value = res.result.orderState === 2   // 以服务端为准
})
```

注意这里查的是 `route.query.orderId`——支付服务回跳时用的参数名是它自己定的，和前面支付页的 `id` 不是同一个名字。这类「同一份数据在不同环节叫不同名字」的情况，看接口文档比看代码更快。

**真正的确认动作发生在服务端之间。** 支付宝在你付款成功后会异步 `POST` 一条通知到你在开放平台登记的「异步通知地址」（notify_url），后端收到后才把订单状态改为已支付并扣减库存。前端的 `/paycallback` 页面只是一个「告知用户结果」的展示层，它不承担任何状态变更的职责。

这个分工可以用一句话记住：**用户看到的成功不等于系统认定的成功。**

## 七、倒计时：一个 composable 的三个约束

支付页要显示「还剩多少时间」，这段逻辑被抽成了一个组合式函数（composable）：

```js
import { computed, onUnmounted, ref } from 'vue'
import dayjs from 'dayjs'

export const useCountDown = () => {
  let timer = null
  const time = ref(0)

  const formatTime = computed(() => dayjs.unix(time.value).format('mm分ss秒'))

  const start = (currentTime) => {
    time.value = currentTime
    timer = setInterval(() => {
      time.value--
    }, 1000)
  }

  onUnmounted(() => {
    timer && clearInterval(timer)
  })

  return { formatTime, start }
}
```

不到二十行，但有三个约束必须补上，否则就会出事。

**约束一：起点必须来自服务端。** `start(currentTime)` 的参数不该是前端写死的 `1800`。它应该是「订单过期时间 − 当前时间」：

```js
const start = (expireAt) => {
  time.value = Math.max(0, Math.floor((new Date(expireAt) - Date.now()) / 1000))
  // ...
}
```

如果前端写死 30 分钟，用户刷新页面倒计时就重置，等于给了一个无限续期的漏洞。

**约束二：到 0 必须停。** 原始写法里 `time.value--` 会一路减到负数，显示成 `-1分-30秒`。要加一个终止条件：

```js
timer = setInterval(() => {
  time.value--
  if (time.value <= 0) {
    time.value = 0
    clearInterval(timer)
    timer = null
    onExpire?.()        // 通知外部：订单超时了
  }
}, 1000)
```

**约束三：重复 `start` 不能叠定时器。** 如果用户在页面上触发了两次 `start`（比如失败后重试），就会有两个 `interval` 同时在减，倒计时以两倍速消失：

```js
const start = (currentTime) => {
  if (timer) clearInterval(timer)   // 先清掉旧的
  time.value = currentTime
  timer = setInterval(/* ... */)
}
```

至于 `dayjs.unix(time.value).format('mm分ss秒')`，它的作用是把「还剩 1799 秒」变成「29分59秒」。注意 `mm` 是两位分钟，超过 59 分钟会从 `60` 绕回 `00`——支付超时一般在半小时以内，所以这个写法够用；如果真的需要显示小时，格式串要改成 `HH时mm分ss秒`。

`onUnmounted` 里清定时器是底线。少了这一句，用户点「进入首页」之后定时器还在后台跑，控制台里能看到组件已经销毁但 `time` 还在变——这类泄漏在单页应用里不会报错，只会慢慢吃掉性能。

## 八、工程实践与常见坑

1. **订单号用 `query` 不用 `params`**，否则刷新即白屏。这一条在订单页已经决定过一次，支付页是它在另一个位置的兑现。
2. **`route.query` 里的值全是字符串。** `payResult === 'true'`、`id` 是字符串而非数字，参与运算前要显式转换。
3. **`payInfo` 初始值给 `{}` 而不是 `null`**，配合可选链 `payInfo.payMoney?.toFixed(2)` 才安全。
4. **金额只显示、不计算。** 前端重算金额在支付页是最严重的错误之一——用户改一下内存里的 `payInfo.payMoney` 就能少付钱。
5. **URL 参数里套 URL 必须 `encodeURIComponent`**，`redirect`、`backURL`、`returnUrl` 都是。
6. **回调路径必须和后端登记的一致**，`paycallback` 少一个字母就回不来。
7. **不要相信跳转回来的参数。** `payResult`、`trade_status`、`amount` 都要用服务端订单状态复核。
8. **支付成功后跳 `replace` 而不是 `push`**，避免用户按返回键回到「请尽快完成支付」的页面。
9. **`setInterval` 三件套：先清旧、到 0 停、卸载时清。** 缺任何一个都会变成 bug，而且是不报错的那种。
10. **倒计时的起点取服务端时间。** 前端 `Date.now()` 可以被改系统时间绕过，能造成「订单已超时但仍显示可支付」。
11. **微信 PC 端不能直接跳转。** 需要扫码，所以那个 `a` 标签的 `href` 只能是 `javascript:;`，真实现要换成二维码组件。
12. **支付失败要给出下一步。** 只显示一个红叉没有意义，应该提供「重新支付」「取消订单」两个动作。
