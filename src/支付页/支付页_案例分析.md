# 支付页 · 案例分析

> 四个案例分别对应本章的四条命脉：卡号为什么不能落在自己手里、支付结果到底由谁说了算、倒计时背后锁的是什么、以及浏览器为什么会偷偷放慢你的计时器。

## Case 1：从 TJX 到 PCI DSS——为什么收银台必须是别人的

### 背景

2000 年代中期，电商刚成规模，绝大多数商户的做法很朴素：在自己的网站上放一个表单，让用户输入卡号，然后由自己的服务器转发给银行。卡号就存在自己的数据库里，「下次再来就不用重输了」。

听起来很方便。但它意味着：只要能攻进你的数据库，就能拿到几百万张可以直接刷的卡。

### 事件经过

2005 年，美国零售商 TJX（TJ Maxx、Marshalls 的母公司）公开披露数据泄露，事后确认约 4500 万张银行卡信息被窃取，是有记录以来规模最大的卡数据泄露之一。攻击者据称是通过商场无线网络的弱加密（WEP）进入内网，随后在服务器上潜伏了将近两年。

2008 年，支付处理商 Heartland Payment Systems 披露泄露，涉及约 1.3 亿张卡，攻击手法是往处理程序里注入恶意代码，实时截获经过的卡号。

这两起事件把整个行业推到了同一个结论前面：**只要卡号在你手里，卡号就会被偷。**

于是有了 PCI DSS（Payment Card Industry Data Security Standard）。它的核心思路不是「让商户更安全地存卡号」，而是「尽一切可能让商户根本不碰卡号」。在这个标准下，最省事的合规方式就是把用户直接送到持牌支付机构的收银台，商户只收到一个结果和一个令牌化的编号。

### 与本章的关系

第一节说「支付页是唯一会被外部接管的一环」，Case 1 解释了它为什么必须如此。

这不是「Vue 还没学到位所以只能跳转」，而是行业用两起上亿规模的泄露事故换来的架构决定：你的前端不接触敏感凭证，你的后端也不接触。支付页那个 `a` 标签指向第三方域名，正是这条规则在代码里的样子。

上一节提到的「表单 POST 到第三方域」也是同一个道理——参数不出现在地址栏，浏览器历史、代理日志、截图都不会留下痕迹。

### 参考资料

- [PCI Security Standards Council 官网](https://www.pcisecuritystandards.org/) —— PCI DSS 的发布方，标准文本可免费下载。
- [PCI DSS（维基百科）](https://en.wikipedia.org/wiki/Payment_Card_Industry_Data_Security_Standard) —— 版本演进、适用对象与争议，适合快速建立整体印象。
- [TJX 数据泄露（维基百科）](https://en.wikipedia.org/wiki/TJX_Companies#Computer_security_breach) —— 事件时间线与后续和解金额。

## Case 2：从 IPN 到 Webhook——支付结果到底由谁说了算

### 背景

支付渠道把用户送回你的网站时，会在地址栏带上一串参数，比如 `payResult=true`。早期很多购物车就直接拿这串参数判断成败。

问题在第六节已经讲过：地址栏是用户可以编辑的。这不只是「用户可能作弊」，还有一个更麻烦的情况——**用户付了钱，但回跳的那一步失败了**。网络断了、用户提前关了页面、浏览器崩了，回跳参数永远不会到达。

如果只靠回跳，就会同时出现两种错误：没付钱的显示成功，付了钱的显示失败。

### 事件经过

2004 年，PayPal 推出 IPN（Instant Payment Notification）。它的做法是：**不从浏览器走，而是从服务器到服务器**。用户付款成功后，PayPal 的服务器主动向商户登记的地址 `POST` 一条通知，商户收到后回一个确认，这条通知才算完成。

这条通道与用户的浏览器完全无关，所以用户关页面、断网、清缓存都影响不到它。同时它天然解决了「用户伪造」的问题——伪造者得先能伪造 PayPal 服务器的请求，还得通过签名验证。

2010 年代，Stripe 把这套机制推广成更通用的名字：Webhook。Stripe 的文档里有一条现在被广泛抄走的建议——**不要依赖 Webhook 的到达顺序，也不要假设它只到达一次**；每个事件带唯一 id，收到重复的要按幂等处理。

### 与本章的关系

第六节说「用户看到的成功不等于系统认定的成功」，Case 2 是这句话的行业出处。

前端 `/paycallback` 页面里那句 `orderState === 2`，就是在向服务端要一个权威答案；而服务端的那个答案，来源是它自己收到的 Webhook / 异步通知，不是浏览器的回跳。

这也解释了为什么回跳参数仍然值得读——它是**乐观渲染**：让用户在 200 毫秒内看到反馈，而不是等到接口返回。但乐观归乐观，最终以账本为准。

### 参考资料

- [PayPal：IPN 介绍](https://developer.paypal.com/api/nvp-soap/ipn/IPNIntro/) —— 官方文档，包含验证流程与重发机制。
- [Stripe：Webhooks 最佳实践](https://docs.stripe.com/webhooks) —— 关于「至少一次」「乱序到达」「幂等处理」的完整说明。
- [MDN：Same-origin policy](https://developer.mozilla.org/zh-CN/docs/Web/Security/Same-origin_policy) —— 理解为什么这条通道必须绕开浏览器。

## Case 3：30 分钟——倒计时背后锁的是什么

### 背景

电商的库存不是「无限」的。用户在结算页停留的这段时间里，那件商品到底算不算卖掉了？

如果不锁，两个人同时下单，最后一个付款的会发现没货了；如果永久锁，一个犹豫不决的用户能把最后一件商品锁一整天。

### 事件经过

2011 年，淘宝第一次把双十一做成全民活动，当天交易额 33.6 亿元。在这种瞬时流量下，「下单未付款」的订单如果不能自动释放，库存很快就会被虚占清空。淘宝后来的规则是：**订单提交后一段时间内未支付，系统自动关闭订单并释放库存**，具体时长在不同业务线里从 30 分钟到 24 小时不等。

铁路系统面临的是同一个问题的极端版本。12306 在 2012 年前后上线了「订单保留 30 分钟」的机制：抢到票之后必须在 30 分钟内完成支付，否则席位回到票池。这个设计让「抢票」变成了一场有明确时限的竞赛，也让 2018 年推出的「候补购票」成为可能——候补之所以能成立，正是因为系统知道哪些席位会在什么时候被释放。

在技术实现上，这类「到点自动关单」通常不靠页面上的倒计时触发，而是靠服务端的定时任务或 Redis 的键过期（TTL）。页面上的倒计时只是一个**读数的镜子**，真正的时间由服务端掌握。

### 与本章的关系

第七节说「起点必须来自服务端」，Case 3 是这个要求的业务背景。

倒计时不是装饰。它对应服务端的一个真实约定：到点之后这张订单会被关闭、库存会被释放。前端如果把时间写死 30 分钟、每次刷新重置，用户看到的就是一个永远不会到期的倒计时，而他以为还能付的钱，实际上早就随着订单关闭而无法支付了。

这也解释了为什么到 0 之后前端不该继续显示「可以支付」——一旦服务端关单，支付接口会直接拒绝，用户体验就变成了「点了没反应」。

### 参考资料

- [淘宝开放平台：交易订单](https://open.taobao.com/doc.htm) —— 搜索「订单超时关闭」相关文档，能看到超时规则在产品层的表达。
- [12306 官方网站](https://www.12306.cn/) —— 购票流程中关于订单保留时间的说明，是最直接的公开依据。
- [Redis：EXPIRE 命令](https://redis.io/docs/latest/commands/expire/) —— 键过期是实现「到点关单」最常用的一种底层机制。

## Case 4：Chrome 88 的后台节流——你的秒表会自己变慢

### 背景

`setInterval(fn, 1000)` 看起来是个精确的秒表：每 1000 毫秒执行一次。但从它诞生起，它就只是一个「大约每秒一次」的约定——浏览器要在主线程空闲时才执行回调，页面卡一下，回调就晚到。

单页应用普及后，这个问题被放大：一个页面可能同时有十几个定时器，其中大多数在用户切到别的标签页时毫无意义，却仍在消耗电量与 CPU。

### 事件经过

2021 年 1 月，Chrome 88 上线了一项变更：对**后台标签页**中的链式定时器（即回调里再次调用 `setTimeout` / `setInterval` 形成的链）实施重度节流，最短间隔被拉长到 **1 分钟**。官方博客给出的理由很直接：这类定时器在后台几乎从不被用户看到，却持续唤醒 CPU，是移动设备耗电的重要来源。

Firefox 与 Safari 也有类似的策略，只是阈值不同。这不是某一家浏览器的怪癖，而是现代浏览器的共识。

后果很具体：一个页面上的倒计时，在可见标签页里走得好好的，用户切到别的标签页看商品信息，五分钟后切回来，会发现倒计时只走了 5 秒，而不是 300 秒。

### 与本章的关系

第七节那个 `time.value--` 的写法，正是会被节流影响的那种实现——它假设「每秒减一」这个动作会真实地每秒发生一次。

正确的修法不是去和浏览器对抗，而是**不要数秒，每次都用当前时间去减终点**：

```js
// 慢：依赖定时器跳动的次数
timer = setInterval(() => { time.value-- }, 1000)

// 稳：每次都重新算剩余秒数
const tick = () => {
  time.value = Math.max(0, Math.floor((expireAt - Date.now()) / 1000))
  if (time.value === 0) clearInterval(timer)
}
timer = setInterval(tick, 1000)
```

这样即使浏览器把回调延迟了一分钟，下一次回调算出来的仍然是正确值——因为答案来自时钟，而不是来自「减了多少次」。

这条经验可以外推到所有与真实时间相关的逻辑：**计数式实现必然漂移，差值式实现才收敛。** 进度条、轮询、会话过期，都是同一个道理。
