# 支付页

> 支付页是整条链路上唯一会被「别的网站」接管的一环。用户在这里离开你的应用，去一个你不拥有的收银台，然后再被送回来。这一章要讲的就是：怎么把他送出去、怎么确认他付了、以及在这段时间里那个数字为什么在往下掉。

## 一、支付页的位置：链条上唯一被外部接管的一环

在餐厅吃饭，前厅是你的：迎宾、点菜、上菜、加水，全在你自己的地盘上完成。可一旦客人说「买单」，他就得走到前台，把卡递进那台不属于你的机器里。刷完卡，机器吐出一张签购单，客人签完字，才算真的付了。

支付页就是那个「从前厅走到前台」的时刻。

前面几页的数据都在你自己的应用里打转：购物车、结算页、订单页，谁都没离开过。到了支付页，第一次出现了别人的地盘——支付宝、微信、银联，这些收银台不归你管。用户点一下「支付宝支付」，浏览器就离开了你的网站，进到支付宝的页面，在那儿验身份、输密码、扣钱，然后被送回你事先说好的那个门口。

这个事实把整章的规则都决定下来了：

1. **支付页自己不收钱，它只是张门票。** 它不创建订单，只告诉你「这单多少钱、还剩多久、能怎么付」。
2. **它必须能刷新还在。** 客人在前台刷卡失败又回来，或者手一抖按了刷新，页面都得重新长出来。
3. **从外面回来的人，说的话不能全信。** 门口那张「我已付款」的纸条，谁都能自己写一张。

## 二、路由与接口：订单号从 URL 来，数据从服务端来

去澡堂存包，人家给你一块牌子，上面写着「37 号」。你去取包，只要把牌子递过去，人家就知道该开哪个柜子——你不需要记住柜子里有什么。

支付页的订单号就是这块牌子。它是上一页递过来的：

```js
router.push({ path: '/pay', query: { id } })
```

而支付页接住它的方式是：

```js
const route = useRoute()
const payInfo = ref({})

const getPayInfo = async () => {
  const res = await getOrderAPI(route.query.id)
  payInfo.value = res.result
}
```

接口只有一个，而且是个「只读」的：

```js
export const getOrderAPI = (id) => {
  return request({ url: `/member/order/${id}` })
}
```

它是 `GET`，意思是「把 37 号柜子打开给我看看」，看一百次柜子里的东西都不会变。这和上一页那个 `POST`（「新开一个柜子」）正好相反。

这里有三件小事，每一件都是踩过坑才记住的。

**第一件：牌子要挂在门口，不能揣在兜里。** 订单号放在 URL 的 `query` 里，刷新之后还在；如果当初塞进 `params`，那就相当于把牌子记在脑子里——一刷新，人就失忆了，页面直接白屏。

**第二件：柜子还没打开时，得假设它是空的。** `payInfo` 的初始值给 `{}` 而不是 `null`，模板里再用 `?.` 兜一下：

```vue
<span>¥{{ payInfo.payMoney?.toFixed(2) }}</span>
```

不然第一眼看到的就是一个红报错，因为你还想在「空柜子」上找东西。

**第三件：没带牌子的人要拦下来。** 有人直接在地址栏敲 `/pay`，这就等于空着手来取包。得先问一句再放行：

```js
if (!route.query.id) {
  ElMessage({ type: 'warning', message: '订单不存在，请重新下单' })
  router.replace('/')
  return
}
```

## 三、渲染：一笔订单需要展示的四个字段

一张餐厅小票上密密麻麻印了一堆字，但你真正会看的只有四样：总共多少钱、还剩多久必须结账、能刷哪几种卡、单号是多少。

支付页一模一样的四样：

```vue
<div class="amount">
  <span>应付总额：</span>
  <span>¥{{ payInfo.payMoney?.toFixed(2) }}</span>
</div>
```

| 小票上的东西 | 支付页里的东西 | 最容易搞错的地方 |
|---|---|---|
| 总共多少钱 | `payMoney` | 前端不能自己算，只能照抄服务端给的数 |
| 还剩多久 | 倒计时 `formatTime` | 起点不能是自己掐表，得听服务端的 |
| 能刷哪几种卡 | 支付渠道列表 | 微信在电脑上不能跳，只能扫码 |
| 单号 | `route.query.id` | 只用来请求，不用印在脸上 |

金额那句 `toFixed(2)` 就像小票上的「¥199.00」——它只负责把 `199` 打扮成两位小数，不负责算账。真要算账，得用「分」为单位慢慢算（购物车那一章讲过为什么）。

再看支付方式那一段：

```vue
<a class="btn wx" href="javascript:;"></a>
<a class="btn alipay" :href="payUrl"></a>
```

微信那个 `href="javascript:;"` 翻译成人话就是「点了没反应」。这不是偷懒，是因为电脑上的微信支付要你掏手机扫码，光一个链接跳不过去。支付宝那个用 `:href="payUrl"`，因为它的地址是现拼的。

一个「点了没用」，一个「点了就走」，这两个 `a` 标签的区别，就是「什么时候能跳、什么时候跳不了」的分界线。

## 四、跳转支付：拼一个能回来的地址

医院转诊的时候，医生会写一张单子：请把这位病人送到 X 分院做检查，检查完送回 Y 门。

拼支付地址就是在写这张转诊单：

```js
const baseURL = 'http://pcapi-xiaotuxian-front-devtest.itheima.net/'
const backURL = 'http://127.0.0.1:5173/paycallback'
const redirectUrl = encodeURIComponent(backURL)
const payUrl = `${baseURL}pay/aliPay?orderId=${route.query.id}&redirect=${redirectUrl}`
```

这张单子上有三样东西：

1. **送到哪个分院**（`baseURL`）：这不是你的医院，所以只能「把人送过去」，不能「打电话问诊」。
2. **病人是哪一个**（`orderId`）：不说清楚，分院不知道给谁做检查。
3. **做完送回哪个门**（`redirect`）：不说清楚，人就在分院门口站着回不来了。

重点是第三样为什么必须「套个信封」。

寄信的时候，如果收信地址里本身就带逗号或者门牌号，你直接写在信封上，邮局会看不明白。正确做法是把这个「里面的地址」装进一个小信封，再贴到大信封上。

`encodeURIComponent` 就是那个小信封。

假设回跳地址是 `http://127.0.0.1:5173/paycallback?from=pc&lang=zh`，里面自带一个 `?` 和一个 `&`。不装信封直接拼：

```
...&redirect=http://127.0.0.1:5173/paycallback?from=pc&lang=zh
```

服务端拿到这串东西，一看到 `&` 就以为是「下一个参数开始了」，于是回跳地址只剩到 `from=pc` 为止，`lang=zh` 被当成了人家自己的参数。回来的路上，那个人的「语言偏好」就丢了。

装了信封之后：

```
...&redirect=http%3A%2F%2F127.0.0.1%3A5173%2Fpaycallback%3Ffrom%3Dpc%26lang%3Dzh
```

`?`、`&`、`=` 全变成了 `%3F`、`%26`、`%3D`，看上去像乱码，但邮局一眼就知道：从这里到那里，整段都是「回跳地址」这个值，谁也不许在中间插刀。

这条规矩是通用的：**只要一个参数的值本身是个网址，就得套信封。** 登录页那个 `redirect`、分类页那个 `path`，都是同一件事。「现在这个地址恰好没有 `&`」也不构成理由——明天有人给它加个参数，不套信封的那段代码就断了。

还有一件事：信封上写的地址，得是邮局认可的地址。上线之后 `backURL` 的域名必须和后端在支付平台登记的那个一模一样，写错了，支付服务会直接拒收——用户点了按钮，页面一动不动，什么提示都没有。

## 五、为什么是整页跳转，而不是 ajax

有人会问：我们一路上都在用 axios 悄悄发请求，页面从来不动，为什么支付非得整个人跳走？

因为这一站不是你家的医院。

ajax 的本质是「派个跑腿的去医院问一句，回来告诉我结果」。可问题是，别的医院的门口贴着告示：**外人不得入内，也不许代问。**

这就是浏览器的同源策略（Same-Origin Policy）：你的网页脚本，不许读别人网站的东西。更别说让用户把银行卡密码敲进你家的表单里，再替你转手送出去——那是绝对不允许的。

所以支付这一步，技术上只有两种可能：

- **把整张表交过去**（表单 `POST` 到对方网站）
- **把人送过去**（跳转到对方页面）

两种都意味着：你的页面被关掉了。

页面一关，后果是连锁的：

| 页面被关掉之后 | 为什么 |
|---|---|
| 内存里存的东西全没了 | 组件销毁，`ref` 一笔勾销 |
| 回来是个全新的页面 | 不是「继续」，而是「重新开始」 |
| 订单号只能从地址栏找 | 内存没了，只剩 URL 和服务器里的记录 |
| 支付结果只能重新问一遍 | 走开这段时间发生了什么，前端一无所知 |

所以那一串 `payUrl` 用 `a` 标签，不是图省事，而是「只能这么干」。

工业级的实现里更常见的是隐藏表单：

```html
<form action="https://gateway.example.com/pay" method="POST">
  <input type="hidden" name="orderId" value="123">
  <input type="hidden" name="amount" value="19900">
</form>
```

用 `POST` 而不是 `GET`，就像把转账单装在信封里递进去，而不是举在头顶上走过大厅——金额、卡号这些东西不出现在地址栏，也就不会被浏览器历史和别人的日志顺手记下来。

## 六、支付结果页：`'true'` 是字符串，而且不能信

从分院回来，你在门口会看到一块牌子：检查成功 / 检查失败。

问题是，这块牌子是从地址栏里读出来的：

```vue
<span v-if="$route.query.payResult === 'true'"></span>
<span v-else></span>
```

第一个坑：`query` 里拿到的东西**永远是字符串**。它不是「真」这个意思，而是「真」这个字。`'true'` 和 `'false'` 都是字，都算「有东西」。

所以千万别写成这样：

```vue
<!-- 错的：字符串 'false' 也是"有内容"，一样会显示成功 -->
<span v-if="$route.query.payResult"></span>
```

那等于看到牌子上写着「失败」两个字，就认定「牌子上有字，那就是成功了」。

第二个坑更严重：**这块牌子是路人可以自己挂的。**

任何人打开地址栏，把 `payResult=false` 改成 `payResult=true`，回车，页面立刻变成绿色的勾。如果后端也只认这块牌子，那就等于——你自己打印一张「已付款」的小票，贴到人家收银台上，然后拎着东西走人。

正确的做法是两道都要：

```js
onMounted(async () => {
  // 1. 先看牌子，让用户马上有个反馈
  const payResult = route.query.payResult === 'true'

  // 2. 再问一次账房，以账本为准
  const res = await getOrderAPI(route.query.orderId)
  isPaid.value = res.result.orderState === 2
})
```

牌子只是「让你先安心一下」，账本才作数。

而且真正的「记账」动作，根本不在你这个页面上。用户付完钱，支付宝会自己悄悄给你的服务器发一条消息（异步通知，notify_url），后端收到、验明正身、才把订单改成「已支付」，顺便扣掉库存。你那个 `/paycallback` 页面，从头到尾只是在「告诉用户一声」。

一句话记住：**用户看到的成功，不等于系统认定的成功。**

## 七、倒计时：一个 composable 的三个约束

微波炉上有个定时器：转三分钟，到点「叮」一声。要是你转完之后又转了一次，它就是六分钟——两个计时器各走各的，谁也不知道另一个。

支付页的倒计时，就是用代码做的这个定时器：

```js
export const useCountDown = () => {
  let timer = null
  const time = ref(0)
  const formatTime = computed(() => dayjs.unix(time.value).format('mm分ss秒'))

  const start = (currentTime) => {
    time.value = currentTime
    timer = setInterval(() => { time.value-- }, 1000)
  }

  onUnmounted(() => { timer && clearInterval(timer) })

  return { formatTime, start }
}
```

不到二十行，但有三条必须补上，不补就出事。

**第一条：起点得看停车票，不能自己掐表。**

停车场的收费时限，看的是你进场时机器打的那张票，不是你自己记的时间。所以倒计时的起点应该从服务端算：

```js
const start = (expireAt) => {
  time.value = Math.max(0, Math.floor((new Date(expireAt) - Date.now()) / 1000))
}
```

如果前端写死「30 分钟」，那就等于每次刷新都换一张新的停车票——用户可以无限续，一直停到天荒地老。

**第二条：到 0 就得停，不能变成负数。**

微波炉转到 0 会「叮」，不会继续往下数到负一分钟。所以：

```js
timer = setInterval(() => {
  time.value--
  if (time.value <= 0) {
    time.value = 0
    clearInterval(timer)
    timer = null
  }
}, 1000)
```

不写这个判断，屏幕上就会出现「-1分-30秒」这种没人看得懂的东西。

**第三条：转之前先停掉上一个。**

就是开头微波炉那个问题。用户如果触发了两次 `start`（比如失败后点了重试），两个定时器同时减，倒计时就会以两倍速度消失：

```js
const start = (currentTime) => {
  if (timer) clearInterval(timer)   // 先把旧的停掉
  time.value = currentTime
  timer = setInterval(/* ... */)
}
```

至于 `dayjs.unix(time.value).format('mm分ss秒')`，它干的事就是把「还剩 1799 秒」翻译成「29分59秒」。

有个细节：`mm` 是两位的分钟数，走到 60 就会绕回 `00`，就像时钟转过 12 点又回到 1 点。支付超时一般都在半小时以内，所以这个写法够用；真要显示小时，格式串得换成 `HH时mm分ss秒`。

最后那句 `onUnmounted` 也别省。用户点了「进入首页」，如果定时器没被收走，它还在后台一秒一秒地跳——你看不见它，但它一直在耗电。单页应用里这种「没人管的小闹钟」不会报错，只会慢慢把页面拖慢。

## 八、工程实践与常见坑

1. **订单号走 `query`，不走 `params`**，否则一刷新就白屏。
2. **地址栏里的东西全是字符串**，`'true'` 不是 `true`，比较之前先想清楚。
3. **`payInfo` 的初始值给 `{}`**，模板里配 `?.`，首屏才不出红字。
4. **金额只显示不计算。** 前端能算的金额等于说「用户可以改价」，这在支付页是最严重的一类错误。
5. **参数里套网址就套信封**（`encodeURIComponent`），`redirect`、`returnUrl` 都一样。
6. **回调路径必须和后端登记的一致**，少一个字母，人就回不来了。
7. **别信跳回来的牌子**，`payResult`、`trade_status`、`amount` 都要用订单状态复核一遍。
8. **支付成功用 `replace` 跳走**，不然用户按返回键又回到「请尽快完成支付」那一屏。
9. **定时器三件套：先停旧的、到 0 停、走人交回。** 少一样都会变成不报错的 bug。
10. **起点用服务端时间。** 用户把电脑系统时间一改，自己掐的表就全乱了。
11. **电脑上的微信支付不能跳转**，只能出二维码，所以那个链接写的是 `javascript:;`。
12. **失败了要给出下一步。** 只画一个红叉没有意义，得给「重新支付」和「取消订单」两条路。

## 一句话总结

支付页是整条链路上唯一一段「别人家的路」——你只能把人送过去、等着他回来、然后用自己的账本核对一遍；任何从外面带回来的话，都只是参考，不是结论。
