# 商品详情

> 这一页是用户做决定的最后一站：图要看清、规格要选对、价格要算准、热榜要能点。它也是全站组件密度最高的一页。

## 一、商品详情页的职责：一个页面承载「决策所需的一切」

列表页解决「要不要点进去」，详情页解决「买不买、买哪个」。用户在这一页要确认四件事：

1. **这是不是我想要的东西**——主图、图片列表、标题、价格、服务承诺
2. **有哪些规格可选**——颜色、尺寸、版本，以及每种组合的价格与库存
3. **别人怎么看**——销量、评价、热榜排名
4. **买了之后怎么履约**——配送、退货、发票

这四件事对应页面上四个区块，但它们的数据来源不一样：一是商品基础接口，二是 SKU 接口（通常与基础接口合并返回），三是热榜（同一接口里的 `hotByDay` 字段），四是静态配置或另一个接口。

不要试图用一个「万能详情接口」把四件事全塞进去。真实项目里它们的更新频率不同：商品基础信息一天改一次，库存与价格每分钟在变，热榜每小时算一次。混在一起会导致「改一个库存就要重取整页」。

这一页还有两个技术特点，贯穿全章：

- **组件密度高**。图片预览、SKU 选择器、热榜 tab、数量选择器，四五个独立组件拼在一起。
- **状态相互依赖**。「加入购物车」按钮能不能点，取决于「规格是否选完」；价格显示多少，取决于「选中了哪个组合」。这就是第 14 章要展开的 SKU 问题，本章先做到「会用它」。

## 二、路由配置与跳转：三个入口，一个页面

路由是 `/detail/:id`，通常挂在 Layout 下（详情页有顶部导航与页脚）：

```js
{
  path: '/detail/:id',
  component: () => import('@/views/Detail/index.vue'),
}
```

进入这一页的入口有三个：商品列表的卡片、热榜的条目、搜索结果的条目。它们都应该指向同一个地址：

```html
<RouterLink :to="`/detail/${item.id}`">{{ item.name }}</RouterLink>
```

三个入口意味着**路由不能假设来源**。常见错误是在详情页写「返回上一页」时用 `router.back()`，用户从外部链接直接进来时，`back()` 会把他带到站外。正确做法是判断 `history.state.back` 是否存在，不存在就跳到首页或列表页：

```js
function goBack() {
  if (window.history.state && window.history.state.back) router.back()
  else router.push('/')
}
```

另一个细节是**滚动位置**。从列表滚到第 5 屏点进详情，再返回时用户希望回到第 5 屏，而不是顶部。这需要列表页配合 `KeepAlive` 或手动记录 `scrollTop`。本章不展开，但要知道「返回后的位置」不是详情页能单独解决的，它是两个页面之间的约定。

参数变化的问题在这里同样存在：从「详情 A」点热榜里的「详情 B」，路由记录相同、只有 `id` 变了，组件会被复用。处理方式与第 6 章一致——`watch` 参数，或者干脆给详情页的 `RouterView` 加 `key`（详情页之间没有共享状态，重建的代价可以接受）。

```html
<!-- 在 Layout 里，只对详情页重建 -->
<RouterView :key="route.path.startsWith('/detail') ? route.path : undefined" />
```

这个写法比全局 `key` 精确，但依然会重建整个详情页（包括图片重新加载）。更稳的还是 `watch`，只是详情页要重置的状态更多（选中规格、当前图片、数量）。两者的取舍要看「详情页内部状态复用的价值」：基本为零，所以 `key` 在这里是可以接受的。

## 三、基础数据渲染：一个接口撑起三块内容

详情接口返回的字段大致是这样：

```js
{
  id, name, price, oldPrice, desc,
  mainPictures: ['...', '...'],          // 主图列表
  details: { pictures: [...], properties: [{ name, value }] },
  categories: [{ id, name }, ...],       // 所属分类，用于面包屑
  hotByDay: [{ type: 1, title: '24小时热销榜', products: [...] }],
  specs: [{ id, name, values: [{ name, picture }] }],
  skus: [{ id, specs: [{ name, valueName }], price, oldPrice, inventory }],
}
```

页面渲染按「上到下」三段：

**第一段，图片与核心信息。** 左侧是图片预览组件，右侧是标题、价格、服务标签。价格要处理两种情况：有原价时显示删除线，没有时不显示；价格是区间（`100-200`）还是单值，取决于 SKU 的分布——这个判断应该由接口返回，不要让前端猜。

**第二段，规格与数量。** 规格由 SKU 组件处理，数量用一个受控的 `el-input-number`，`min` 为 1、`max` 为当前选中 SKU 的库存。

**第三段，图文详情与热榜。** 详情图是富文本或图片数组，热榜是 tab 切换。

一个容易忽略的细节：**详情图要懒加载**。详情图通常又长又多，如果一进页面就全部加载，首屏主图会被挤到后面。第 5 章的 `v-lazy` 指令可以直接用：

```html
<img v-for="src in detail.pictures" :key="src" v-lazy="src" alt="" />
```

另一个细节是**接口返回空字段的兜底**。`details.properties` 可能为空数组（没有参数表），`hotByDay` 可能为 `null`（新品没有热榜）。渲染前要做判断，否则一个空对象就会让整页白屏。

```js
const detail = ref(null)
const loading = ref(true)

onMounted(async () => {
  try {
    const { result } = await getDetailAPI(route.params.id)
    detail.value = result
  } finally {
    loading.value = false
  }
})
```

`loading` 不是可选项。详情页的接口通常比列表慢（要聚合 SKU、库存、热榜），没有骨架屏的话用户会看到一片空白，然后内容突然跳出来。

## 四、热榜区域：同一组件，不同数据形状

热榜的数据形状是一个数组，每项是一个榜：

```js
hotByDay: [
  { type: 1, title: '24小时热销榜', products: [{ id, name, price, picture }] },
  { type: 2, title: '周热销榜', products: [...] },
]
```

渲染时用 tab 切换。小兔鲜的做法是复用一个 `XtxTabs` 组件：tab 头由数据生成，内容区用插槽。

```html
<XtxTabs>
  <XtxTabsItem v-for="h in detail.hotByDay" :key="h.type" :label="h.title">
    <ul class="hot-list">
      <li v-for="p in h.products" :key="p.id">
        <RouterLink :to="`/detail/${p.id}`">{{ p.name }}</RouterLink>
        <span>¥{{ p.price }}</span>
      </li>
    </ul>
  </XtxTabsItem>
</XtxTabs>
```

这里有两个「适配」问题。

**第一，标题不是固定的。** 不要写死「24小时热销榜」「周热销榜」，直接用接口的 `title`。运营改文案时前端不用发版。如果接口只给 `type` 不给 `title`，才在前端做映射，并且要把映射写成常量表而不是散落的 `if`。

**第二，热榜条目可能为空。** 新品没有热榜时 `hotByDay` 是 `null` 或空数组，整个区块应该隐藏，而不是渲染一个空白的 tab 栏。

```html
<div v-if="detail.hotByDay && detail.hotByDay.length" class="hot">
  ...
</div>
```

还有一个交互细节：**点热榜里的商品会跳到另一个详情页**，而当前页面是同一个组件。如果不处理参数变化，用户会觉得「点了没反应」。这就是第二节说的复用问题，在这里第一次真正暴露出来。

## 五、图片预览组件：小图切大图与放大镜

图片预览要解决两个交互：点小图换大图、鼠标移到大图上出现放大镜。这两件事都是纯 DOM 操作，适合封成一个组件。

**小图切大图**的核心是一个「当前索引」：

```html
<div class="preview">
  <div class="large">
    <img :src="list[current]" alt="" @mouseenter="showZoom = true" @mouseleave="showZoom = false" @mousemove="onMove" />
    <div v-show="showZoom" class="zoom" :style="zoomStyle"></div>
  </div>
  <ul class="thumbs">
    <li v-for="(src, i) in list" :key="src" :class="{ active: i === current }" @mouseenter="current = i">
      <img :src="src" alt="" />
    </li>
  </ul>
</div>
```

注意这里是 `mouseenter` 而不是 `click`——电商详情页的惯例是「移上去就换」，点击用于打开大图弹层。两者不冲突，但要想清楚哪个是主交互。

**放大镜**的难点在坐标换算。放大镜的位置由鼠标在图片内的相对位置决定，而不是页面的绝对坐标：

```js
const pos = reactive({ x: 0, y: 0 })
const zoomStyle = computed(() => ({
  left: pos.x + 'px',
  top: pos.y + 'px',
  backgroundImage: `url(${list[current.value]})`,
  backgroundPosition: `-${pos.x * 2}px -${pos.y * 2}px`,
}))
```

这里有两个必须处理的边界。

**第一，放大镜不能出界。** `pos.x` 要被夹在 `[0, width - zoomWidth]` 之间，否则放大镜会飘到图片外面。

**第二，`background-size` 要跟着放大倍数走。** 只改 `background-position` 不改尺寸，看到的不是「放大」而是「同尺寸的图移动了位置」。

```js
function onMove(e) {
  const rect = e.currentTarget.getBoundingClientRect()
  const x = e.clientX - rect.left - zoomW / 2
  const y = e.clientY - rect.top - zoomH / 2
  pos.x = Math.min(Math.max(0, x), rect.width - zoomW)
  pos.y = Math.min(Math.max(0, y), rect.height - zoomH)
}
```

为什么不做成「用 CSS `transform: scale` 放大整张图」？因为那样用户看不到「放大的是哪一块」，需要额外画一个指示框，而且大图会溢出容器。背景图方案更可控。

组件要接受一个 `list` 参数（图片地址数组），并且**在列表变化时重置 `current`**。否则从详情 A 跳到详情 B，`current` 还是 3，而 B 只有 2 张图，大图就空了。这是组件复用最容易漏的一行。

```js
watch(() => props.list, () => { current.value = 0 })
```

## 六、SKU 组件：选规格这件事为什么难

先明确「SKU」是什么：一个 SKU 是一次「具体可售的组合」。一件 T 恤有颜色（黑/白）和尺寸（S/M/L），就有 6 个 SKU，每个 SKU 有自己的价格、库存、图片。

用户的操作是「逐个选规格」，系统的任务是：

1. 根据已选条件，算出「哪些选项还能选、哪些要置灰」
2. 选完之后，定位到唯一的 SKU，拿到它的价格与库存
3. 没选完时，价格显示区间（`99-129`），库存显示总和

第 2、3 步不难，难的是第 1 步。举例：黑色 + M 缺货，那么「选了黑色之后，M 应该置灰」；但「选了 M 之后，黑色也该置灰」。这叫**路径字典**：把所有可选组合的集合提前算出来，每次选择后在集合里查。

穷举所有组合的算法叫「幂集」（power set），第 14 章会完整实现。本章的做法是**直接使用小兔鲜提供的 `XtxSku` 组件**，理解它的输入输出就够了。

```html
<XtxSku :goods="detail" @change="onSkuChange" />
```

```js
const sku = ref(null)
function onSkuChange(selected) {
  sku.value = selected       // { skuId, price, oldPrice, inventory, specsText }
}
```

组件内部接收两个关键数据：`goods.specs`（规格与选项）与 `goods.skus`（所有组合）。它会自己算出可选状态，并在选择变化时把当前 SKU 抛出来。

用组件时要守住三条：

**第一，不要在外层再维护一份「选中状态」。** 组件的 `change` 事件就是唯一真相，外层只存结果。两份状态一定会不同步。

**第二，「加入购物车」必须等 `sku` 有值。** 没选完规格就加购，后端不知道发哪个货。按钮要么禁用，要么点击时提示「请选择规格」。

```html
<button :disabled="!sku" @click="addCart">加入购物车</button>
```

**第三，数量不能超过库存。** `sku.inventory` 是上限，`el-input-number` 要绑定 `:max="sku?.inventory ?? 1"`。库存为 0 时按钮要变成「已售罄」，而不是让用户点了才报错。

如果项目里没有现成的 SKU 组件，自己写也不是不行，但要预期它会花掉这一章两倍的时间——「置灰逻辑」的边界情况（多规格、有图规格、规格名重复）比看上去多得多。

## 七、全局组件插件化：把注册收进一个文件

到这一章，全局组件已经有五六个：`XtxBread`、`XtxBreadItem`、`XtxSku`、`XtxTabs`、`XtxTabsItem`、`XtxImageViewer`。如果都在 `main.js` 里逐个 `app.component()`，`main.js` 会越来越长，而且新增组件要改主入口。

插件化就是把这堆注册收进一个文件，对外只暴露一个 `install`：

```js
// components/index.js
import XtxSku from './XtxSku/index.vue'
import XtxTabs from './XtxTabs/index.vue'
import XtxTabsItem from './XtxTabs/XtxTabsItem.vue'
import XtxImageViewer from './XtxImageViewer/index.vue'

export default {
  install(app) {
    app.component('XtxSku', XtxSku)
    app.component('XtxTabs', XtxTabs)
    app.component('XtxTabsItem', XtxTabsItem)
    app.component('XtxImageViewer', XtxImageViewer)
  },
}
```

```js
// main.js
import UI from './components'
app.use(UI)
```

`app.use()` 会调用对象的 `install(app)` 方法，把注册逻辑执行一遍。好处有三个：主入口干净；组件清单集中，一眼能看完；以后要按需注册（比如只在某些页面注册大组件）时，改一个文件就够。

插件的注册顺序有讲究：**先注册 UI 组件库，再注册自己的组件**。因为自己的组件可能内部用到组件库的组件；反过来虽然也能跑（Vue 的组件解析是运行时查找），但如果自定义组件与组件库组件重名，后注册的会覆盖先注册的。给自己的组件统一加 `Xtx` 前缀，就是为了避免这种覆盖。

还有一个容易忽略的点：**插件里不要写业务逻辑**。有人会把「初始化用户信息」「挂载全局指令」也塞进 `install`，导致「只要引入组件库就会发请求」。插件应该只做注册，副作用放在 `main.js` 或独立的初始化函数里。

```js
// 正确：只注册
app.component('XtxSku', XtxSku)

// 错误：插件里发请求
install(app) {
  app.component('XtxSku', XtxSku)
  getUserInfo()          // 一引入就请求，测试环境直接报错
}
```

## 八、工程实践与常见坑

**第一，从热榜点到另一个商品没反应。** 路由复用，`onMounted` 不再执行。处理方式：`watch` 参数并重置 `current`、`sku`、数量；或给详情页的路由出口加 `key`。

**第二，图片预览切换商品后大图空白。** `current` 没重置，新商品图片更少。处理方式：`watch(() => props.list, () => current.value = 0)`。

**第三，放大镜飘到图片外面。** 坐标没有夹紧到容器范围。处理方式：`Math.min(Math.max(0, x), max)`。

**第四，放大镜只移动不放大。** 只改了 `background-position`，没改 `background-size`。

**第五，没选规格就能加购。** 按钮没有依赖 `sku`。处理方式：`:disabled="!sku"`，并在点击时二次校验。

**第六，数量超过库存。** 没用 `sku.inventory` 限制 `max`。库存为 0 时应直接显示售罄。

**第七，热榜标题写死。** 运营改文案要发版。处理方式：用接口的 `title`。

**第八，`hotByDay` 为空时整页报错。** 直接 `v-for` 了 `null`。处理方式：`v-if` 判断后再渲染区块。

**第九，插件里混入副作用。** 一引入组件库就发请求。处理方式：插件只做注册。
