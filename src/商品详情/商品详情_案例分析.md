# 商品详情 · 案例分析

> 四个背景：SKU 这个词从哪来、放大镜为什么用背景图而不是缩放、插件机制为什么在三个时代反复出现，以及「组件复用导致状态残留」这个通病。

## Case 1：SKU 不是技术词，是零售词

### 背景

很多人以为 SKU 是电商发明的，其实它是零售业的老概念：**Stock Keeping Unit（库存量单位）**，指「库存管理上不可再分的最小单位」。1950 年代美国百货业就用它来盘点——同一款衬衫，黑色 M 码与白色 L 码是两个 SKU，因为它们的库存、成本、销量必须分开统计。

### 事件经过

电商把这套体系原样搬了过来，并多加了一层含义：SKU 不只是「库存单位」，还是「下单单位」。用户加购时选择的不是「一件 T 恤」，而是「黑色 / M 码」这个具体的 SKU，因为只有它能对应唯一的价格与库存。

这带来一个前端必须解决的问题：**用户是逐个选属性的，系统要还原成一个 SKU**。属性有多个维度（颜色、尺寸、版本），每个维度有多个值，组合数是乘积。如果某些组合不存在（比如黑色不出 XXL），还要把不可选的选项置灰。

早期电商的做法是「穷举所有组合，存成一张表」，用户每选一次就查表。这张表的学术名字叫幂集（power set），第 14 章会完整实现。后来的系统开始用「位图」或「布尔矩阵」优化查询，但本质没变：**可选状态是一个多维组合问题，不是单维判断**。

### 与本章的关系

本章第六节说「先会用组件，第 14 章再造」，正是因为这件事的复杂度集中在这一层。理解「SKU 是零售概念」也有实际好处：它解释了为什么价格是「每个 SKU 一个价」而不是「每个商品一个价」，以及为什么库存必须绑在 SKU 上而不是商品上。

## Case 2：放大镜为什么用背景图

### 背景

商品图放大有三种常见实现：整图 `transform: scale`、弹层显示原图、以及「放大镜」——鼠标位置出现一个方块，方块里显示局部放大图。

`transform: scale` 最简单，一行 CSS 就能放大。但用在详情页上有两个问题：放大的图会溢出容器（要么裁剪、要么遮挡旁边的文字），而且用户看不出「现在看的是原图的哪个位置」，需要额外画一个指示框。

### 事件经过

早期电商（2000 年代）大量使用 Flash 做放大镜，因为当时 CSS 无法方便地做「局部放大」。2010 年代 Flash 退场后，主流方案变成两种：

1. **背景图方案**：把原图设为放大镜的 `background-image`，用 `background-size` 放大，用 `background-position` 偏移。方块本身跟着鼠标移动。
2. **Canvas 方案**：把原图绘制到 canvas 上，按比例裁剪局部并缩放。

背景图方案的优势是「零 JS 绘制」——所有放大都由浏览器的合成层完成，性能好、代码少。代价是要自己算坐标与边界，而且 `background-position` 的负值语义容易搞混（偏移量要取负）。

主流电商至今仍以背景图方案为主，原因很实际：它不需要处理 canvas 的像素比、也不需要担心图片跨域（`drawImage` 会受 CORS 限制）。

### 与本章的关系

本章第五节选了背景图方案，并在第八节把「只移动不放大」列为坑——只改 `background-position` 不改 `background-size`，看到的是平移而不是放大。理解这段技术史，也就理解了「为什么不用更简单的 scale」：简单方案解决不了「局部」这个需求。

## Case 3：插件机制为什么反复出现

### 背景

「把一组能力打包，对外只暴露一个安装入口」——这个模式在前端史上出现过至少三次，每次解决的都是同一个问题：**注册逻辑散落、顺序不可控、新增要改主入口**。

### 事件经过

**第一次是 jQuery 插件（2006 年前后）。** 通过 `$.fn.myPlugin = function(){}` 把方法挂到原型上，引入脚本即生效。优点是简单，缺点是「引入即污染」，无法控制顺序，也无法按需加载。

**第二次是 Vue 2 的 `Vue.use()`（2014 年）。** 插件是一个对象或函数，Vue 调用它的 `install(Vue, options)`。这解决了「注册集中化」，也允许传配置。Vue 3 把它改成 `app.use(plugin)`，`install` 收到的是应用实例，顺带解决了「多个应用实例共享全局状态」的问题。

**第三次是构建工具的插件体系。** webpack 的 `plugins` 数组、Vite 的 `plugins` 数组、Babel 的 presets，都是同一思路：一个对象带一个约定方法（`apply`/`transform`），由宿主在固定时机调用。顺序敏感这一点在 webpack 里尤其明显——`HtmlWebpackPlugin` 必须放在某些插件之后。

三次演进的共同结论是：**插件是「注册的容器」，不是「逻辑的容器」**。一旦往里塞业务，就会出现「引入即副作用」的问题。

### 与本章的关系

本章第七节把五六个全局组件收进 `components/index.js`，正是 Vue 插件机制的最小用法。那一节强调「插件里不要写业务逻辑」，对应的就是 jQuery 时代「引入即污染」的教训；强调「先注册组件库再注册自己的组件」，对应的则是 webpack 插件顺序敏感的经验。

## Case 4：组件复用导致的状态残留

### 背景

「同一个组件、不同的数据」是前端框架的通用优化：复用实例可以减少创建销毁的开销。但它带来一个通病——**组件内部的状态不会自动跟着数据重置**。

这个 bug 的表现非常一致：换了一个对象，页面上还残留着上一个对象的痕迹。图片还是旧图、选中的 tab 还是旧 tab、滚动位置还在原处。

### 事件经过

React 在 2018 年前后把「用 `key` 强制重建」写成了官方推荐做法：给组件一个与数据绑定的 `key`，数据变了 key 变了，React 就会销毁重建。Vue 社区同期流行「给 `RouterView` 加 `key="route.fullPath"`」，解决路由参数变化时组件不重建的问题。

但 `key` 是「核弹级」方案：它重建整棵子树，把「不该重置的状态」也重置了（比如输入框里用户正在输入的内容）。

于是更精确的做法成为主流：**在组件内部监听数据源，手动重置相关状态**。

```js
watch(() => props.list, () => { current.value = 0 })
```

这段代码只重置「当前图片索引」，其他状态（比如是否显示放大镜）不受影响。代价是「要记得重置哪些」，漏一个就留一个 bug。

Vue 3 的 `watch` 配合 `immediate` 与 `flush: 'post'`，让这种「数据变 → 重置 → 重新渲染」的流程更可控。React 则用 `useEffect` 的依赖数组 + `key` 组合。两个生态最终都收敛到同一个结论：**复用是默认，重置要显式**。

### 与本章的关系

本章第五节说「组件要接受 `list`，并在列表变化时重置 `current`」，第八节把「换商品后大图空白」列为坑，都是这个通病的具体表现。本章第二节讨论「详情页之间要不要用 `key` 重建」，判断依据也来自这段历史：详情页没有值得保留的内部状态，所以 `key` 可以接受；列表页有滚动位置，所以不能一刀切。
