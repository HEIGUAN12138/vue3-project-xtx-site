## 一、是非题（10 题）

1. 会员中心的侧边栏应该写进「个人中心」和「我的订单」各自的组件里，这样更内聚。
2. `children` 里那条 `path: ''` 的作用，是让 `/member` 直接显示某个三级页。
3. 子路由的 `path` 应该写成 `'/order'`，这样拼出来的地址才完整。
4. `to="/"` 的导航链接不加 `exact`，会在所有页面都显示为激活状态。
5. 个人中心应该重新请求一次用户信息接口，保证数据是最新的。
6. `total` 可以用 `orderList.value.length` 计算出来。
7. 切换订单 tab 时，应该把 `page` 重置为 1。
8. tab 的 `name`（如 `'unpay'`）可以直接赋给接口的 `orderState`。
9. `el-pagination` 会根据 `:total` 自动计算总页数。
10. `v-for` 渲染订单列表时，`key` 用数组索引比用订单号更合适。

### 答案解析

1. **错**。侧边栏是会员中心这个区域共享的 UI，应提到父级路由 `Member` 组件里，否则就是重复代码。
2. **对**。空 path 表示「父路径本身」，它是默认三级页的落点。
3. **错**。带前导斜杠会变成绝对路径 `/order`，而不是 `/member/order`。
4. **对**。所有路径都以 `/` 开头，所以它会一直匹配成功；必须加 `exact`。
5. **错**。`userInfo` 已在登录时写入 Pinia 并持久化，再请求一次会造成两份可能不同步的数据。
6. **错**。`length` 只是当前页的条数，总数必须来自接口的 `counts`。
7. **对**。否则会请求「新状态的第 N 页」，很可能返回空列表。
8. **错**。tab 的 name 是给人看的字符串，`orderState` 是数字，中间必须有映射表。
9. **对**。`total` ÷ `page-size` 向上取整就是总页数，组件会自动处理。
10. **错**。列表会因筛选整体替换，用索引会导致组件状态错位复用；应该用 `order.id`。

### 答案解析

1. **B**。空 path 表示父路径本身，是默认三级页。

4. **C**。单一真相源，避免「刷新一下就好了」的同步问题。
5. **B**。分页接口通常返回 `{ items, counts }`，列表与总数是一个整体。
6. **B**。`counts` 是服务端算好的总数。
7. **C**。请求了「新状态的第 N 页」，而该状态可能不足 N 页。
8. **B**。`tab-change` 给的是当前 tab 的 `name`。
9. **B**。`const` 存在暂时性死区，声明前访问会直接抛错。
10. **B**。空态能区分「查过了没有」和「页面坏了」。

## 四、情境分析（3 题）

### 情境 1：切到「待付款」，页面说没有订单

用户反馈：订单列表第一页有 5 单，翻到第 2 页看了几单，然后点「待付款」，页面显示「暂无订单数据」。刷新之后又有数据了。

**问**：成因与修法。

**答**：成因是切 tab 时没有重置 `page`。用户当时停在第 2 页，点「待付款」后请求的是「待付款的第 2 页」；而待付款只有 1 页，所以返回空数组，命中 `orderList.length === 0` 的空态分支。刷新会把 `params` 恢复成初始值（`page: 1`），所以又能看到数据。

修法：在 `tabChange` 里，改完 `orderState` 后立刻 `params.value.page = 1`，再请求。同类问题还包括「修改 `pageSize` 后不回第 1 页」。

### 情境 2：三个地方显示的用户名不一样

用户在个人中心把昵称改成「阿橙」，顶部导航变了，左侧边栏还是「橙子」，刷新后才一致。

**问**：技术上怎么回事？结构上该怎么修？

**答**：昵称被存了三份：侧边栏、顶栏、个人中心各自请求或各自缓存了一份，改名的那个组件只更新了自己那份。

正确的结构是让 `userInfo` 只存在于 `userStore`，所有展示昵称的地方都从 store 读。改名成功后调用 `userStore` 的 action 更新 store，三处会同时重渲染——因为它们是同一份数据的三个读者，而不是三份副本。

### 情境 3：新上线「退款中」，老订单全变了

后端新增了「退款中」状态，为了排序好看，把原来的 `6`（已取消）改成了「退款中」，已取消挪到了 `7`。前端没改，结果历史订单里的「已取消」全显示成了「退款中」。

**问**：问题的性质？短期与长期分别怎么处理？

**答**：性质是「对外暴露的枚举值被改义」。`orderState` 一旦被前端依赖，就是契约，不能悄悄改含义。

短期：前端更新映射表，补上 `7`；同时把 `stateMap[n] || '未知状态'` 的兜底加上，避免再出现空白。

长期：约定「只增不改」——新增状态用新数字，旧数字的含义永久保留；或者干脆由后端返回 `orderStateDesc`，前端不维护映射。无论哪一种，都要写进接口文档并纳入评审。

## 五、代码阅读（3 题）

### 题 1

```js
const getOrderList = async () => {
  const res = await getUserOrder(params.value)
  orderList.value = res.result.items
  total.value = res.result.counts
}
const total = ref(0)
```

**问**：这段代码有什么问题？

**答**：`total` 在声明之前被使用，触发暂时性死区错误（`Cannot access 'total' before initialization`）。`const` 声明的变量在初始化之前不能访问，即使这段赋值发生在函数体里、看起来「还没执行」也一样——因为函数被调用时，`total` 的声明语句可能还没执行到。修法：把 `const total = ref(0)` 移到 `getOrderList` 之前。

### 题 2

```js
const tabChange = (type) => {
  params.value.orderState = type
  getOrderList()
}
```

**问**：两处问题。

**答**：一，`type` 是 tab 的 `name`（字符串 `'unpay'` 等），不能直接赋给 `orderState`，必须经过 `stateMap` 映射为数字，否则后端会返回 400 或空列表；二，没有把 `page` 重置为 1，用户在第 N 页切 tab 会请求一个可能不存在的页。

### 题 3

```js
const pageChange = (page) => {
  params.value.page = page
}
```

**问**：为什么用户点第 2 页，列表没有变化？

**答**：只改了参数，没有重新请求。`params` 变了不会自动触发接口调用——必须显式调用 `getOrderList()`。这是「参数驱动」模型里最容易漏的一步：参数是输入，请求是动作，两者要成对出现。

## 六、延伸思考（2 题）

1. 订单列表的筛选状态（当前 tab、当前页码）要不要写进 URL？

   **思路**：分两种情况。如果这个页面需要「分享给别人」或「刷新后回到原处」，就该写进 URL——比如商品列表的筛选条件，用户会想 bookmark。个人订单通常不分享，但「刷新后回到第 3 页」是有价值的，所以折中做法是把 `orderState` 与 `page` 写进 query，进页面时从 `route.query` 读初始值，切换时 `router.replace` 更新。

   代价是代码复杂度上升：要考虑「URL 变了但组件没重建」「用户手改 URL」「非法值兜底」三种情况。判断标准是——**这个状态是否值得被外部（刷新、分享、后退）引用。** 值，就写进 URL；不值，就留在组件里。

2. 会员中心把 `GoodsItem` 从首页目录里 import 过来用，这个决定的风险是什么？在什么信号出现时应该立刻重构？

   **思路**：风险是**隐式耦合**——会员中心依赖了首页的目录结构，而这个依赖不会在代码审查里显形（import 路径看起来很正常）。一旦首页重构把组件挪走，会员中心会先断，而且断在一个「跟它没关系」的改动上，排查成本很高。

   该重构的信号有三个：同一个组件被第三个页面 import；组件开始需要「只在某个页面生效」的参数（说明它已经在承担多种职责）；组件所在目录被移动过一次。满足任一条，就该把它升到 `src/components/`，并顺手把「首页」这个隐含语义从名字里去掉。

## 自测标准

- 能说出嵌套路由为什么能复用外壳，并正确配置空 path：合格
- 能用一份 `params` 同时驱动 tab 与分页，且不漏掉「重置页码」：良好
- 能解释单一真相源、状态枚举的契约性质，以及 `total` 为什么必须由服务端给：优秀
