# 会员中心 · 案例分析

> 四个案例分别对应本章的四条命脉：页码分页的代价、单一真相源的由来、状态枚举一旦外露就变成契约、以及「一共多少条」这个数字为什么比想象中贵。

## Case 1：从 page 到 cursor——页码分页的代价

### 背景

`page` / `pageSize` 是最符合直觉的分页方式：第 1 页、第 2 页、每页 20 条。翻译成 SQL 就是 `LIMIT 20 OFFSET 20`，跳过前面 20 条，取 20 条。

它对用户友好——能跳页、能显示「共 5 页」。但有两个隐藏代价。

### 事件经过

第一个代价是深分页的性能。数据库执行 `LIMIT 20 OFFSET 100000` 时，并不是「直接跳到第 10 万条」，而是**先读出前 10 万条再丢掉**。页码越大，越慢，而且是线性变慢。

第二个代价更隐蔽：**数据是动的，页码是静态的**。用户看第 1 页时，如果有人插入了一条新数据，第 2 页的第一条就会是上一页最后一条——用户看到了重复项；反过来如果有人删除，就会有数据被跳过，永远看不到。

2012 年，Twitter 在 API v1.1 中把分页方式从 `page` 改成 `cursor`。请求里不再说「我要第 3 页」，而是说「给我这一批，并把下一批的把手一起给我」：

```json
{ "next_cursor": "1234567890" }
```

客户端下次带着这个 `next_cursor` 再来，服务端从「这条记录之后」继续取。这样既不需要「跳过 N 条」，也不会因为数据变动而重复或遗漏。

同一时期，大量面向开发者的 API 走向了同一方向：Stripe 用 `starting_after` / `ending_before`，Slack 用 `cursor`，Elasticsearch 用 `search_after` / `scroll`。

### 与本章的关系

第六节的 `params = { orderState, page, pageSize }` 就是 offset 分页。它在这里完全合适，理由有三：

1. **用户需要跳页**。「我的订单」里用户会想直接翻到第 5 页，cursor 做不到。
2. **数据量小**。一个人的订单通常几十到几百条，深分页不存在。
3. **顺序稳定**。订单按创建时间倒序，很少在中途插入。

所以这不是「page 过时了，该用 cursor」，而是：**page 适合「有页码、要跳转、量不大」的场景；cursor 适合「无限加载、量很大、顺序会变」的场景。** 二级分类页的无限滚动其实更接近后者的语义，只是教学项目用 page 也能跑。

### 参考资料

- [Twitter API：分页（cursoring）](https://developer.twitter.com/en/docs/twitter-api/pagination) —— 官方对 cursor 模型的说明与迁移理由。
- [Stripe API：自动分页](https://docs.stripe.com/api/pagination) —— `starting_after` / `ending_before` 的用法，附带对「为什么要避开 offset」的解释。
- [MySQL：SELECT 语句（LIMIT）](https://dev.mysql.com/doc/refman/8.0/en/select.html) —— `LIMIT offset, row_count` 的语义，理解深分页为何慢的起点。

## Case 2：Flux 与「单一真相源」——为什么用户信息不该请求两次

### 背景

2010 年前后，前端的主流做法是 jQuery 式的：谁需要数据，谁就去拿一次，然后直接把结果塞进自己那块 DOM。

问题在页面变复杂之后出现。同一个用户昵称可能出现在顶栏、侧边栏、个人中心三处；三处各自请求、各自渲染。用户改了昵称，顶栏更新了，侧边栏还是旧的——因为没有任何一个地方「拥有」这份数据。

### 事件经过

2014 年，Facebook 在 React 大会上公开了 Flux 架构。它提出的核心约束很朴素：

- 数据只有一份，放在 **store** 里
- 视图不能直接改 store，只能发出 **action**
- store 变化后，单向地流回视图

2015 年，Redux 把这件事推到极致，总结成三条原则，第一条就是「**单一状态树**（single source of truth）——整个应用的 state 存在一个对象树里」。

同年 Vuex 出现，把这套模型带进 Vue 生态；2019 年 Pinia 作为 Vuex 的继任者发布，API 更贴近组合式写法，但「一份状态、多处读取」的内核没有变。

### 与本章的关系

第四节那个「个人中心不发请求，直接读 `userStore`」，就是单一状态树最直接的应用。

登录成功后 `userStore.getUserInfo()` 把数据写进 store 并持久化；顶栏读它、个人中心读它、下单时读它——**读的地方可以有很多，写的地方只有一个**。这样「三个地方显示不同昵称」这种问题在结构上就不可能发生。

反过来，如果每个页面各自请求一次，就等于把「同一份事实」抄了好几份，然后指望它们永远同步。这在分布式系统里有个更严肃的名字，叫数据冗余导致的不一致；在单页应用里，它表现为「刷新一下就好了」的玄学 bug。

这里也能看出 Pinia 与「组件内 `ref`」的分工：只在一个组件里用的数据放 `ref`；跨页面共享、需要持久化、需要被多处读取的，才进 store。会员中心的 `likeList` 属于前者，`userInfo` 属于后者。

### 参考资料

- [Flux：官方文档](https://facebookarchive.github.io/flux/) —— 单向数据流与 store 的原始描述。
- [Redux：三大原则](https://redux.js.org/understanding/thinking-in-redux/three-principles) —— 「单一状态树」这一条的正式表述。
- [Pinia：State](https://pinia.vuejs.org/zh/core-concepts/state.html) —— Vue 生态里这份「唯一账本」当前的实现方式。

## Case 3：Stripe 的 API 版本化——状态枚举一旦外露就是契约

### 背景

订单状态是一组有限的取值，专业术语叫状态机（state machine）：待付款 → 待发货 → 待收货 → 待评价 → 已完成，随时可能走到已取消。前端拿到的 `orderState` 就是这几个数字。

问题在于：这组数字的含义，一旦被前端（乃至所有接入方）依赖，它就不再是「后端内部的事」。

### 事件经过

2011 年 Stripe 成立时做了一个当时不太常见的决定：**API 从第一天起就版本化**，版本号是日期，形如 `2019-12-03`。请求头里带 `Stripe-Version`，服务端按那个日期对应的行为来响应。

意思是：即使 Stripe 后来把某个字段的语义改了、把某个状态拆成了两个，一个固定在旧版本的客户端仍然会收到旧行为。破坏性变更不会「悄悄发生」，只会「在新版本里发生」，是否升级由接入方自己决定。

这套做法的代价很高——服务端要长期维护多个版本的兼容逻辑。但它换来了一个关键承诺：**已经对外发布过的字段含义，不能被无声地改掉。**

反面的例子在行业里很常见：某接口的 `orderState` 原本是 1–6，某天产品要加「退款中」，于是把 `6`（已取消）改成了「退款中」，把「已取消」挪到 `7`。前端那张映射表没动，于是所有已取消的订单在页面上都显示成了「退款中」——没有人报错，只是数字变了意思。

### 与本章的关系

第八节说「`orderState` 的显示要做映射」，隐含的前提是这个映射必须和后端对齐。Case 3 说明了这个「对齐」为什么值得被当成契约来对待。

由此可以推出两条实践：

1. **映射表要能容忍未知值。** 不要写成 `return stateMap[n]`，因为新增的状态会返回 `undefined`，页面上就是一片空白。写成 `return stateMap[n] || '未知状态'` 至少能让用户知道「有这个东西，只是我不认识它」。
2. **状态的中文名如果由后端给，前端就别自己维护映射。** 有些接口会直接返回 `orderStateDesc`，前端只负责显示——这是把「含义」的归属留在服务端，代价是前端少了一层自由度。

这两条不冲突，选哪条取决于团队约定，但**不能两处都维护**：前端一份中文名、后端一份中文名，早晚会出现两套说法。

### 参考资料

- [Stripe：API 版本化](https://docs.stripe.com/api/versioning) —— 官方对版本策略的完整说明，含 `Stripe-Version` 头。
- [Stripe：API 更新日志](https://docs.stripe.com/changelog) —— 可以看到每一次破坏性变更的具体描述，是「契约如何演进」的真实样本。
- [MDN：HTTP 状态码](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Status) —— 另一个「数字代表状态」的经典例子，注意它的取值为什么几十年不变。

## Case 4：Elasticsearch 的 `track_total_hits`——「共多少条」有多贵

### 背景

分页条上要显示「共 37 条」，组件需要 `total`。直觉上这只是「数一数」，应该很便宜。

在数据量小的时候确实便宜。但当一个查询可能命中上亿条文档时，「精确数一遍」意味着要把所有命中的记录都走一遍——这和「只取出前 20 条」完全不是一个量级的开销。

### 事件经过

Elasticsearch 在 7.0（2019 年）做了一个改动：默认情况下，`hits.total` 只精确计算到 **10000** 条，超过就返回 `"relation": "gte"`（大于等于），意思是「至少 1 万条，具体多少不知道」。

想拿到精确总数，必须显式加上 `"track_total_hits": true`，并承担相应的性能代价。

这个改动的理由写在官方文档里：绝大多数场景（无限滚动、搜索建议）根本不需要精确总数，为了一个没人看的数字付出全量扫描的代价不划算。

顺带一提，Nielsen Norman Group 在更早的可用性研究里就指出过：无限滚动与分页各有适用场景——需要「知道自己在哪、能回到某处」的浏览，分页更合适；需要「连续探索」的，滚动更合适。而「共 N 条 / 第 X 页」这种定位感，正是分页的核心价值。

### 与本章的关系

第六节那句 `total.value = res.result.counts`，就是「向服务端要总数」。Case 4 解释了为什么这个数字必须由服务端给，以及它为什么可能不便宜。

三条推论：

1. **`total` 不能自己数。** `orderList.length` 只是当前页的条数，它和总数是两个不同的概念。
2. **`total` 是分页组件的输入，不是它的输出。** `el-pagination` 靠 `:total` 算页数，它不会帮你算总数。
3. **总数可能是个近似值。** 在数据量大的系统里，「共 1 万+ 条」是常态，不是 bug。如果产品要求「必须精确」，那是一个需要单独评估的成本项。

对「我的订单」这种页面，个人订单量小，精确总数毫无压力；但这个习惯要建立起来——**先问「这个数字谁算的、算它贵不贵」，再决定它在哪儿算。**
