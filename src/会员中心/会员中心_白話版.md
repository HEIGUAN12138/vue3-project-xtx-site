# 会员中心

> 会员中心是这套课件里第一个「一个页面装下多个页面」的结构。它的技术价值不在长得好看，而在于：怎么用一个外壳带出两个三级页面、怎么让同一份用户信息不必请求两遍、怎么用一份参数对象同时驱动 tab 与分页。

## 一、会员中心的位置：一个「壳」加两个三级页面

去菜市场买菜，摊位一字排开，每个摊只卖一样东西，你走到哪个摊就买哪样。以前的页面都是这样：首页一个地址、分类页一个地址、支付页一个地址，一一对应。

会员中心不一样。它像一间办公室：走廊和前台是固定的，你左边那扇门进去是「个人信息」，右边那扇门进去是「我的订单」。**门是同一扇，走廊也是同一条，只有里面的房间在换。**

这就是「嵌套路由」要干的事：把不变的部分留在外面，把会变的部分塞进一个出口。

```
/member           → 左边侧边栏 + 右边内容区（壳）
/member           → 个人中心（默认打开的那间屋）
/member/order     → 我的订单
```

用户在左边点「我的订单」，只有右边那块换了，左边那列导航纹丝不动。要是没有这一层壳，你就得在「个人中心」和「我的订单」两个页面里各写一遍侧边栏——duplicated，将来加个「收货地址」，就是第三遍。

这个套路其实前面见过：Layout 那一章就是拿 Layout 当外壳，首页、分类页、详情页都是它的孩子。会员中心是同一件事的第二次——Layout 里再套一个 Member，Member 里再套个人中心和我的订单。

判断标准很好记：**当一片区域里有好几个页面共用同一块 UI 时，就把那块 UI 往上提一层。**

## 二、路由：`/member` 与空 path 作默认

外壳组件的模板，最关键只有一行：

```vue
<template>
  <div class="container">
    <div class="xtx-member-aside">
      <div class="user-manage">
        <h4>我的账户</h4>
        <div class="links">
          <RouterLink to="/member/user">个人中心</RouterLink>
        </div>
        <h4>交易管理</h4>
        <div class="links">
          <RouterLink to="/member/order">我的订单</RouterLink>
        </div>
      </div>
    </div>
    <div class="article">
      <RouterView />
    </div>
  </div>
</template>
```

那个 `<RouterView />` 就是一个「空房间」。你在侧边栏点哪扇门，哪间屋子的内容就填到这儿来。

路由这么配：

```js
{
  path: '/member',
  component: Member,
  children: [
    { path: '', component: MemberInfo },        // /member
    { path: 'order', component: MemberOrder },  // /member/order
  ],
}
```

`path: ''` 那一条，就是「推开门第一眼该看到谁」。用户只敲 `/member`，没说要进哪间屋，那就默认给他看个人信息。

三个小细节：

**第一，孩子的门牌号前面不要加斜杠。** 写 `path: '/order'` 就成了「整栋楼里的 /order」，而不是「会员中心里的 order」。Vue Router 会自动把父级的门牌接在前面。

**第二，空 path 只能有一条。** 两条都写着「默认」，那到底进哪间？系统会犯难。

**第三，`/member` 和 `/member/` 是一回事。** 末尾那个斜杠，Vue Router 会自己忽略掉。

还有一件事：这个外壳组件不该有自己的数据和请求。它只负责摆好走廊、留出空房间。一旦它开始管数据，就会和里面的房间抢同一本账。

## 三、侧边栏：链接激活态与 `exact-active`

走廊里的指示灯，得告诉人「你现在站在哪」。

Vue Router 很贴心，会自动给 `RouterLink` 加两个类名：

| 类名 | 什么时候亮 |
|---|---|
| `router-link-active` | 当前路径**以**链接地址开头 |
| `router-link-exact-active` | 当前路径**完全等于**链接地址 |

差别就在「开头」两个字。

打个比方：你家的门牌是「3 号楼」，那么「3 号楼 201」「3 号楼 305」都算「你在 3 号楼里」——这叫「以它开头」。但如果你要的是「你正好站在 201 门口」，那就得完全一样。

问题出在首页那个链接：它的地址是 `/`。而**所有**路径都以 `/` 开头，所以只要你用了默认的 `active`，首页那盏灯在任何页面都会亮着，永远不灭。

所以导航栏里那个「首页」得加一个 `exact`：

```vue
<RouterLink to="/" exact>首页</RouterLink>
```

翻译成人话就是：「必须完全等于 `/` 才算」。

会员中心这几个链接是好几个平行的具体地址，不存在这种「父级前缀」的问题，用默认的就行：

```scss
a {
  display: block;
  padding: 15px 0;
  color: #666;
  position: relative;

  &.active,
  &.router-link-exact-active {
    color: $xtxColor;

    &:before {
      display: block;
    }
  }

  &:before {
    content: '';
    display: none;
    width: 6px;
    height: 6px;
    border-radius: 50%;
    position: absolute;
    top: 19px;
    left: -16px;
    background-color: $xtxColor;
  }
}
```

那个小圆点是纯 CSS 画出来的：平时 `display: none` 藏着，高亮时才 `display: block`。好处是不用多放一个元素，也不依赖任何图标字体。

## 四、个人中心：从 Pinia 读，而不是再请求一次

个人中心要显示头像和账号：

```vue
<script setup>
import { useUserStore } from '@/stores/userStore'
const userStore = useUserStore()
</script>

<template>
  <div class="user-meta">
    <div class="avatar">
      <img :src="userStore.userInfo?.avatar" />
    </div>
    <h4>{{ userStore.userInfo?.account }}</h4>
  </div>
</template>
```

注意，这里**一行请求都没发**。

为什么不发？因为头像和账号在登录那一刻就已经拿到了，一直存在 `userStore` 里，还顺手存进了本地存储。再请求一次，图什么？

- 多一次网络往返，页面会先闪一下空白
- 多一份数据：万一用户在别处改了昵称，store 里是旧的、接口给的是新的，页面上就会冒出两个不同的名字

第二条才是要命的地方。就像户口本只有一本——要是每家自己抄一份，过两天一定对不上。

这个原则有个响亮的名字：**单一真相源**（Single Source of Truth）。翻译成人话：同一件事，整栋楼只写在一个本子上。

那两个 `?.` 也不是随手加的。用户信息是异步到家的，头一次渲染时 `userInfo` 可能还是空的，直接写 `userInfo.avatar` 就像在还没搬进来的房间里喊人，会直接报错。加了 `?.` 相当于「人不在就先留个空位」，等数据到了自动补上。

## 五、猜你喜欢：复用首页的商品卡片

个人中心下面有一块「猜你喜欢」，接口很短：

```js
export const getLikeListAPI = ({ limit = 4 }) => {
  return request({
    url: '/goods/relevant',
    params: { limit },
  })
}
```

组件里：

```vue
<script setup>
import { onMounted, ref } from 'vue'
import GoodsItem from '@/views/Home/components/GoodsItem.vue'
import { getLikeListAPI } from '@/apis/home'

const likeList = ref([])

const getLikeList = async () => {
  const res = await getLikeListAPI({ limit: 4 })
  likeList.value = res.result
}

onMounted(() => getLikeList())
</script>

<template>
  <div class="goods-list">
    <GoodsItem v-for="good in likeList" :key="good.id" :goods="good" />
  </div>
</template>
```

这一节的真正看点不是那几行代码，是那个 import 路径：`@/views/Home/components/GoodsItem.vue`。

**它跑去首页的目录里拿组件了。**

好处理由很明显：同一张商品卡片，图的比例、价格的字体、标题的省略方式都一模一样，用户不该在两处看到两种「商品」。就像同一款饼干摆在两个货架上，包装必须一致。

坏处理由也很明显：会员中心从此依赖上了首页的目录结构。哪天首页装修，把 `GoodsItem` 搬到了公共仓库，会员中心这边就直接断货。

判断标准一句话：**这个组件是不是要跨页面用。** 如果是，它就不该住在任何一个页面的仓库里，该升到公共层去。课件为了少建目录留在原地，但你自己做项目时，`GoodsItem` 应该住进 `src/components/`。

还有一件小事：`onMounted` 里请求，意味着**每次进这间屋子都会重新要一次推荐**。从「我的订单」切回「个人中心」，猜你喜欢会刷新一遍。这通常没关系——推荐位本来就该给新的；但如果它变成了负担，就该考虑缓存或者 `keep-alive`。

## 六、我的订单：一份参数对象驱动整个列表

订单列表的接口：

```js
/*
params: {
  orderState: 0,   // 0 = 全部
  page: 1,
  pageSize: 2
}
*/
export const getUserOrder = (params) => {
  return request({
    url: '/member/order',
    method: 'GET',
    params,
  })
}
```

组件里就维护一张「点餐单」：

```js
const orderList = ref([])
const total = ref(0)

const params = ref({
  orderState: 0,
  page: 1,
  pageSize: 2,
})

const getOrderList = async () => {
  const res = await getUserOrder(params.value)
  orderList.value = res.result.items
  total.value = res.result.counts
}

onMounted(() => getOrderList())
```

这张单子上就三样东西：要看哪种状态的订单、要第几页、每页几道菜。**改单子，再重新点一次菜**——整个列表的交互模型就这么简单。

三行赋值值得逐个说：

**`orderList = res.result.items`**：菜端上来的这一摞。注意它在 `items` 里，说明后端把「这一摞」和「一共有多少」打包在同一个盒子里递给你。

**`total = res.result.counts`**：一共多少道菜。**必须问后厨要**。要是自己数手上这一摞（`orderList.length`，只有 2 条），那就永远只有一页——像数自己手里的两页纸，就说整本书只有两页。

**`params` 得是响应式的**：整张单子换掉才会触发更新。传参的时候记得是 `params.value`，写成 `params` 就是把「装单子的夹子」递给了后厨（序列化出来是个空对象）。

原稿里还有一个真实的坑，很适合记住：`total` 必须先声明再使用。如果先写 `total.value = res.result.counts`，后面才 `const total = ref(0)`，代码会直接报错 `Cannot access 'total' before initialization`。这叫「暂时性死区」——**钥匙还没领到，就去开门。**

这种报错最麻烦的地方在于：它不在保存时报，而是页面一打开、`onMounted` 执行到那一行才炸，而那一行看着完全正常。

## 七、tab 与分页：两个入口，同一份状态

列表上面是一排 tab，下面是分页。看着是两件事，其实是**同一张点餐单的两个出口**。

tab：

```js
const tabTypes = [
  { name: 'all', label: '全部订单' },
  { name: 'unpay', label: '待付款' },
  { name: 'deliver', label: '待发货' },
  { name: 'receive', label: '待收货' },
  { name: 'comment', label: '待评价' },
  { name: 'complete', label: '已完成' },
  { name: 'cancel', label: '已取消' },
]

const tabChange = (name) => {
  params.value.orderState = stateMap[name]
  params.value.page = 1
  getOrderList()
}
```

分页：

```js
const pageChange = (page) => {
  params.value.page = page
  getOrderList()
}
```

```vue
<el-pagination
  :total="total"
  :page-size="params.pageSize"
  background
  layout="prev, pager, next"
  @current-change="pageChange"
/>
```

三件必须说清的事。

**第一件：tab 的名字和接口的编号对不上。**

菜单上写的是「A 套餐」「B 套餐」，可厨房里的单子上编号是「套餐 1 号」「套餐 2 号」。你直接把「A 套餐」这三个字报给厨房，厨师只能愣住。

`'all'`、`'unpay'` 这些是给人看的名字，而 `orderState` 是要发给后端的数字 0–6。所以中间必须有一张对照表：

```js
const stateMap = {
  all: 0,
  unpay: 1,
  deliver: 2,
  receive: 3,
  comment: 4,
  complete: 5,
  cancel: 6,
}
```

直接把 `'unpay'` 塞进 `orderState`，后端要么给你 400，要么给你一个空列表。

**第二件：换了 tab，必须回到第 1 页。**

这个坑特别隐蔽。用户翻了 3 页，然后点了「待付款」——如果没重置 `page`，请求就变成了「待付款的第 3 页」。而待付款可能只有 1 页，于是返回空，页面显示「暂无订单数据」。

用户看到的结论是「我明明有待付款的订单，网站却说没有」。而这个 bug 只在「翻过页之后又切 tab」这条路上出现，手工点两下测不出来。

**第三件：`total` 要绑后端的条数。**

换了 tab，总数变了，`el-pagination` 自动算出新的页数——因为 `:total` 是活的。这也是为什么它不能自己数当前页。

至于 `layout="prev, pager, next"`，它决定这条分页带长什么样：上一页、页码、下一页，不含「共 N 条」。想显示总数，改成 `layout="prev, pager, next, total"`。

## 八、工程实践与常见坑

1. **空 path 只能有一条**，它是「只报 `/member` 时该看谁」的答案。
2. **孩子的门牌号不要带前导斜杠**，`'order'` 才是 `/member/order`，`'/order'` 是另一栋楼。
3. **`to="/"` 的链接必须加 `exact`**，不然它在地球上任何页面都亮着。
4. **个人中心不要再请求一次用户信息**，从 `userStore` 读——账本只有一本。
5. **跨页面用的组件别住在某个页面的仓库里**，`GoodsItem` 该去 `src/components/`。
6. **总数要问后端要**，自己数当前页的条数，分页就永远只有一页。
7. **`const` 变量要先声明再使用**，顺序反了就是「钥匙没领到就去开门」。
8. **tab 的名字和接口的字段之间要有对照表**，不能把 `'unpay'` 直接报给厨房。
9. **切 tab 时页码必须回 1**，否则会请求一个不存在的页。
10. **改每页条数（`pageSize`）时也要回 1**，理由一模一样。
11. **`v-for` 的 `:key` 用订单号**，不要用序号——筛选之后整批换掉，序号会让组件错位复用。
12. **订单级的钱和商品级的钱不是一回事。** `order.payMoney` 是整单，`skus[i].realPay` 是单件，`order.postFee` 是运费，三个不能互相顶替。
13. **状态要翻译成中文再显示**，用户看到的应该是「待付款」，不是「1」。
14. **没有订单时要给空态。** 一片空白会让人以为网站坏了，`<el-empty description="暂无订单数据" />` 至少说明「查过了，确实没有」。
15. **函数名一旦被模板调用，就不算私有。** `fomartPayState` 这个拼法是错的（应该是 format），但它已经被引用；能改的时候尽早改，改不动就加注释说明，别指望别人猜。
16. **待付款的订单要显示倒计时。** 这是支付页那套逻辑的复用，但列表里可能有好几单，得每单各起一个计时器，不能共用一份。

## 一句话总结

会员中心教的是「分层」——把走廊提上去、把房间放下来，把账本收归一处、把入口收敛成一张参数单；剩下的所有坑，几乎都出在这四件事被写乱的时候。
