# 会员中心

> 会员中心是这套课件里第一个「一个页面装下多个页面」的结构。它的技术价值不在长得好看，而在于：怎么用一个外壳带出两个三级页面、怎么让同一份用户信息不必请求两遍、怎么用一份参数对象同时驱动 tab 与分页。

## 一、会员中心的位置：一个「壳」加两个三级页面

前面的页面都是「一个路由对应一个页面」。首页是一个页面，分类页是一个页面，支付页是一个页面。到了会员中心，结构变了：

```
/member           → 侧边栏 + 内容区（壳）
/member           → 个人中心（默认三级页）
/member/order     → 我的订单
```

用户在左侧点「个人中心」或「我的订单」，只有右边那块内容换掉，左边那列导航不动。这是嵌套路由最典型的用途——**把不变的部分提上去，把变的部分放下去**。

这个模式在 Layout 那一章已经用过一次：`Layout` 是外壳，首页、分类页、详情页都是它的子路由。会员中心是同一件事的第二层——`Layout` 里再套一个 `Member`，`Member` 里再套 `UserInfo` 与 `UserOrder`。

于是整个应用的路由层级变成三层：

```
Layout
├── Home / Category / Detail ...
├── Member                  ← 新增的外壳
│   ├── ''   → UserInfo
│   └── order → UserOrder
└── ...
```

**为什么要多这一层？** 因为侧边栏（我的账户、交易管理两组链接）属于会员中心这个区域，不属于任何一个具体页面。如果把它写进 `UserInfo` 和 `UserOrder` 各自的模板里，就是两份重复代码；将来加「收货地址」又是一份。

这个判断标准可以一直复用：**当一个区域里有多个页面共享同一块 UI 时，把那块 UI 提到共同的父级路由上。**

## 二、路由：`/member` 与空 path 作默认

先写外壳组件，它的模板里只有一块内容区是活的：

```vue
<template>
  <div class="container">
    <div class="xtx-member-aside">
      <div class="user-manage">
        <h4>我的账户</h4>
        <div class="links">
          <RouterLink to="/member/user">个人中心</RouterLink>
        </div>
        <h4>交易管理</h4>
        <div class="links">
          <RouterLink to="/member/order">我的订单</RouterLink>
        </div>
      </div>
    </div>
    <div class="article">
      <RouterView />
    </div>
  </div>
</template>
```

`<RouterView />` 那行是整个组件的关键——它是一块占位，三级路由的组件会渲染到这里。

路由配置：

```js
{
  path: '/member',
  component: Member,
  children: [
    {
      path: '',              // 空 path：/member 本身
      component: MemberInfo,
    },
    {
      path: 'order',         // /member/order
      component: MemberOrder,
    },
  ],
}
```

**空 path 的那一条，就是「默认三级页」。** 用户访问 `/member` 时，路由匹配到父级 `Member`，再匹配到 path 为空的那条子路由，于是右侧渲染 `MemberInfo`。

这个写法有三个细节：

1. **子路由的 path 不要以 `/` 开头。** 写 `path: '/order'` 会变成绝对路径 `/order`，而不是 `/member/order`。Vue Router 对此有明确规则：子路由的 path 不加前导斜杠，父级会自动前缀。
2. **空 path 只能有一条。** 两条 `path: ''` 会让匹配结果不确定。
3. **`/member` 与 `/member/` 是同一件事**，Vue Router 默认会忽略末尾斜杠，不必额外处理。

外壳组件的定位也顺带定下来了：它不该有自己的状态、不发自己的请求。它只做两件事——摆好侧边栏，留一个出口。一旦外壳开始管数据，它就会和子页面争夺同一个真相源。

## 三、侧边栏：链接激活态与 `exact-active`

侧边栏看上去只是几个链接，但「当前在哪一页」这个视觉反馈必须正确。Vue Router 给 `RouterLink` 自动加两个类：

| 类名 | 什么时候加 |
|---|---|
| `router-link-active` | 当前路径**以**链接的 to 开头 |
| `router-link-exact-active` | 当前路径**完全等于**链接的 to |

差别在于前缀匹配。`to="/member"` 这个链接，在访问 `/member/order` 时也会被加上 `active`——因为 `/member/order` 确实以 `/member` 开头。

这在侧边栏里通常不是问题（你希望父级一直高亮），但在导航栏里就会出问题：首页的 `to="/"` 会在所有路径上高亮，因为所有路径都以 `/` 开头。所以导航栏里那个 `to="/"` 必须配 `exact`：

```vue
<RouterLink to="/" exact>首页</RouterLink>
```

而会员中心这几个链接是同级的具体路径，用默认行为就够了：

```scss
a {
  display: block;
  padding: 15px 0;
  color: #666;
  position: relative;

  &.active,
  &.router-link-exact-active {
    color: $xtxColor;

    &:before {
      display: block;
    }
  }

  &:before {
    content: '';
    display: none;
    width: 6px;
    height: 6px;
    border-radius: 50%;
    position: absolute;
    top: 19px;
    left: -16px;
    background-color: $xtxColor;
  }
}
```

那个小圆点是纯 CSS 画的：默认 `display: none`，激活时 `display: block`。比起放一个图标元素，它的好处是不占 DOM、不依赖字体文件。

## 四、个人中心：从 Pinia 读，而不是再请求一次

个人中心要显示头像和账号：

```vue
<script setup>
import { useUserStore } from '@/stores/userStore'
const userStore = useUserStore()
</script>

<template>
  <div class="user-meta">
    <div class="avatar">
      <img :src="userStore.userInfo?.avatar" />
    </div>
    <h4>{{ userStore.userInfo?.account }}</h4>
  </div>
</template>
```

注意这里**没有发请求**。头像和账号在登录页就已经拿到了，存在 `userStore` 里，还带持久化。再请求一次接口意味着：

- 多一次网络往返，页面会闪一下
- 多一份可能不同步的数据：如果用户改了昵称，store 里还是旧的，接口返回是新的，页面上就会有两个不同的名字

第二条才是关键。**同一份数据只能在系统里存一份**，否则迟早不一致。这条原则有一个专门的名字：单一真相源（Single Source of Truth）。

那两个 `?.` 也不是装饰。用户信息是异步写入 store 的，首次渲染时 `userInfo` 可能还是 `null`，`userInfo.avatar` 会直接抛错。可选链让首屏先渲染出空头像框，等数据到了再自动补上。

## 五、猜你喜欢：复用首页的商品卡片

个人中心下方有一块「猜你喜欢」，接口是：

```js
export const getLikeListAPI = ({ limit = 4 }) => {
  return request({
    url: '/goods/relevant',
    params: { limit },
  })
}
```

组件里：

```vue
<script setup>
import { onMounted, ref } from 'vue'
import GoodsItem from '@/views/Home/components/GoodsItem.vue'
import { getLikeListAPI } from '@/apis/home'

const likeList = ref([])

const getLikeList = async () => {
  const res = await getLikeListAPI({ limit: 4 })
  likeList.value = res.result
}

onMounted(() => getLikeList())
</script>

<template>
  <div class="goods-list">
    <GoodsItem v-for="good in likeList" :key="good.id" :goods="good" />
  </div>
</template>
```

这一节的真正内容不是那几行代码，而是那个 import：`@/views/Home/components/GoodsItem.vue`。

**它从首页的目录里拿组件。** 这在工程上是个需要停下来看一眼的决定。

好处是显然的：商品卡片的样式、图片比例、价格排版完全一致，用户不需要在两处看到两种「商品」。坏处也很显然：会员中心开始依赖首页的目录结构——哪天首页重构，把 `GoodsItem` 挪到 `components/common/`，会员中心就断了。

判断标准是：**这个组件是不是「跨页面复用」的。** 如果是，它就不该住在任何一个页面的目录里，而应该升到公共层。课件为了少建目录留在了原地，但你自己做项目时，`GoodsItem` 应该放在 `src/components/`。

还有一个细节：`onMounted` 里调用，意味着**每次进入 `UserInfo` 都会重新请求一次**。从「我的订单」切回「个人中心」，猜你喜欢会刷新。这通常没问题（推荐位本来就要新数据），但如果它变成了性能负担，就该考虑缓存到 store 或加 `keep-alive`。

## 六、我的订单：一份参数对象驱动整个列表

订单列表的接口是：

```js
/*
params: {
  orderState: 0,   // 0 = 全部
  page: 1,
  pageSize: 2
}
*/
export const getUserOrder = (params) => {
  return request({
    url: '/member/order',
    method: 'GET',
    params,
  })
}
```

组件里维护一份参数对象：

```js
const orderList = ref([])
const total = ref(0)

const params = ref({
  orderState: 0,
  page: 1,
  pageSize: 2,
})

const getOrderList = async () => {
  const res = await getUserOrder(params.value)
  orderList.value = res.result.items
  total.value = res.result.counts
}

onMounted(() => getOrderList())
```

这三行赋值值得逐条看：

**`orderList = res.result.items`** —— 列表数据。注意是 `items` 而不是直接 `result`，说明后端把列表和总数包在了一个对象里。这个形状在分页接口里非常常见。

**`total = res.result.counts`** —— 总条数，**必须来自服务端**。用 `orderList.value.length` 算页码是错的：那只是当前页的条数（2 条），永远只有一页。

**`params` 是个 `ref`** —— 整个对象替换才触发更新。如果写成 `params.value.page = 2` 也能用（Vue 3 的 `ref` 对对象做了深层响应），但要注意传给接口时是 `params.value`，别传成了 `params`（那会传进去一个 `Ref` 对象，序列化成 `{}`）。

这里还有一个原稿里的真实 bug 值得提：`total` 必须先声明再使用。如果在 `getOrderList` 里写了 `total.value = ...`，而 `const total = ref(0)` 在后面，会直接抛 `Cannot access 'total' before initialization`——`const` 的暂时性死区（TDZ）。这类错误的诡异之处在于：它是运行时抛的，`onMounted` 里执行到才报，堆栈指向的那一行看起来完全正常。

## 七、tab 与分页：两个入口，同一份状态

列表上面是 tab，下面是分页。它们看起来是两件事，其实是**同一个 `params` 对象**的两个出口。

tab 部分：

```js
const tabTypes = [
  { name: 'all', label: '全部订单' },
  { name: 'unpay', label: '待付款' },
  { name: 'deliver', label: '待发货' },
  { name: 'receive', label: '待收货' },
  { name: 'comment', label: '待评价' },
  { name: 'complete', label: '已完成' },
  { name: 'cancel', label: '已取消' },
]

const tabChange = (name) => {
  params.value.orderState = stateMap[name]   // 注意这里是映射，不是直接赋值
  params.value.page = 1                      // 切 tab 必须回到第 1 页
  getOrderList()
}
```

分页部分：

```js
const pageChange = (page) => {
  params.value.page = page
  getOrderList()
}
```

```vue
<el-pagination
  :total="total"
  :page-size="params.pageSize"
  background
  layout="prev, pager, next"
  @current-change="pageChange"
/>
```

这里有三个必须说清的点。

**第一，tab 的 `name` 是字符串，接口要的是数字。** `'all'`、`'unpay'` 这些是给人看的标识，而 `orderState` 是 0–6 的数字。直接 `params.value.orderState = 'unpay'` 会把字符串发给后端，得到 400 或者一个空列表。所以中间必须有一层映射：

```js
const stateMap = {
  all: 0,
  unpay: 1,
  deliver: 2,
  receive: 3,
  comment: 4,
  complete: 5,
  cancel: 6,
}
```

**第二，切 tab 必须把 `page` 重置为 1。** 否则用户在第 3 页点「待付款」，请求的是「待付款的第 3 页」——如果待付款只有 1 页，返回空列表，页面上就会出现「暂无订单数据」，而实际上是有订单的。这是这类页面最常见的一个 bug，而且只在「翻过页之后又切 tab」这条路径上出现，手工测试很容易漏掉。

**第三，`total` 必须绑服务端的 `counts`。** 换了 tab，总数会变，`el-pagination` 的页数也跟着变，这是自动的——因为 `:total` 是响应式的。

至于 `layout="prev, pager, next"`，它决定分页条长什么样：上一页、页码、下一页，不含「共 N 条」与「跳转」。想要总数显示，改成 `layout="prev, pager, next, total"` 即可。

## 八、工程实践与常见坑

1. **空 path 只能有一条**，它是「访问父路径时显示哪个子页」的答案，多了就匹配不确定。
2. **子路由的 path 不要带前导斜杠**，`path: 'order'` 才是 `/member/order`。
3. **`to="/"` 的导航链接必须加 `exact`**，否则它在所有页面都高亮。
4. **个人中心不要再请求一次用户信息**，从 `userStore` 读，保证同一份数据只有一个来源。
5. **跨页面复用的组件不该住在某个页面的目录里**，`GoodsItem` 应该放在 `src/components/`。
6. **`total` 必须从接口的 `counts` 取**，用 `orderList.length` 会让分页永远只有一页。
7. **`const` 变量必须在声明之后使用**，`total.value = ...` 写在 `const total = ref(0)` 之前会抛 TDZ 错误。
8. **tab 的 name 与接口的 `orderState` 之间要有映射表**，不能直接赋值。
9. **切 tab 时 `page` 必须重置为 1**，否则会请求一个不存在的页码。
10. **改 `pageSize` 时同样要重置 `page`**，理由同上。
11. **`v-for` 的 `:key` 用 `order.id`**，不要用 index——订单列表会因筛选而整体替换，index 会导致组件状态错位复用。
12. **订单级的金额与商品级的金额不是一回事。** `order.payMoney` 是整单应付，`order.skus[i].realPay` 是单件实付，`order.postFee` 是运费；三者不能互相替代。
13. **`orderState` 的显示要做映射，不要把数字直接印在页面上。** 用户看到的应该是「待付款」，不是「1」。
14. **空列表要渲染空态。** `<el-empty description="暂无订单数据" />` 比一片空白好得多，用户至少知道「请求成功了，只是没有订单」。
15. **状态映射表一旦被模板引用，函数名就不要随便改。** `fomartPayState` 这个拼写是错的（应为 format），但它已经被模板调用，改名就得同时改所有调用点——**能改的时候尽早改，改不动的时候加注释说明原因**。
16. **待付款的订单要显示倒计时。** 这是支付页那套逻辑的复用，但列表里可能是很多单，需要为每一单起一个独立的计时，不能共用一份。
